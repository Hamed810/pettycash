# T240 / T241 Implementation Report — Database Portability Enforcement

**Feature**: PettyCash V1 Core Workflow (`specs/001-pettycash-v1-core`)
**Date**: 2026-09-25
**Status**: Both tasks complete. T239 (CI matrix) deliberately not started — dependency-blocked.

## T241 — Declare the supported backend set

`appinfo/info.xml` now declares the V1 backend set inside `<dependencies>`:

```xml
<database>mysql</database>
<database>pgsql</database>
<database>sqlite</database>
<nextcloud min-version="34"/>
```

**The element order is load-bearing and was verified, not assumed.** The authoritative
`https://apps.nextcloud.com/schema/apps/info.xsd` defines `<dependencies>` as an `xs:sequence`:

```
php -> database -> command -> lib -> owncloud -> nextcloud -> architecture -> backend
```

Appending `<database>` *after* the existing `<nextcloud>` element — the obvious minimal edit —
would have produced a schema-invalid file that Nextcloud rejects on load. The declaration was
placed before `<nextcloud>` accordingly.

The same XSD confirms the `databases` enumeration is exactly `sqlite | mysql | pgsql`, so `oci`
is **structurally not declarable** at all. The `oci` exclusion is therefore enforced by the
schema itself, independent of the deferred constraint recorded in `plan.md`.

Verification: sequence validated programmatically against the fetched XSD; `occ app:list` still
reports `pettycash: 1.0.0`; live authenticated `GET /me` and `GET /sheets` both return HTTP 200.

## T240 — Static portability check

`scripts/portability-check.js` (Node, no new dependencies) enforces the construct catalogue in
`research.md` Decision 16. It is wired as the **first** gate in `npm run check` so a portability
regression fails before typecheck.

| Rule | Rejects |
|---|---|
| `declared-backends` | missing/duplicate `<database>` entries, `oci`, and out-of-XSD-order `<dependencies>` children |
| `raw-sql` | SQL string literals passed to `executeQuery`/`executeStatement`/`executeUpdate` |
| `abstraction` | `Doctrine\DBAL` types, `getInner()`, `new \OC\DB\…`, raw SQL via `prepare()` |
| `delete-limit` | deletes relying on a `LIMIT` clause (MySQL/MariaDB-only) |
| `group-by` | selected columns that are neither aggregated nor grouped (`ONLY_FULL_GROUP_BY`) |
| `schema-identifier` | table/column/index names over 63 chars, allowing for the `oc_` prefix (PostgreSQL `NAMEDATALEN`) |
| `schema-nullability` | `NOT NULL` boolean columns (PHP casts `false` to `''`, which PostgreSQL rejects) |

Deliberately **not** enforced: Oracle-specific limits (table ≤ 27 incl. prefix, strings ≤ 4,000),
per the user's decision not to treat unverified Oracle-specific limits as V1 requirements.

### Every rule was proven load-bearing

All eight rules were verified with injected violations *and* with valid-SQL probes that must not
fire. Three defects in the check itself were found and fixed during this verification:

1. The GROUP BY clause extractor called `.concat()` on a string and **crashed** the script.
2. The grouped-column list was extracted from the whole statement, so a selected column masked its
   own violation.
3. A false positive on `select("a.id","a.status") … groupBy("a.status")`, which MySQL accepts via
   primary-key functional dependency. Fixed by allowing a bare `id`, valid here because every table
   carries an auto-increment `id` PK.

**Known limitation, stated rather than hidden:** primary-key detection in the `group-by` rule is by
name convention (`id`), not by reading the schema. It also operates on statement text, so a
sufficiently complex multi-line query could evade it. It is a regression guard, not a SQL parser.

A false verification was also caught and corrected mid-task: the first probe run injected
violations as `//` comments, which the check deliberately skips, producing misleading "MISS"
verdicts. The probes were rebuilt with real code.

## Not done, and why

**T239 (CI matrix) was not started.** Its acceptance criterion is that SC-013 becomes achievable,
which requires the suites it runs to exist: `tests/Integration/Persistence/` does not exist
(T236 unstarted), and the representative workflow-query and schema-compatibility checks have no
home yet. Authoring a four-backend harness now would produce jobs that execute nothing, and — with
no persistence suite to run — I could not validate the harness end to end. Shipping unverified CI
would repeat the hollow-green failure mode already caught twice in this task.

Recommended order: **T236** (persistence integration suite) → **T239** (CI matrix) → **T101/T102/
T105/T106** (totals and reporting queries, which are the first real source of `GROUP BY` violations
that T240's rule will police).
