# T258 — Make the draft transaction delete actually delete

**Status**: Complete

## Task

Make `TransactionService::deleteTransaction()` actually delete the draft. It validated ownership,
the open sheet, and the optimistic lock, then inside its transaction called only
`ExpenseSheet::removeTransaction($transaction->id)` — which filters an in-memory array — and re-saved
the sheet and the transaction. No `DELETE` reached `pc_transactions` (now `pettycash_transactions`),
no revision was removed, and the endpoint answered `204 No Content`.

## Why it mattered

The caller was told the expense was deleted while it remained fully present in the database and in
every later total. FR-025 requires that before submission a purchaser can add, edit, and delete
transactions, and Constitution IV requires the server — not the interface — to be the authority on
business effects. A delete that reports success without deleting is a correctness and auditability
defect.

## Implementation notes

**Draft-state guard.** The open-sheet check was not sufficient on its own. A transaction that was
submitted and then returned for correction sits in an open sheet again, so the original condition
would have permitted deleting submitted business history — which Constitution IV forbids. The
service now also requires `TransactionStatus::Draft`.

**Delete order.** `pettycash_transaction_revisions.transaction_id` points at the row being removed,
and the migrations declare no foreign keys. Revisions are therefore deleted first, then
`pettycash_evidence`, then the transaction; any other order would strand rows that no query reaches.

**Evidence.** The transaction's own AppData binaries are removed through `PrivateFileStore` while the
keys are still known, because the repository `delete()` cannot reach the file store. The metadata rows
go with the transaction. This is the FR-058 pre-submission case; after submission evidence is still
only ever deactivated, never deleted.

**Portability.** Three query-builder deletes, no raw SQL and no delete-`LIMIT`, so
`npm run check:portability` remains green.

## Verification detail

`testDeletingASubmittedTransactionIsRefused` asserts two things: that a submitted transaction cannot
be deleted by its owner, and that the transaction is still readable afterwards. Asserting only the
refusal would pass even if the delete removed the row and then reported an error.

## Known limitations

- `DbExpenseTransactionRepository::delete()` also removes `pettycash_evidence` rows directly. That is
  correct only because the service has already restricted the delete to draft state; the repository
  method itself does not re-check, so a future caller could erase submitted evidence through it. The
  port docblock states the precondition, but an enforced invariant would be stronger than a
  documented one.
- The four `ManagementReviewControllerTest` decision failures and the six remaining
  `PurchaserFlowControllerTest` failures are unchanged and owned by T259, T269, T270, and T271.
