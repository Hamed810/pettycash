# T277, T278, T279 — P1 contract path repaired, fixture made a true reset

**Status**: T277 and T278 complete; T279 recorded and open

After T269–T271, four OCS contract failures remained. Each turned out to hide a distinct real
defect, and two were caused by the test fixture rather than the code under test.

## The four failures and their actual causes

| Endpoint | Symptom | Real cause |
|---|---|---|
| `POST /sheets/{id}/submit` | 422 "At least one transaction is required" | Sheet aggregate never loaded its transactions |
| `POST /transactions/{id}/correction` | 403 | Cloned revision lost its owning-transaction join key |
| `POST /transactions/{id}/resubmit` | 422 "Cost center not found: 22222222-…" | UUID passed where a code was expected |
| `PATCH /transactions/{id}` | 422 "Revision is incomplete" | Partial edit nulled untouched fields |

### Submit — the sheet aggregate was always empty

`DbExpenseSheetRepository` deliberately does not compose the sheet's transactions, so a sheet
loaded from the database always carried an empty collection and `assertSubmittable()` rejected
every sheet that genuinely had one. `SubmitSheet` now attaches them via
`ExpenseTransactionRepository::findBySheetId()` before validating. The new dependency is wired in
both `lib/AppInfo/Application.php` and `tests/bootstrap.php`, and in the one integration test that
constructs `SubmitSheet` directly.

### Correction — 403 for an entitled caller

`TransactionRevision::correction()` clones the business fields into a fresh aggregate but not the
owning-transaction join key, and `CreateCorrectionDraft` never carried it over. The save was then
refused by `requireTransactionDbId()`. It now sets `transactionDbId`, exactly as
`TransactionService::createTransaction()` already did.

### Resubmit — the same unit mismatch T257 found

`SubmitSheet` and `ResubmitCorrection` both passed `revision()->costCenterId()` — the cost center's
**public UUID** — to `CostCenterRepository::findByCode()`, which looks up a business code such as
`CC-100`. It could never match. Both now resolve through a private helper that tries the numeric
join key, then the public UUID, then the code snapshot.

This is the third occurrence of that class of defect. It is a good candidate for a single
repository-level lookup that hides the representation difference, rather than a per-callsite helper.

### Update — a partial edit destroyed business data

`PATCH /transactions/{id}` with only an expense date and an amount is legitimate, and building a
new revision left description, cost center, and expense type `null`. The purchaser's own
transaction then failed `assertSubmittable()` — and had it passed, it would have silently dropped
real data. Omitted fields now carry forward from the current revision.

### Two audit defects found alongside

`SubmitSheet` and `ResubmitCorrection` both called `AuditWriter::append((array) $auditEvent)`. But
`append()` reads **snake_case** keys, so casting an `AuditEvent` object produced camelCase
properties, `command_id` was never found, and the insert failed on the NOT NULL column with an HTTP
500. Both now pass a proper snake_case array, matching `ManagementReviewService`.

## T278 — the fixture was not a reset

The seeder's own docblock promises "every run is a reset", but it cleared decisions, evidence, and
audit while leaving two kinds of state behind:

- `POST /sheets/{id}/transactions` writes a real draft with only a date and an amount. Those rows
  accumulated on the fixture sheet until submission walked them and failed on a transaction with no
  cost center — so `testSubmitSheetReturns200WithSubmittedSheetDetail` passed or failed depending
  on which tests had run first.
- Correction revisions were never removed, so a correction run left `revision_number 2` and the next
  run violated `pettycash_transaction_revisions_number_uniq` with `Duplicate entry '42-2'`.

The seeder now removes stray transactions' decisions, evidence, audit, revisions, and the
transactions themselves, then any fixture revision above 1. All five states seed cleanly and
repeatedly.

One trap worth recording: the first attempt at that select used separate `getQueryBuilder()`
instances for `expr()` and `createNamedParameter()`. A parameter from a different builder is never
bound and is emitted verbatim, producing `... (:dcValue1) AND (\`id\` <> :dcValue1)` — a syntax
error that surfaced only as an empty seeder manifest. This is the same trap the `upsert()` docblock
already documents; one builder must serve the whole statement.

## T279 — recorded, not started

`SheetController::formatSheet()` reports `transactionCount` from an aggregate that is still empty at
that point, so a submitted sheet answers `200` with `status: COST_CENTER` and
`transactionCount: 0` — a self-contradictory response. T277 fixed the submission path but not this
read model, so it is left open rather than folded into a completed task.

**0 lost task text** — every deletion is either an intentional `[ ]`→`[x]` checkbox flip or a
