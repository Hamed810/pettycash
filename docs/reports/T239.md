## Why MySQL and MariaDB are separate jobs

ACC-002 requires it, and the run demonstrates it is load-bearing rather than ceremonial. Both
`mysql`-typed jobs report `dbtype=mysql`, yet they resolve to different engines:

| job | `dbtype` | provider | platform |
|---|---|---|---|
| `mysql` | `mysql` | `mysql` | `Doctrine\DBAL\Platforms\MySQL84Platform` |
| `mariadb` | `mysql` | `mysql` | `Doctrine\DBAL\Platforms\MariaDb1010Platform` |
| `postgresql` | `pgsql` | `postgres` | `Doctrine\DBAL\Platforms\PostgreSQL120Platform` |
| `sqlite` | `sqlite3` | `sqlite` | `OC\DB\OCSqlitePlatform` |

A single job would have made that distinction invisible. Platform identity is read from Nextcloud's
own configuration at runtime and printed, so a job cannot report green for the wrong backend.

## Defects found by running it

Each was found by executing a job. None would have been visible by reading the workflow.

1. **The schema fixture refused every backend but MySQL.** It opened its own PDO connection, queried
   `information_schema` + `SHOW INDEX`, and `exit(1)`-ed on `dbtype !== 'mysql'` — so three of four
   jobs could not report a schema at all. Now reads through `IDBConnection::createSchema()`, the
   portable abstraction, and accepts all declared backends.

2. **PostgreSQL's primary-key names would have failed SC-014 falsely.** PostgreSQL reports a primary
   key as `<prefix>pettycash_accounts_pkey`; MySQL/MariaDB report the literal `PRIMARY`. The fixture
   excluded primary keys *by name*, so on PostgreSQL all 15 were reported as unnamed offenders and two
   `SchemaConstraintNamingTest` cases failed against a fully compliant schema. Now excluded *by kind*
   (`Index::isPrimary()`).

3. **The persistence tests hardcoded the lab's user.** Five assertions compared actor columns to the
   literal `'employee1'`, and `leak-a-sheet.php` required the acting user to *hold an account*. Both
   hold in the lab, neither in a fresh CI instance. Assertions now read `PETTYCASH_TEST_USER`; the CI
   pass seeds the acting user via the contract fixture seeder. The pass deliberately does **not** add
   that user to `admin` — `roundtrip-runner.php` uses it as the *non*-administrator, and promoting it
   made exactly the two "a non-administrator is refused" assertions fail.

## Check constraints: reported, not fabricated

Doctrine's portable `Table` has no check-constraint API — measured, reflection over
`Doctrine\DBAL\Schema\Table` yields zero methods or properties containing "check". So the fixture
reports `checkConstraintsObservable: false` rather than an empty list, because "0 offenders out of an
unasked question" is a green light wired to nothing — the exact vacuity `SchemaConstraintNamingTest`
exists to end.

The guarantee moves to `V1SchemaMigrationTest`, which asserts from migration source that no check
constraint is declared. That holds on every backend regardless of engine and is **mutation-verified**:
adding `addOption('checks', …)` to a migration fails it with the offending file named.

## Pre-existing defect this work could not fix inside its scope

No `occ` command worked in a CI container. `composer/autoload.php` returns this repository's
**development** `vendor/autoload.php`, whose `symfony/console` **v8.1.7** shadows Nextcloud's copy —
and Symfony 8 removed `Application::add()` (renamed `addCommand()`), which
`core/register_command.php:116` calls. Every `occ` command registering a core command died with
`Call to undefined method Symfony\Component\Console\Application::add()`.

**This predates T239 and is already known.** `~/projects/nextcloud-lab/shims/nextcloud-core-autoload.php`
documents it in full and binds a shim for exactly this reason; the lab works only because that shim is
present. `composer/autoload.php` itself states the real fix "belongs in the app repository: the file
Nextcloud loads for an app should expose production dependencies only" — a separate change from T239,
deliberately not smuggled in here.

A CI-owned equivalent exists so the matrix can run at all, duplicated because a GitHub Actions runner
cannot mount a file from a sibling checkout. **Deleting that shim and its two mounts is the signal that
the underlying defect has been fixed at source.** That deletion is tracked as follow-up, not left
implicit.

## What this does not claim

- **SC-013 is not claimed.** A success criterion is satisfied by the acceptance record. This is a
  compatibility-suite pass on ephemeral instances, not the acceptance run. ACC-002's outstanding item
  (T239 unchecked, no CI, `info.xml` declarations "stated intent") is closed; the criterion is not.
- **The OCS contract suite is not in the matrix.** It issues live HTTP and authenticates with an app
  token, so its failures would concern credentials and web-server setup rather than the database, and
  would make the matrix red for reasons unrelated to portability. Widening the scope is a separate
  decision.
- **T405 and T171 are untouched** and remain unverifiable for their own environmental reason (the
  Playwright CDN is geo-blocked from this host).
- **`plan.md`'s Constitution Check** now records ACC-002's verification plan as executed.

## Docker safety

Every backend ran in a throwaway container created and removed by the pass, sharing no volume with
`pettycash-lab` or `pts-lab`. `scripts/dev/in-container` is deliberately unused: it targets
`pettycash-lab-nextcloud-1` by name and would reach the wrong runtime. Both labs were confirmed
running and healthy after every run, and the full local PHP suite was re-run green afterwards.
