# T289 — one definition of the `Account` and `Movement` payload shapes

**Task**: T289 (complete)
**Feature**: PettyCash V1 Core Workflow (`specs/001-pettycash-v1-core`)
**Date**: 2026-09-27
**Slice**: US3 finance/account, continuing the area T290, T292 and T293 last touched

## The task

T289 recorded a duplication rather than a defect: `AccountPayloadFormatter` lives in
`Infrastructure/Http/`, which the Application layer may not depend on, so `AccountService` built the
same two arrays itself. The formatter's docblock explained the duplication instead of removing it,
which is at least honest, and the task left the fix open between relocating the projection and
moving formatting into the controllers.

## What was actually there

Three copies of the `Account` shape and three of the `Movement` shape, not two:

| File | Account | Movement |
|---|---|---|
| `lib/Infrastructure/Http/AccountPayloadFormatter.php` | `account()` | `movement()` |
| `lib/Application/Account/AccountService.php` — `listForUser()` | inline | — |
| `lib/Application/Account/AccountService.php` — `accountPayload()` | private twin | — |
| `lib/Application/Account/AccountService.php` — `listMovements()` | — | inline |
| `lib/Application/Account/AccountService.php` — `movementPayload()` | — | private twin |

So the service alone held four of the six, including a pair of private twins of its own inline copies.
The task text said "the same two arrays inline"; the code said more.

## The decision, and the option that was rejected

**Taken: relocate.** `AccountPayloadFormatter` moved to
`lib/Application/Account/AccountPayloadFormatter.php` (namespace `OCA\PettyCash\Application\Account`)
and `AccountService` takes it as a seventh constructor dependency, delegating in all four public
methods. `AccountController` needed no change — it passes the service's array straight through — and
`ReviewController` changed one `use` and one argument order.

**Rejected: have the controllers format from the aggregates.** That is what
`TransactionPayloadFormatter` and `SheetPayloadFormatter` already do, so it is the direction the rest
of the codebase took, and for the two reads it would be fine. It cannot be applied to the two writes,
and the reason is specific rather than stylistic:

`createFor()` and `charge()` return **through `IdempotencyService`**. Their arrays are not only the
HTTP response — they are the *stored* command result that a replay is answered from, read back out of
`pc_command_results` on a later request. Storing identifiers and re-reading the aggregates instead
would mean a replay reports the account balance *as of the replay* rather than as of the charge.
That is present-but-different, which is worse than absent, and it is the precise failure T290's own
task text warns about ("a balance recomputed as if it were about to be spent again"). The frozen
stored answer is correct idempotency; re-deriving it is not.

So the Application layer became the single home, because Presentation depends on Application and not
the reverse. The formatter is a pure aggregate→array mapping that invents no business rule, so putting
it there does not move a rule out of the domain — it makes the contract knowledge it already had
explicit and single-sourced.

### Why not `lib/Application/Dto/`

`plan.md` declares that directory and it does not exist. This was still not done, because reconciling
the declared structure is T238's open work and quietly creating one of its four directories inside a
task about a duplication would be taking a piece of another task without recording it. The formatter
sits beside its only other caller instead. Noted for T238.

## The guard, and why it is structural

A behavioural test cannot see this class of defect. Both copies build the same array, so a projection
that has drifted from its twin still answers every assertion anyone can make about the endpoint, and
the two differ only in the field one of them forgot — which is exactly the field nobody asked about.
That is not hypothetical: `TransactionPayloadFormatter` exists because the transaction payload had a
flat `revision` object with no `allowedActions`, `decisions` or `evidence`, and every affected template
dereferenced `undefined` on a live response while the endpoint answered 200 throughout.

`tests/Integration/Account/AccountPayloadSingleDefinitionTest.php` (6 tests, 9 assertions) therefore
reads the source and fails if `'balanceAfter' =>`, `'sourceRevisionId' =>` or
`'userId' => $account->userUid` is written outside the formatter, naming the offending file.

**The quoted array-key form is load-bearing, and the first version got it wrong.** The bare member
names are also property names on the `AccountMovement` aggregate and column names in
`DbAccountMovementRepository`, so the initial test matched `balanceAfter` in four files and
`sourceRevisionId` in six, three and five of them innocent. Only a file writing the key inside an array
literal is building a contract payload.

Three behavioural tests sit alongside the structural ones, because a text match cannot tell a
projection that is *called* from one that merely exists, and cannot catch a caller that post-processes
the formatter's output.

## Mutation checks

Each guard was checked by breaking the code, not by reading the test.

| Mutation | Structural half | Behavioural half |
|---|---|---|
| Restore the inline `Account` array in `listForUser()` | **fails 1** | passes |
| Make the ledger row lose `sourceRevisionId` *after* formatting | passes | **fails 1** |

Neither half is sufficient on its own, which is why there are two. Both mutations were reverted and
the suite re-run green.

`mutation()` takes `($account, $movement)` rather than the previous `($movement, $account)`. Both
parameters are non-nullable and always supplied together, so this is a readability change with no
behavioural effect; the two call sites were updated together.

## Known limitations

- The guard is a source scan, so it is as good as its literals. It watches the three array keys that
  are unique to these two shapes; a copy written with different key names would not be caught by it,
  which is why the behavioural half exists.
- `SheetPayloadFormatter` and `TransactionPayloadFormatter` remain in `Infrastructure/Http/`, where
  `plan.md` declares only "stream responses and error mapping". Neither has a duplicate, so this task
  did not touch them; the declared-structure reconciliation belongs to T238 and T264.
