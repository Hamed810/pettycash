# T138 — the seven-year floor, measured against MariaDB and held structurally

**Task**: T138 (complete)

**Date**: 2026-09-27
**Pass**: Autopilot implementation pass 2 of 50
**Requires**: T237 (the subject it asserts against)

## What the task asked for

"Write failing integration test verifying audit records younger than 7 years are never archived or
deleted (FR-057 7-year retention floor)". It could not be written before T237, because the retention
policy it tests did not exist.

## The claim, stated precisely

"Never archived or deleted" is enforced at the **application** boundary, not by the database. MariaDB
will execute a `DELETE` from `pettycash_transaction_audit` if something issues one, and pretending
otherwise would be the kind of claim that reads well and proves nothing. What FR-053 and Constitution IV
actually require is that no service, port, or repository exposes a path that does it, and that the
schema has nowhere to record that it was done.

So the file has two halves, and it is the combination that holds the guarantee:

| Half | What it establishes | Where |
|---|---|---|
| Real database | A young row survives, is still protected, and evaluating the policy removes nothing. A ten-year-old row is archivable. | `retention` scenario in `roundtrip-runner.php` |
| Structural | No public method on `AuditEventRepository`, `AuditRetentionPolicy` or `RetentionPolicyService` is a removal or rewrite path, and the real schema has no archive/deletion column. | reflection, in the test file |

## Why the ten-year-old row exists

A test that wrote only a young record and asserted "still protected" would pass against a policy that
answered `protected` for every input, including records centuries old. The old row is the control.
`testTheYoungAndOldRecordsGetOppositeVerdicts` asserts the two come back with opposite verdicts, and the
mutation check below confirms it bites.

The old row must still be *readable* too — archival is not deletion, and `testARecordOlderThanSevenYearsIsArchivable`
asserts `survived` as well as `archivable` so the two cannot be quietly conflated.

## The structural half, and why it asserts data rather than a pattern

`testNoPublicMethodCanRemoveOrRewriteAnAuditRecord` matches public method names against a removal
pattern, and it fails the moment somebody adds `delete()` to the port. Alongside it,
`testTheAuditPortOffersOnlyReadsAndAnAppend` and `testThePolicyObjectIsAdvisoryOnly` assert the exact
method lists. That is deliberate duplication: the pattern catches a `purge()` or `expunge()` that the
list assertion would also catch, but the list makes adding a method a *visible act in a diff* rather
than something only a regex notices.

`AuditRetentionPolicy::permitsDeletion()` is intentionally not matched by the pattern. It is a
question, not an operation — the value object has to be able to ask and answer false, and that is
exactly what makes "the policy may never rewrite business history" a property of the type rather than
a promise about its callers.

## Two things the real database turned up

**1. `createSchema()` returns prefixed table names, and `hasTable()` does not accept the logical name.**
`$db->createSchema()->getTables()` yields `oc_pettycash_transaction_audit`, and
`$schema->hasTable('pettycash_transaction_audit')` is **false** on a live instance. The scenario
therefore matches tables by *suffix* and reports their columns under the logical name. That is not a
workaround — it is what FR-078 requires: no test may hardcode an instance prefix such as `oc_`.
`$db->getPrefix()` is deliberately not consulted either, because it does not report the prefix the
query builder actually applies, so trusting it would have been wrong in a way that only showed up on
another instance.

**2. `AuditEvent::$commandId` is nullable in the domain but NOT NULL in the schema.**
`lib/Migration/Version010200Date20260920000000.php:47` declares `command_id` with no `notnull => false`,
so it is NOT NULL, while `AuditEvent::__construct()` types it `?string`. The first two attempts to run
this scenario failed with `Column 'command_id' cannot be null`. The existing `expense` scenario passes
a real command id and so never hit it.

This is a **latent domain/schema mismatch, not a defect this task fixed**, and it is recorded here
rather than appended as a new task, because convergence owns that decision and it should be judged
against the whole set rather than discovered by one test. Either the column should become nullable —
`data-model.md` lists `command_id` as "Correlation/idempotency reference", which reads as optional —
or the domain should stop claiming it is nullable. Nothing currently depends on the nullable form: the
`expense` scenario, the contract fixtures, and `AuditWriterService` all supply one.

## Limitations

- The real-database half proves the *application* exposes no removal path and the schema offers nowhere
  to record one. It does not and cannot prove MariaDB refuses a `DELETE`; it does not.
- The runner deletes its own rows in a `finally`, and a new fingerprint sweep entry
  (`explanation LIKE 'Retention probe %'`) was added for both audit tables as a backstop, matching the
  two-sweep pattern T236 established after an early run leaked 32 rows into the shared database.
- Psalm and `php-cs-fixer` remain unavailable for the reasons recorded in `docs/reports/T237.md`.
