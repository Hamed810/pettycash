# T294 — Configuration audit reaches `pettycash_configuration_audit`

**Status:** complete
**Suite at completion:** 640 tests, 2840 assertions, 1 known baseline failure (T275), no new failures

## What was wrong

FR-056 requires transaction audit and configuration audit to stay separately identifiable.
Nothing in the application wrote the configuration table. `grep -rn pettycash_configuration_audit lib/`
returned the migration and nothing else, so the table was permanently empty, and FR-055's role-scoped
configuration-audit visibility had no subject to scope over.

## Task prose was stale in two ways

The task said `AuditWriterService::appendConfiguration()` (line 90) "is the intended writer and is
never called". It did not exist — T296 had deleted the dead method. The work was to write a writer, not
to wire a dormant one.

It also said the repository hardcodes the table in "all seven of its methods". The six reads all use
`select('*')` through one shared `mapRow()`, so they needed only a bound table name. But `mapRow()`
itself hardcoded `entityType=''`/`entityId=null` with the comment *"for transaction audit"* and read
`$row['sheet_id']` unguarded. A correctly bound configuration read would have warned on absent columns
and returned a null subject: the configuration stream was **unreadable as well as unwritten**. The task
did not record that.

## What landed

**Stream as a constructor binding, not a `save()` parameter.** `DbAuditEventRepository` takes a
`$stream` name resolved through a private two-entry whitelist to a table plus a subject-column set. An
unrecognised name throws at construction rather than falling back — a silent fallback would write
configuration events into the transaction table, the precise failure this task exists to prevent.

This left the seven-method `AuditEventRepository` port unchanged and all six production `append()` call
sites untouched, and made the reads stream-scoped for free.

The two tables are disjoint in subject columns, so `save()` writes exactly its own set:

| Stream | Table | Subject columns |
|---|---|---|
| transaction | `pettycash_transaction_audit` | sheet_id, transaction_id, revision_id, stage, decision_id |
| configuration | `pettycash_configuration_audit` | entity_type, entity_id |

**`appendConfiguration()` is back, through the port.** Added to the `AuditWriter` interface, not to the
service alone, so `AuditWriterSurfaceTest`'s rule — every public writer method is a port member — holds.
A configuration event with no `entity_type` is refused rather than written.

**Settlement writes the charge.** `FinanceSettlementService::recordDecision()` emits an
`ACCOUNT_CHARGED` configuration event naming the account it debited, on approval only, so a rejection or
return does not accrue a charge. The payload records no `before` balance on purpose:
`recordConsumption()` mutates the account in place, so a "before" read there would be the
post-consumption value wearing a "before" label.

**T253 settled the naming:** `entity_type`/`entity_id` win over the task's
`subject_type`/`subject_public_id`, so that is what T294 writes and what T093 will query.

## Verification

The PHPUnit process has no `IDBConnection` — the real database is reachable only from the separate
`roundtrip-runner` process — so **no single test can span settlement to table**. Both ends are covered:

| Test | Suite | Proves |
|---|---|---|
| `testAConfigurationAuditEventLandsInItsOwnTableAndIsInvisibleToTheTransactionStream` (18 assertions) | real MariaDB | a real row in `oc_pettycash_configuration_audit`; entity_type/entity_id survive; transaction subject columns come back null; shared actor columns survive; the transaction binding **cannot read it** |
| `testFinanceApprovalAuditsTheChargeInTheConfigurationStream` | integration | settlement calls `appendConfiguration` with the right account, event type and command id, and does **not** smuggle it into the transaction stream |
| `testARejectedDecisionLeavesNoConfigurationCharge` | integration | a decision that moves no money writes no charge |
| `testEachWriterPathReachesOnlyItsOwnStream` | unit | each writer path reaches only its own repository |
| `testAConfigurationEventWithoutASubjectIsRefused` | unit | a subjectless configuration event is not written |

All mutation-proven:

- collapsing both streams onto the transaction table → caught (`Unknown column 'entity_type'`; the
  disjoint columns make a stream mix-up a schema error, not silent corruption)
- removing the settlement's `appendConfiguration` call → caught (`actual size 0 matches expected size 1`)

## Regression caught during the batch

The first `mapRow()` rewrite typed its int conversion `?string`, and the real-DB round trip failed
across 9 tests: this platform's driver returns **int** for BIGINT, which the original code tolerated.
Fixed to accept `int|string|null`. The real-DB suite caught what the in-memory doubles could not.

## Known limitations

- No test spans settlement → configuration table in one run, by environment. The two suites above
  compose to cover the path; neither alone does.
- `AuditWriterSurfaceTest` still asserts `appendTransaction` is gone. `append()` is the transaction path.
- Configuration events are not exposed by any API yet. T093 (role-scoped query) and T086 (before/after on
  every configuration mutation) remain open and build on this.
