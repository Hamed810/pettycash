# T282, T284, T285 — Restore the frontend test suites' validity

**Status**: Complete (3 of the 4 tasks appended by Phase 36; T283 remains open)

## Why these three first

Convergence found the project quality gate red for a reason no open task covered: `npm test`
reported **58 failed / 18 passed with 26 unhandled errors**, while `T034`, `T042`, `T047`, and `T053`
were all marked `[x]`. Constitution V's Delivery rule 8 says a task is complete only when
implementation, verification, and task status agree — they did not.

The deeper problem was that the counts were not trustworthy in either direction:

- **US2 measured nothing.** All 19 `ManagementReview.spec.ts` tests died inside `vue-router` during
  `mount()`, before a single assertion ran.
- **US1's 18 green tests passed for the wrong reason.** The axios mock resolved `undefined`, so every
  mount-time fetch raised an unhandled `TypeError`, the store stayed empty, and the component
  rendered whatever it renders for "no data" — which happened to satisfy the structural assertions.

So no conclusion about the US1 or US2 frontend could be drawn from the suite until the harnesses
were fixed. That is what these three tasks do; `T283` then acts on trustworthy numbers.

## T285 — the OCS unwrap

`return response.data.ocs.data` was a three-level unguarded dereference, and the `catch` below it
only recognised `AxiosError`. A session expiry, a proxy error page, or an empty 204 each produced a
raw `TypeError` that failed the `isAxiosError` branch and was re-thrown verbatim — so the caller
never received the `ApiError` envelope `T030` is accountable for.

`unwrap()` now type-checks the body before dereferencing and returns either the payload or an
`ApiErrorBody`. It also treats an `error` member inside a 2xx `ocs.data` as a rejection, because OCS
permits a failure to arrive as HTTP 200 and a caller must not be handed a business failure as if it
were a payload.

`tests/Frontend/http.spec.ts` (15 tests) was proven RED first: the seven non-OCS cases each failed
with exactly the predicted `TypeError: Cannot read properties of undefined`.

## T284 — the rejection leak was shipping

Fixing the mock revealed two further facts.

**The mock was wrong about a shape, not the client.** `revisions.value = await listRevisions()`
assigns into a `ref<Revision[]>`; answering `/revisions` with a page produced
`TypeError: transactionStore.revisions.map is not a function` at `TransactionDetailView.vue:53`. The
contract declares a bare `Revision[]` (`contracts/ocs-api.yaml:552-565`), so the client was right.
The declared shape is now encoded in the mock.

**The unhandled rejections were a production defect.** Every store records a failure in its own
`error` ref and then re-throws — and five views fired those loads from `onMounted` and `watch` with
nothing attached, so any failed load became an unhandled rejection in the user's console. The store
re-throw is load-bearing (`SheetFormView.handleSubmit` relies on it to skip its navigation), so the
fix belongs at the fire-and-forget call sites, each now absorbing the rejection with a comment
pointing at the alert that already renders the error.

## T282 — the US2 suite measured nothing

All five review views call a router composable in `setup()` and render `<RouterLink>`; the tests
mounted them with pinia only, so all 19 died in `vue-router` with
`TypeError: Cannot read properties of undefined (reading 'resolve')`.

Three sources of false confidence were removed:

1. The router is now built from the application's own exported `routes` table, so a route name a
   view links to cannot silently go missing in a test copy.
2. `DecisionForm.vue` and `PriorDecisionHistory.vue` were replaced by inline `{ template: '<div/>' }`
   placeholders even though both real components exist — six tests asserted against a stub.
3. `@/services/reviewsApi` was mocked with function names the store never calls
   (`listQueue`/`getTransaction`/`submitDecision` against the real
   `fetchQueue`/`fetchTransactionForReview`/`recordDecision`), leaving the real functions in place to
   issue live requests. The transport is now stubbed at the axios boundary.

**Corrected count: 15 failures of 19** — every one an `AssertionError` or a `setValue` mismatch
against the real control, with no harness crash left.

## A 30-second regression, and its cause

Wiring the real router made the file take **33s**. Two causes, neither of them the router itself:
mounting the routes' real lazy components made every `router.push` re-import every view, and asking a
never-navigated router for `isReady()` stalled ~5s per test. Replacing the route components with
inert placeholders and always performing a navigation brought it to **3.1s**.
