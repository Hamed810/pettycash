## Requirements the slice implements

- **FR-064 / FR-065** — the seven report subjects and the filter set; the query carries only the
  filters the user filled in, so an unfilled field can never narrow a result set.
- **FR-066** — export of the permitted subject in CSV, XLSX, or PDF, with the grouped evidence
  report offering the ZIP archive `contracts/exports.md` assigns it. An unsupported format is
  refused, never silently swapped for a supported one.
- **FR-068** — the predefined calendar periods (month, quarter, year) plus the custom range, which
  the filter bar only shows for the `custom` preset.
- **FR-075** — a failed read or export is reported and retried only when the user asks; the store
  re-issues nothing by itself, and a failed read clears the previous rows so stale data is never
  presented as current.
- **FR-071** — the report renders right-to-left and carries a per-row card layout for the 390px
  viewport instead of a horizontally scrolling table.
- **Contract paging** — `page` and `pageSize` are clamped to the contract window (`page >= 1`,
  `1 <= pageSize <= 100`, default 25) on the client so an out-of-range page is never requested.

## Known limitations

- **Not routed.** `src/router/index.ts` is a shared coordination file owned by T117 and was off
  limits for this slice, so `ReportView.vue` is not registered at a path. Wiring `/reports` into the
  hash router is the remaining step of T117.
- **No server behind it.** `ReportingController` and `ReportController` do not exist (T112), so
  `GET /reports/{reportType}` and `POST /exports` answer 500 in the running instance. The client is
  tested against the contract shapes, not against a live response.
- **Dashboard deliberately excluded.** FR-061's role-aware dashboard (`src/services/dashboardApi.ts`,
  `src/stores/dashboard.ts`, `src/views/DashboardView.vue`) is the other half of T113 and was left
  out because `src/views/DashboardView.vue` is a plausible target of the active T286 work. It stays
  open.
- **No Persian catalog entries.** Every string goes through `t('pettycash', …)` under one
  `pettycash.` root, but `l10n/` does not exist yet and T119 owns the catalog, so the keys render
  as their own identifiers until then.
- **Column identifiers pass through untranslated.** A report column the catalog does not name keeps
  the server's canonical identifier instead of showing a raw translation key. Values are rendered
  exactly as the projection supplies them; the client never rescales, rounds, or substitutes a
  currency, so the T266/T267 presentation-layer currency defects cannot be reintroduced here.

## Contract ambiguity to confirm

`contracts/ocs-api.yaml` declares a single `filters` query parameter of `type: string` on
`GET /reports/{reportType}`, described as "Report-specific filter object encoded as query parameters
by the client". Those two statements disagree. This client follows the description and sends each
populated filter as its own parameter under the `ReportFilters` field name, which also matches the
existing `listSheets()` precedent. If T112 instead expects one JSON-encoded `filters` parameter,
`reportQuery()` in `src/services/reportsApi.ts` is the single place to change.
