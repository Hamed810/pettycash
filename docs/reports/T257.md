# T257 — Build the review scope from the actor's role assignments

**Status**: Complete

## Task

Build the acting user's responsibility scope from their actual role assignments instead of from
the record being decided. `ManagementReviewService` passed the transaction's own cost center as the
scope, and `AuthorizationService::canReview()` asks whether that cost center is in the scope list —
a value compared against a list derived from that same value, which is always true.

## Why it mattered

A manager assigned to `CC-100` could decide a transaction belonging to `CC-200`. FR-004, FR-005,
and FR-009 require authorization to be enforced server-side across decisions, and Constitution IV
requires the server to be the authority on workflow transitions and role/scope authorization
regardless of client behaviour. Hiding the action in the interface must never be the only
restriction.

T255 had already made scope *empty* (so every decision returned 403). Left alone, this defect
would have turned that into scope that is *permanently true*, which reads as a working system
while denying nothing.

## Implementation

The subject and the scope are now both resolved to **cost-center codes**, which is what
`canReview()`'s strict `in_array` needs:

- `getManagedCostCenterCodes()` reads the actor's active `RoleAssignment` rows for the role the
  stage requires and resolves each numeric `costCenterId` to its code.
- `resolveCostCenterCode()` prefers the revision's submission-time `costCenterCode` snapshot and
  falls back to the numeric join key via `CostCenterRepository::findById()`.

Resolving both sides mattered. The previous code passed `revision()->costCenterId()` — the cost
center's **public UUID** — into `findByCode()`, a lookup that expects a code such as `CC-100` and
therefore always returned `null`. The scope comparison was not merely vacuous; it compared unlike
units, and a real code could never have matched under strict comparison either.

Finance keeps its shared queue and correction stays owner-only, so both stages carry an empty
scope deliberately. `AuthorizationService` is unchanged, so the code-based matrix in
`AuthorizationServiceTest` and `ManagementReviewAuthorizationTest` still holds.

## A latent fixture defect this exposed

Making scope enforceable required a cost center the actor does *not* manage. Adding one surfaced a
pre-existing bug: the seeder wrote `status => 'AWAITING_COST_CENTER_REVIEW'` on `pettycash_sheets`.
That is a **transaction** status; `SheetStatus` has no such case. Any read of a submitted sheet
raised:

```
"AWAITING_COST_CENTER_REVIEW" is not a valid backing value for enum SheetStatus
```

The row could never be hydrated. It had gone unnoticed because no test listed sheets while the
fixture was in the `submitted` state. The sheet status is the earliest outstanding stage, so the
baseline is now `COST_CENTER` for cost-center review and `CORRECTION` for the correction state.

## Why the allowed case is asserted too

`testDecisionInsideTheManagedCostCenterIsStillAllowed` asserts `201` in the same `scope` state. A
blanket refusal would also satisfy the denial test, so without this the fix could have been
"reject every decision" and still go green.

## Known limitations

- `getUserRole()` still ignores the cost-center code it is passed and returns the actor's highest
  role overall, so the `actor_role` audit snapshot is not the role actually held *for that cost
  center*. Constitution IV requires role-at-event fidelity. This is outside T257 and was left
  untouched rather than folded in silently.
- The four `ManagementReviewControllerTest` decision-contract failures (T269, T270, T271) are
  unchanged.
