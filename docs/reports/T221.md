# T221 — Make the live-HTTP OCS contract suites valid

**Status**: Complete (test validity). Product defects it exposed remain open.

**Task**: T221 (Phase 14, HIGH) — unblocked by T249

## Problem

`PurchaserFlowControllerTest` and `ManagementReviewControllerTest` talked to a real Nextcloud but
asserted against fixtures that did not exist, so their failures carried no information:

- `ManagementReviewControllerTest` addressed `transactions/00000000-0000-0000-0000-000000000000`
  — a well-formed UUID matching no record — so every decision assertion only ever exercised the
  404 branch.
- Both suites shared one seeded sheet and transaction and mutated it in place, so each assertion
  ran against whatever the previously executed test left behind. PHPUnit's method order was the
  only thing making them deterministic.
- `expectedVersion` was hardcoded to `1` while the fixture rows' `lock_version` had drifted, so
  every mutable-resource command failed with `Stale version`.
- `DELETE /transactions/{id}` and `POST /correction` omitted `expectedVersion`, which
  `contracts/workflow.md` requires for mutable-resource commands.
- The evidence deactivation and content assertions addressed `ContractFixtures::unknownId()`,
  which exists precisely to match nothing.
- Command IDs were fixed literals, so a second run replayed the first run's stored command result
  instead of exercising the endpoint.

## The seeder

A single transaction cannot be both an editable draft and one awaiting cost-center review, so the
seeder takes the state explicitly and **resets** rather than only first-seeding:

| State | Sheet | Transaction | Used by |
|---|---|---|---|
| `draft` | `OPEN` | `DRAFT` | sheet, transaction, evidence lifecycle |
| `submitted` | `AWAITING_COST_CENTER_REVIEW` | `AWAITING_COST_CENTER_REVIEW` | management decisions |
| `correction` | `AWAITING_COST_CENTER_REVIEW` | `AWAITING_PURCHASER_CORRECTION` + evidence | correction, resubmit |

Each run overwrites the fixture rows to the requested baseline and deletes the
`pc_workflow_decisions`, `pc_evidence`, and `pc_transaction_audit` rows the suites created, then
reports the live `lock_version` values the suites must echo as `expectedVersion`. It also assigns
the acting user `COST_CENTER_MANAGER` and `SENIOR_MANAGER` on the fixture cost center, because
FR-002 permits self-review only when role, scope, and stage all hold independently.

The `submitted` and `correction` states depend on T249: `AWAITING_COST_CENTER_REVIEW` (27) and
`AWAITING_PURCHASER_CORRECTION` (29) could not be written into the old `VARCHAR(24)` column.

## Defects found and their disposition

Two product defects surfaced. Both were confirmed against the running container.

### 1. Double-nested OCS envelope on evidence — fixed here

`EvidenceController::upload()` and `destroy()` returned
`new DataResponse(['data' => $this->formatEvidence($evidence)], ...)`,

producing `ocs.data.data.id`, while `contracts/ocs-api.yaml` defines the `201` and `200` responses
as the `Evidence` schema itself and every other endpoint in the codebase returns the payload
unwrapped. Fixed in both actions.

### 2. Decision authorization scope is always empty — open, not fixed

`ManagementReviewService` builds its authorization scope from
`$transaction->revision()->costCenterId()`. That reads `TransactionRevision::$costCenterId`, a
**private** property assigned only by `complete()` — the draft-to-submit transition. Persistence
never calls it, so for every revision loaded from the database `costCenterId()` returns `null`,
`$context->costCenterCodes` is `[]`, and `AuthorizationService::canReview()` denies because
`in_array('', [], true)` is false.

Consequence: **no cost-center or senior decision can ever be authorized**, at any cost center, for
any user. FR-004, FR-005, FR-008, FR-033, and FR-035 are unreachable at the server boundary
regardless of the interface. This belongs to the still-open management-review work (T050/T178),
not to this task, and is recorded for the next convergence.

A second, related observation: `ManagementReviewService` passes the transaction's own cost-center
code into `AuthorizationContext::$costCenterCodes` (line 118) and then compares it against itself in
`canReview()`, so the scope check is a no-op even once the value is correct. Fixing only the null
would make the check vacuous rather than enforcing FR-004.

The 500s are logged as `dirty table reads: SELECT filecache...`, the same cross-connection AppData
defect T247 fixed for the upload path; the deactivation and content paths still read AppData inside
an open transaction.

A defect found while writing the seeder is worth recording because it recurred: building a query
with several `getQueryBuilder()` instances leaves named parameters unbound and emits SQL such as
`... near ':dcValue1 LIMIT 1'`. It fails silently with exit code 0 under the Nextcloud CLI
bootstrap because the exception handler discards output. This is the same class of mistake as T188;
`upsert()`, `deleteWhere()`, and `scalar()` now each use a single builder, with a comment saying why.

## Known limitations

- Each `ContractFixtures::prepare()` launches a subprocess that bootstraps Nextcloud, so the contract
  suite is noticeably slower. Acceptable for a live-HTTP contract suite.
- Resetting deletes fixture-scoped evidence metadata; the corresponding AppData binaries become
  orphans. The read-only reconciliation diagnostic that is meant to surface these is still open
  under T130.
- The container runs `opcache` with `revalidate_freq => 60`, so a PHP edit can take up to a minute
  to reach live HTTP.
