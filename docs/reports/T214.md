# T214 — Apply `IdempotencyService` to all state-changing command handlers

**Status:** Complete — by reconciliation, not by new code. T214 was a duplicate of T149, which had already
delivered all four named handlers.

**Report date:** 2026-09-29

---

## Summary

T214 asks for `IdempotencyService` on four handlers: management decisions, finance settlement, correction
resubmit, and account charges. The task was marked `(partial)`.

All four were already implemented by **T149**, which is marked `[x]` and names the same four services. So
the question was not "what is missing" but "is the `(partial)` marker true, and if not, on what evidence".

I verified each handler rather than trusting either checkbox, and the marker was stale.

## Verification

Every handler wraps its **entire** closure, not a part of it:

| Handler | `execute()` call | Hashed payload | Replay path |
|---|---|---|---|
| `SubmitSheet` | `SubmitSheet.php:56` | yes | re-reads the sheet by public id after the block (`:192`) |
| `ManagementReviewService` | yes | yes | reads the decision back by command id |
| `FinanceSettlementService` | `:115` | yes | reads the decision back by command id (`:347`) |
| `ResubmitCorrection` | `:62` | yes | returns the stored result |

Two things were worth checking closely because they would not have shown up in a count of `execute()`
calls:

**`FinanceSettlementService`: the `ACCOUNT_CHARGED` write is inside the idempotent block.** The
configuration event is written at `:287`; the closure runs `:115 → :334`. So a replayed settlement
returns the stored result without charging the account twice. Had it sat outside, replay would have
produced a second charge *and* a second audit event in an append-only table. T294 is what created that
write, and it landed in the right place.

**`SubmitSheet`: discarding `execute()`'s return value is correct here.** It ignores the return and then
re-reads the sheet by public id. That looks like a bug — the closure never runs on replay, so nothing
would be returned — but the re-read supplies the aggregate, and the method's declared `: ExpenseSheet`
return type is satisfied. `ResubmitCorrection` takes the opposite approach and returns the stored array.
Both are sound; they differ because they return different things.

`IdempotencyServiceTest` passes.

## What this changed

`tasks.md`: T214 marked `[x]` with the verification above, replacing the stale `(partial)`.

## The real gap, recorded as T317 rather than absorbed here

Verifying T214 surfaced a genuine defect **outside its named scope**, which I did not fold into a task I
was marking complete.

`TransactionController` reads the `X-PettyCash-Command-ID` header at `:56` and `:126`, echoes it through
both error paths, and then calls:

```php
$transaction = $this->transactionService->createTransaction($sheetId, $expenseDate, $amountMinor);
```

**without passing it.** Neither `createTransaction()` nor `updateTransaction()` takes a `$commandId`, and
`TransactionService` holds no `IdempotencyService` at all. So the header is honoured on submission,
decision, settlement and resubmit, and ignored on the two endpoints that create and edit the revision
FR-042 names explicitly.

This matters more after T213. Those two handlers now write `REVISION_CREATED` and `TRANSACTION_CHANGED`
audit events, and T213 had to make `command_id` nullable on both audit tables specifically because these
paths have no command id. FR-042's atomicity *is* satisfied — both already run inside
`transactionManager->transactional()` — but a retried request or a double-clicked button creates a
**second revision** and a second permanent audit event. `expectedVersion` guards only a *concurrent*
edit; it does nothing for a sequential retry of a request that already succeeded.

Absorbing this into T214 would have widened a completed task's scope without announcing it, so it is
recorded as **T317** in Phase 48 with the open decisions: whether a missing header is refused or tolerated
(that changes contract behaviour and belongs with whoever owns `contracts/ocs-api.yaml`), and whether the
replay path re-reads the aggregate or widens what `IdempotencyService` stores.
