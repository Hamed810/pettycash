## The design decision that carries the task

`contracts/exports.md` requires that "every report query is role-scoped **before** filtering,
aggregation, or file generation". A report that filtered first and scoped second returns the right
*count* over the wrong rows — which is the failure that reads as correct in a smoke test and leaks data
in production.

So the order is **structural, not conventional**: `ReportQuery::paginate()` takes a `ReportScope` and a
`ReportFilter` and applies the scope first, with no second entry point. `configurationAuditScope()` is
named to make the order visible at the call site. This is the same reasoning that made the route guard
and the account-payload guard structural: a rule that depends on every call site remembering it is a rule
one call site will eventually not remember.

**The scope-before-filter ordering is mutation-checked.** Swapping the two steps fails the test that
seeds an out-of-scope row which would pass every filter, so the removal can only be the scope's doing.

## The page size is clamped, not refused

`ReportFilter::MAX_PAGE_SIZE = 100` per the contract. A request for 5,000 is **clamped down**: a client
sending "give me everything" is exactly what server-side paging is for, and a 422 would push the
bounding into every client. The offset is then computed from the *clamped* size, so the clamp cannot
silently return a different window than the one it reported.

A zero or negative **page number** is refused, because there is no sensible bound to fall back to and
swapping it would return the wrong records without saying so.

## An empty scope never widens

The direction that fails dangerously: a scope bug that returns everything is a data leak, and one that
returns nothing is a bug report. So each rule is asserted in both directions — a manager with a cost
centre sees it, a manager without sees **none**, a finance officer with charged accounts sees those, and
one without sees **none**.

`ReportScope::narrowCostCenters()` returns `[]` for an actor with no cost-centre scope rather than the
requested set, and `configurationAuditScope()` reports `visible: false` for a finance officer given no
charged accounts, with the reason saying *"an empty scope must not widen to all"*.

## Two bugs the tests caught, both mine

**The multi-role union was lost.** `configurationAuditScope()` returned on the first matching branch, so
an actor who was both a manager and a finance officer silently lost the cost-centre half of their
visibility. FR-002/FR-008 require the **union** for reads as much as for decisions. It now accumulates
across both rules, with a `cost_center_or_account` subject type when both apply.

**The administrator was shown purchaser sections.** `DashboardQuery::sections()` gated the purchaser
blocks on `coversOwned($scope->actorUid)`, which is trivially true for anyone — they always own their own
record. So an administrator with no purchaser role was handed `mySheets`/`returnedToMe`/`balances`. It
now gates on the **role**.

A third failure was my **test** being wrong, not the code: I asserted the default page size while
explicitly passing 5,000, mixing two intents. Split into two tests — one for the clamp, one for the
default.

## One gap, recorded rather than hidden

The FR-055 rule for finance officers is *implemented and tested*, but resolving **which** accounts an
officer has charged is **not derivable from the current schema or ports**:

- `AccountMovement` records **no actor**, so the ledger cannot answer it.
- `AccountMovementRepository` has no by-actor read.
- `CommandResultRepository` exposes only `find($commandId)` and `save()`, so the `pettycash_command_results`
  row that *does* carry `actor_uid` and `operation` is reachable one row at a time and cannot be
  enumerated by actor.

`configurationAuditScope()` therefore accepts the charged account ids the caller already knows, and an
officer given none sees nothing. Inventing a `findByActorAndOperation()` port method to serve one report
would change a port `IdempotencyService` also depends on; that decision belongs to T112's orchestration
layer. This is a genuine dependency for the report *endpoint*, and it is now written down rather than
discovered later.

## Also delivered, with a caveat

FR-056's stream-separation predicates (`isConfigurationEvent()` / `isTransactionEvent()`) are in place,
and transaction-audit visibility defers to the transaction's own scope per FR-055. **But T294 still means
no configuration event exists to separate** — the predicates are what T139 needs once it does.

## Deliberately not done

- **Not registered in the container.** Nothing consumes these services until T112's controllers exist.
  Registering unreferenced services is the speculative pattern already used twice in this feature's
  history (the two dead audit-writer methods this feature removed) and is avoided deliberately.
- **No `findByIds()` added to `CostCenterRepository`.** I reached for one, found it did not exist, and
  removed the call rather than adding a port method for a report's convenience. An assignment pointing
  at a missing cost centre is a data-integrity question for the owning code.
