# T213 — Audit event insertion for all workflow transitions

**Status:** Complete.

**Report date:** 2026-09-29

**ADR:** `docs/decisions/0001-transaction-audit-event-type-vocabulary.md`

---

## Summary

The task asked for audit events on every workflow transition. Investigation found something more urgent
than the missing events: **two paths were writing audit rows that looked correct and contained nothing.**
Both had the same root cause — a caller and `AuditWriterService` disagreeing about a key name, with
nothing in between to notice. Neither would ever have raised an error; both produced well-formed rows in
an append-only table, permanently.

With those fixed, the task itself was finished: the event-type vocabulary was reconciled (it had two
disagreeing sources of truth), and the four transitions FR-051 names that had no writer at all now have
one.

---

## Defect 1 — `EvidenceService::deactivateEvidence()` wrote an empty event

The call site constructed an `AuditEvent` **positionally** and cast it to an array:

```php
$auditEvent = new AuditEvent(/* 17 positional arguments */);
$this->auditWriter->append((array) $auditEvent);
```

Casting an object yields its **camelCase** property names — `eventType`, `entityType`, `beforeJson`.
`AuditWriterService::toEvent()` reads **snake_case** keys. Not one matched, and every constructor
argument had a default, so the event was stored as:

| Field | Stored | Should be |
|---|---|---|
| `event_type` | `'UNKNOWN'` | `'EVIDENCE_DEACTIVATED'` |
| `stage` | `'DRAFT'` | `'EVIDENCE'` |
| `entity_type` | `''` | `'evidence'` |
| `entity_id` | `null` | the evidence id |
| `transaction_id` / `revision_id` | `null` / `null` | both known |
| `before_json` / `after_json` | `"[]"` / `"[]"` | the full snapshots |

FR-052 requires every event to retain the applicable before-and-after values. Here they were discarded,
and FR-053 makes the row unrepairable.

`SubmitSheet` already carried a comment describing the *identical* bug — hit there, patched locally, left
unfixed next door. That is the argument for fixing the writer rather than the call sites.

## Defect 2 — both `DECISION` trails stored `"[]"` for before and after

`ManagementReviewService` and `FinanceSettlementService` passed `before_json` / `after_json`. The writer
reads `before` / `after` and does the encoding itself, so those payloads had **no snapshot key at all**
and the `?? []` default stored the literal `"[]"` in both columns.

The `after` payload was discarded wholesale: the decision, stage, explanation, revision number, and — for
finance — the `financial_effect` recording whether money moved. **This is the approvals / rejections /
returns trail.** Every decision was written with no record of what was decided.

The other three callers already used the correct keys, so the writer's vocabulary was never wrong — it
was undocumented, and nothing detected a caller disagreeing with it.

## The vocabulary: two sources of truth, neither authoritative

`AuditEventType` was used by nothing except `EnumColumnWidthTest`, while the code wrote five raw strings
of which **one** appeared in the enum. Deriving the list from FR-051 — as decided — rather than trusting
either side is recorded in the ADR. In summary:

- `Decided` split into `Approved` / `Rejected` / `Returned`. FR-051 names them separately and `Decision`
  is exactly `{APPROVE, REJECT, RETURN}`, so one type for all three meant the outcome was unqueryable.
- `Settled` removed: FR-051 does not name settlement, and `ACCOUNT_CHARGED` already records the charge
  under FR-055.
- `RevisionCreated` and `TransactionChanged` added: FR-051 names both and the enum had no case for either,
  which is part of why nothing wrote them.

Both audit tables were measured at **zero rows**, so this was code-only — no migration, no repair.

## Changes

### Defect fixes

- **`lib/Application/Audit/AuditWriterService.php`** — two refusals replacing silent defaults. Neither
  triggers on any payload the production code sends (verified against every call site).
  - `requiredEventType()` refuses an event with no `event_type` instead of storing `UNKNOWN`. Scoped to
    `event_type` alone: `appendConfiguration()` already refuses an event with no `entity_type` (FR-055
    addresses configuration events by subject), but the transaction stream does not need the same rule and
    `AuditWriterSurfaceTest` writes a subject-less event deliberately to prove the streams do not cross.
  - `rejectPreEncodedSnapshots()` refuses `before_json` / `after_json`. Deliberately narrow — a blanket
    "reject any key the writer does not read" rule would also reject `actor_uid`, `actor_name` and
    `occurred_at`, which callers legitimately pass and the writer resolves from the session.
- **`lib/Application/Evidence/EvidenceService.php`** — the payload is now the named-key shape, carrying
  real `before` / `after` arrays. Unused `AuditEvent` import removed. `actor_uid` / `actor_name` omitted
  deliberately so the writer resolves them from the session.
- **`lib/Application/Workflow/ManagementReviewService.php`**, **`FinanceSettlementService.php`** —
  `before_json` / `after_json` → `before` / `after` as plain arrays.

### Vocabulary

- **`lib/Domain/Shared/Enum/AuditEventType.php`** — rewritten to the ten FR-051 transitions.
- **`lib/Application/Audit/DecisionEventType.php`** (new) — maps `Decision` to the event type, shared by
  both decision services so the two cannot drift. Lives in the Application layer because `Decision` is a
  workflow concept and the enum is shared vocabulary; making the shared enum depend on a specific workflow
  type would invert that.
- Five producers now pass enum cases. `FinanceSettlementService` uses `ChargedAccountScope::CHARGE_EVENT_TYPE`
  for the FR-055 configuration write, so the value T294 derives accounts from has one definition.

### The four missing writers

| Writer | Location | Notes |
|---|---|---|
| `ROUTED` | `SubmitSheet` | One per transaction. Records the manager assigned at submission time, read via `findActiveByRoleAndCostCenter()` with today's date, so a later assignment change cannot retroactively alter what a submission was routed to. Null when no manager is assigned — recorded honestly rather than invented. |
| `REVISION_CREATED` | `TransactionService::createTransaction()` | Inside the transaction, so the event and the rows it describes commit together. |
| `TRANSACTION_CHANGED` | `TransactionService::updateTransaction()` | The before-snapshot is read from `$current` *before* `complete()` runs, so it is the real prior state and not a re-read of the mutated object. |
| `EVIDENCE_ADDED` | `EvidenceService::uploadEvidence()` | Records name, media type, byte count and checksum — not the content. |

### Supporting changes

- **`lib/Domain/Expense/ExpenseSheet.php`** — `addTransaction()` is now idempotent. It guarded currency
  and status but not membership, so correctness depended on `DbExpenseSheetRepository` never composing
  transactions. Surfaced here as two `ROUTED` events and a doubled transaction count for a one-transaction
  sheet. A silent double count in a sheet total is hard to trace back to an aggregate method, so the
  invariant is now stated in the aggregate.
- **`lib/Migration/Version010400Date20260929000000.php`** (new) — makes `command_id` nullable on both
  audit tables. See below.
- **`appinfo/info.xml`** — 1.3.0 → 1.3.1, so the migration is picked up (`occ upgrade` reported "No
  upgrade required" without it).
- **Three test doubles corrected** where they diverged from the implementations they stand in for. Each was
  a real trap, and each is documented at the fix:
  - `InMemoryEvidenceRepository` / `InMemoryExpenseTransactionRepository` did not assign `publicId` from the
    aggregate's `id`, though both real repositories do — so `findByPublicId()` could never find anything a
    test had just saved.
  - `InMemoryRoleAssignmentRepository` returned `array_filter()` output, which **preserves keys**, so a
    lookup returned `[1 => $assignment]`. The port declares `@return list`. `$result[0] ?? null` then
    silently evaluated to null and the audit event recorded "no manager assigned" for a cost centre that
    had one. Nothing failed; the answer was simply wrong.
- **`tests/E2E/purchaser-submit.spec.ts`** — `SUBMISSION` → `SUBMITTED`. The event type is rendered in
  the sheet detail view, so this is a user-visible string.

### Why a migration was needed

`command_id` was created as `Types::STRING` with no `'notnull' => false`, and Doctrine's default is NOT
NULL — while `explanation`, `before_json` and `after_json` beside it were each declared explicitly
nullable. Every writer that existed passed a real command id, so the constraint was never violated and the
column looked like a deliberate requirement. The four new writers are on paths that are **not**
command-wrapped and have no honest command id. FR-052 does not list `command_id` among the fields an event
must retain, so nullable is the accurate representation: non-null where a command exists, null where the
transition is not a command. Wrapping them is T317 — not T214, whose four named handlers T149 had already
delivered. **T317 is now done for both `TransactionService` methods**, so `REVISION_CREATED` and
`TRANSACTION_CHANGED` carry a real command id; only `EVIDENCE_ADDED` still records null, and the nullable
column is correct for it.

## Known limitations

- **A pre-existing crash, found here and not fixed.** `TransactionRevision::description()` and
  `expenseTypeTitle()` are nullable, but `complete()` declares both as `string`, and
  `updateTransaction()` passes `$description ?? $current->description()` straight through. So **editing a
  draft that has no description or no expense type throws a `TypeError`** — a purchaser cannot complete a
  new transaction by adding only a cost centre. It is T212's behaviour and whether `complete()` should
  accept null is a domain decision, so it was reported rather than changed. The new tests supply both
  fields and say why.
- **`TransactionController::formatAuditEvent()` still reports `decision` as the literal string
  `'DECISION'`** whenever an event carries a decision id, so the API cannot yet distinguish the three
  outcomes even though the stored event type now does. The outcome *is* in the `after` snapshot, so the
  fix is to read it from there. It was reverted rather than shipped untested: the formatter is private,
  `TransactionController` extends `OCSController` which is not autoloaded in the unit or integration
  bootstrap, and the contract fixture that would need a seeded decision audit event deletes and re-seeds
  audit rows from several independent paths. Recorded in the ADR as a follow-up.
- **`actor_role` fidelity is unchanged but still wrong.** `EvidenceService::getUserRole()` is a stub that
  hardcodes `'PURCHASER'`, which is why omitting `actor_role` changed nothing. FR-052 requires the role *at
  the time of the event*; the two decision services derive it properly from the cost centre. The stub is a
  pre-existing gap, not folded in here.
- **`sheet_id` is null on evidence events.** `EvidenceService` holds no transaction repository, so it
  cannot resolve the sheet. A *wrong* sheet id would attribute an event to a record the evidence does not
  belong to, which is worse than admitting the link is unknown. The transaction and revision ids are
  present, so the rows stay reachable.
- **`occurred_at` is ignored by the writer.** Callers pass it; the writer stamps `now`. Harmless in
  practice, since events are written immediately, but a caller's intended event time is not the recorded
  one.
- **Routing to a cost centre with no assigned manager records null.** Submission does not require an
  assignee. Whether it *should* is a workflow question this task did not decide.
- **Already-written rows are not repaired — and there are none to repair.** Both audit tables measured zero
  rows, so the `"[]"` snapshots were never persisted here and the fix is entirely preventive. On an
  instance that had run the affected paths, FR-053 would forbid editing the rows and the only remedy would
  be a documented migration appending correcting events.
- **`EnumColumnWidthTest` needed no change** — it derives from the enum, which is the point of the change.
  A separate test asserts all ten values fit the `VARCHAR(48)` the migrations leave behind.
