# T330 — The expense type is identified, not merely named

**Status:** complete
**Date:** 2026-10-03
**Phase:** 55 — Convergence (seventeen wire-level gaps between the contract, the server, and the client)

## The defect

`Revision.expenseType.id` carried the expense type's **title**:

```php
'expenseType' => [
    'id'   => $revision->expenseTypeTitle() ?? '',
    'name' => $revision->expenseTypeTitle() ?? '',
],
```

`EntitySnapshot.id` is `format: uuid` (`specs/001-pettycash-v1-core/contracts/ocs-api.yaml:1184-1189`).
The neighbouring `costCenterSnapshot()` already emitted a real uuid plus an optional `code`, so this was
an inconsistency rather than a convention.

It was not cosmetic. `TransactionFormView.vue:175` copies `activeRevision.expenseType.id` into the
draft, and `TransactionService.php:307` resolves it with `findByPublicId()` — so an edit submitted from
a server-shaped payload sent `"Contract Fixture Expense Type"` where a uuid was required and was
refused. **Every update of an existing draft failed with a 422**, taking FR-025's "edit" and US4's
correction path with it.

## Why the formatter alone could not fix it

`TransactionRevision` had no public-id accessor to use. It stored `costCenterId` (public uuid),
`costCenterDbId`, `expenseTypeTitle` and `expenseTypeDbId` — but no expense-type public id. The only
string available for that field was the title, so the fix had to run four layers deep.

## Changes

### Domain — `lib/Domain/Expense/TransactionRevision.php`

- New `public ?string $expenseTypeId = null`, paired with `$expenseTypeDbId` exactly as `$costCenterId`
  is paired with `$costCenterDbId`.
- `complete()` takes it as a **trailing optional** parameter, so none of the ~25 existing `complete()`
  call sites across the integration suites changed and no unrelated test was disturbed.
- `hydrate()` is untouched: `expenseTypeDbId` was already assigned as a public property immediately
  before `hydrate()` is called, so `expenseTypeId` is set the same way rather than widening a method
  whose docblock is specifically about restoring business fields.
- `correction()` copies it — without that, a correction draft loses the id and US4 stays broken while
  the create path looks fixed.
- New `expenseTypeId(): ?string` accessor.

### Persistence — `lib/Infrastructure/Persistence/Expense/DbTransactionRevisionRepository.php`

New `getExpenseTypePublicId()`, placed directly beside the existing `getCostCenterPublicId()` and called
from `mapRow()` in the same place. **This is where the cost centre's public id was already being
resolved** — putting the expense type's anywhere else would have recreated the inconsistency this task
closed. Returns null rather than substituting, because a join key with no matching row is not an
identifier.

### Application — `lib/Application/Expense/TransactionService.php`

`$expenseTypePublicId` is carried through both branches of the expense-type if/else and passed to
`complete()`, mirroring how `$costCenterPublicId` is carried beside `$costCenterCode`.

### Presentation — `lib/Infrastructure/Http/TransactionPayloadFormatter.php`

New `expenseTypeSnapshot()` beside `costCenterSnapshot()`, emitting `id => expenseTypeId() ?? ''` and
`name => expenseTypeTitle()`.

The **stored title** is used for `name`, not a fresh lookup, so a historical revision keeps the name it
was submitted with — the same reason `costCenterSnapshot()` prefers its snapshot columns.

An unresolvable id yields an **empty string rather than the title**: an absent identifier is visibly
absent, whereas a title in an id field looks like data.

## A fixture was hiding this

`PurchaserFlow.spec.ts` used:

```ts
const COST_CENTER_ENGINEERING = 'cc-eng-0001'
const EXPENSE_TYPE_SUPPLIES   = 'et-sup-0001'
```

Readable placeholders in fields the contract types as `format: uuid`. That is the trap Phase 55 named
for T327: a fixture shaped to agree with the client rather than with the server — simultaneously wrong
about the contract and unable to say so. **All four are real UUIDs now.** A readable id is comfortable
in a fixture and impossible on the wire.

### RED state

Both contract tests failed on missing behaviour before the fix, with zero skipped and zero incomplete.
The round-trip test reproduced the live symptom exactly:

```
422 {"error":{"code":"VALIDATION_FAILED",
     "message":"Expense type not found: Contract Fixture Expense Type"}}
```

### The round-trip test asserts on the status code, and why that changed

Its first draft asserted the PATCH answer was not a refusal by inspecting the *shape* of `data` — and
**that assertion passed against the 422**, because a 422 answers a JSON OCS envelope too. A shape check
cannot distinguish success from the exact refusal the test exists to catch. It now asserts
`getStatusCode() === 200`. Worth remembering for the other OCS write tests.

### An honest limit on the component test

The component test **cannot detect this defect on its own**: the form copies whatever
`expenseType.id` says, so it passes identically against the broken server and the fixed one. Its value
is pinning the client half — the form must submit the *id* and must never substitute the *name* — and
it is the component half of the loop the contract test closes. **The load-bearing assertions are the two
over HTTP.**

The component test also seeds the transaction on the **transport** (`setTransactionDetail`) rather than
assigning the store after mount. The view reads the transaction during mount, so a store populated
afterwards leaves the draft empty, the form fails its own validation, and no request is issued — which
is how a test can look like it exercised the edit path while having exercised nothing.

## Known limitations

- A revision whose stored `expense_type_id` matches no expense-type row now emits `id: ''` where it
  previously emitted the title. That is the honest reading — an unresolvable join key is not an
  identifier — but such a revision's expense type cannot be edited until the dangling reference is
  repaired. No task owns dangling-reference repair; recorded rather than silently widened.
- The frontend needed no production change: `TransactionFormView` already submitted
  `activeRevision.expenseType.id` verbatim. It was submitting the wrong *value*, and the value was the
  server's to get right.
