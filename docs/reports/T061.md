## What was left

T061 names seven effects a finance approval must commit atomically. The T056 pass delivered six —
decision, unique movement, balance, transaction final state, command result, audit. The seventh,
**sheet final state**, was missing: `sheetRepository` was injected into
`FinanceSettlementService` and used nowhere except the lock. FR-043 requires a sheet to become
completed once every transaction has a final financial outcome, and `contracts/workflow.md` lists
"recalculated sheet state" among the things settlement creates.

## The obvious fix would have been a no-op

`ExpenseSheet` already has `recalculateStatus()`, and it already implements the rule — it maps the
earliest outstanding stage across the sheet's transactions, then sets `Completed` or
`CompletedWithRejections` when all of them are final. Calling it from the settlement looks like the
whole job.

It would have done nothing. **A sheet loaded from either repository carries no transactions.** Neither
`DbExpenseSheetRepository` nor the in-memory double hydrates the collection, so the aggregate's own
list is empty, and `recalculateStatus()` returns immediately on an empty collection. The method
looks like it does the work; it cannot, for any caller that did not build the sheet in memory. That
is the most likely reason the omission survived — the code to do it was present and plausible.

Reusing `addTransaction()` to populate the collection is not available either: it refuses a sheet
that is not open (*"Submitted sheets are read-only"*), and by the time anything is settled the sheet
is long submitted. So `ExpenseSheet::recalculateStatusFrom(array $transactions)` was added, letting
the caller state which transactions it means. `recalculateStatus()` now delegates to it with the
aggregate's own collection, so existing in-memory callers are unaffected.

The settlement loads the sheet's transactions, recalculates, and saves — **after** the transaction is
saved and inside the same transaction, so a sheet can never be completed against a settlement that
rolled back. A sheet that cannot be loaded is left alone rather than treated as complete: inventing
a status for a sheet the settlement cannot see is worse than leaving it stale.

## A mutation found a real gap in my own work

Removing the `recalculateSheet()` call fails 3 tests, as expected. Removing the **empty-set guard**
from `recalculateStatusFrom()` failed *nothing* — 28/28 still green.

That is worth recording rather than smoothing over. Walk an empty set and `$allCompleted` is never
cleared, so the sheet is declared `COMPLETED`: a caller that loaded nothing would complete a sheet it
knows nothing about. The settlement cannot reach that branch, because the transaction it is settling
necessarily carries the sheet id it looks up, so a loaded sheet always has at least that one
transaction. The guard is a safety property of a public method, and it is now pinned by a direct
test on the aggregate — asserted there rather than through the settlement precisely because the
settlement suite cannot see it. Re-running the mutation then fails with *"Failed asserting that two
variables reference the same object"*, the status having become `COMPLETED` from nothing.

## Two of my own fixtures were wrong before the tests were

- **Each transaction first got its own sheet.** That made FR-043 unobservable: a sheet with one
  transaction always completes, so "completes", "completes-with-rejections" and "does not complete
  yet" all read the same. The requirement is about *a sheet's* transactions, and the fixture denied
  it any.
- **The fixture attached transactions with `addTransaction()`**, which correctly refuses a sheet once
  a settlement has recalculated it — so the second transaction in a test threw *"Submitted sheets are
  read-only"*. The domain was right and the fixture was wrong.

With one shared sheet the requirement becomes observable, and the ordering matters: the
completes-with-rejections case settles an approval first (sheet reaches `COMPLETED`), *then* adds a
rejected transaction. Had both existed when the first was settled, the sheet would correctly have
stayed at `FINANCE` and there would have been nothing to observe.

## Known limitations

- **T060 stays open.** Account locking and movement insertion are done and verified; the
  **reconciliation repository** is not, and it has nothing to implement against —
  `AccountRepository` declares no reconciliation method and neither adapter has one. That is a
  design decision about what reconciliation means in V1, not a missing class.
- The real-MariaDB coverage of the unique consumption index and the rollback of a partially failed
  settlement is T236 and is untouched.
- `contracts/workflow.md` also requires that a file/export I/O failure never be inside the
  settlement transaction. Nothing in the settlement path performs I/O today, so there is nothing to
  verify; it becomes checkable when T107–T111 land the exporters.
