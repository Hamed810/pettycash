# T056 — Finance settlement tests, and the dead stage they uncovered

**Task**: T056 complete · T060 and T061 partly advanced, both still open
**Feature**: PettyCash V1 Core Workflow (`specs/001-pettycash-v1-core`)
**Date**: 2026-09-26
**Preceded by**: `docs/reports/T288.md`, whose opcode-cache rule this pass used throughout. The
container was not running at the start of the session and was recovered with `docker start` on the
existing containers; every PHP number below was taken through `scripts/dev/phpunit`, which settles
first.

## The finding that mattered

`TransactionStatus::SeniorApproved` was declared in the enum and read by
`FinanceDecisionPolicy::canFinanceApprove()` — and **nothing in the codebase ever assigned it**.
`ExpenseTransaction::applyDecision()` set `AwaitingFinanceReview` on a senior approval instead.

So every senior-approved transaction arrived at the finance stage in a state nobody was permitted
to approve, and the refusal named the wrong cause: *"Finance cannot approve a senior-rejected
transaction"* for a transaction the senior had approved. **FR-038, FR-040 and FR-043 were
unreachable.** This is why the missing consumption movement read as an unimplemented feature: it
was the second defect sitting behind a dead stage, and fixing only it would have changed nothing
observable.

`contracts/workflow.md` settles the intent without ambiguity — it gives finance two rows keyed on
the senior's *outcome*:

| Stage | Allowed decisions |
|---|---|
| Finance after senior approval | Approve, reject, return |
| Finance after senior rejection | Reject, return; approval forbidden |

and the cost-centre branch already recorded outcome-named statuses (`CostCenterApproved` /
`CostCenterRejected`), so the senior branch now records `SeniorApproved` too. Reverting that one line
fails **17 of 24** tests, which is the measure of how dead the stage was.

`findForFinanceQueue()` selected on `AWAITING_FINANCE_REVIEW` — a state no code path produces —
which also hid every senior-**rejected** transaction, so FR-039's "finance may reject it or return
it" had nothing to act on. It now selects both senior outcomes.

## FR-039 was broken in two halves, and the second was user-visible

- `recordDecision()` called `assertCanApprove()` **unconditionally** — asking only "may finance
  approve this?" and applying the answer to whichever decision was requested. A senior-rejected
  transaction therefore could not be rejected or returned either, and a purchaser whose expense was
  refused at senior stage could not be sent back to correct it.
- `TransactionPayloadFormatter::allowedActions()` set `canApprove`, `canReject` and `canReturn` all
  to `true` whenever the actor could decide at all, never consulting the policy. The interface
  offered finance an **Approve button the command path then refused** — the precise disagreement
  that method's own docblock claims cannot happen, and which nothing covered, because the only
  `allowedActions` in the suite were frontend stubs.

Both now consult one decision-aware policy, and a test asserts the offered set equals the permitted
set for both senior outcomes and all three decisions.

## FR-040's consumption movement

`PettyCashAccount::consume()` already **returned** the `AccountMovement` it built; the return value
was discarded, so the ledger row was constructed and thrown away while only the balance was
persisted. It is now saved inside the caller's transaction. The source it recorded was also wrong —
the **decision** id was passed as the source *revision* — and both are now carried, per
`data-model.md`.

In the MariaDB adapter, `save()` cast `sourceRevisionId` to `(int)` while the aggregate carries the
revision's **public UUID** (`contracts/ocs-api.yaml` declares `sourceRevisionId` as `format: uuid`).
The cast yielded `0` — a valid key pointing at a *different* revision, colliding on
`pettycash_account_movements_consumption_uniq` with every other consumption. That is silent
corruption, not a failure. `source_decision_id` was hard-coded `null`, which the data model marks
required for consumption. Both are now resolved, and an unresolvable reference aborts rather than
defaulting.

## The lock the contract requires was unreachable

`NextcloudTransactionManager::lockInSettlementOrder()` existed and was **absent from the
`TransactionManager` port**, so no application-layer code could call it and nothing did. It is now
on the port, and settlement takes sheet → transaction → revision → account in that fixed order,
re-reading the account after the lock — the account is the row most likely to be contended, and it
has to be read before its key is known.

## The test double could not have supported any of this

`InMemoryAccountMovementRepository` keyed movements on `(int) $movement->id`, but that id is a public
UUID string, so **every movement collapsed onto key `0`** and the second silently replaced the first.
`findBySourceRevisionId()` compared a `?string` against its own `int` parameter with `===`, so it
could never match — and it is the lookup FR-040's uniqueness rests on. `findByAccountId()` filtered
on `$m->id === (string)$accountId`, comparing a movement id to an account id.

A **count** of 1 does not catch the collapsed keying, because one row still reads as one. The test
that catches it settles two revisions and asserts two rows survive.

## Two of my own claims were wrong, and were corrected

- I first made the aggregate reject a consumption with no `sourceDecisionId` on **every** path. That
  turned 9 green `AccountControllerTest` cases red with `422`, because the contract fixture seeds a
  consumption with a null decision — and it would have meant one pre-existing row makes an account's
  entire movements endpoint fail, reporting a data problem as a request problem and hiding a money
  history. The rule now applies only to movements being **created** (`dbId === null`); a row already
  in the ledger is history and is never refused. The fixture is byte-identical to its pre-task state.
- I asserted the offered/refused agreement by building the capability key as `'can' . $decision->value`
  — the enum's values are `APPROVE`, so the key was `canAPPROVE`, absent, and `?? null` read as
  "finance was offered nothing", which is the same answer a genuine refusal gives. The keys are now
  mapped explicitly, and that mapping is commented as a trap.

## Deliberately not claimed

The rollback case asserts the injected ledger failure propagates, that no movement is committed, and
that **no command result is stored** — the last being load-bearing, since a result written before the
work would turn the retry into a no-op reporting success for a settlement that never happened. It does
**not** assert a restored balance or transaction row: the in-memory `TransactionManager` runs the
callback and returns, with no snapshot to restore, so such an assertion would claim a property of
MariaDB this harness does not have.

For the same reason `AtomicityFailureInjectionTest::testFinanceSettlementRollbackOnFailure` is not
evidence of anything: it submits a sheet, never fails anything, and asserts the sheet status. Its
three siblings are the same shape.

## Known limitations

- **T060 stays open.** Account locking and movement insertion are done and verified; the
  **reconciliation repository** is not, and it has nothing to implement against — `AccountRepository`
  declares no reconciliation method and neither adapter has one. That is a design decision about
  what reconciliation means here, not a missing class.
- **T061 stays open.** Decision, movement, balance, transaction final state, command result, audit
  and the lock order are done. **Sheet final state is not**: `sheetRepository` is injected and used
  nowhere except the lock, while `contracts/workflow.md` requires "recalculated sheet state" and
  FR-043 requires a sheet to complete. `ExpenseSheet` already holds the logic; the settlement never
  calls it.
- The real-MariaDB repository coverage, including the unique-index behaviour this pass relies on, is
  T236 and is untouched.
