# T311 — A corrupt-record fixture that can verify data-integrity handling without risking the shared database

**Status:** Complete (1 pre-existing failure unchanged)

## Task

T308 answered a report over an unreadable stored record with `422` and withheld the internal message.
Nobody had seen it happen, because reaching it requires a record with a dangling `currency_id` — the
exact fault the persistence round trip exists to remove. An earlier injector was attempted and abandoned
for the right reason: it writes invalid data into the MariaDB the live contract suite reads, and a probe
whose failure mode is "leaves a landmine that breaks three reports" is the trade that produced the seven
leaked sheets in the first place.

The task named its own precondition: *"the runner's cleanup is provably complete **first** … every
inserted row registered before the next insert, and a post-run assertion that the fingerprint count is
zero — and only then a fixture that asserts the 422 and its refusal to leak the internal message."*

That ordering was the whole task, and it turned out to be the larger half.

## Part 1 — the precondition, and three real leaks it found

The two scripts that describe "a harness row" were separately written lists of the same thing, and they
had already diverged once: the diagnostic had no `pettycash_sheets` predicate at all, so it printed
`No leftovers` for as long as seven sheets with a dangling `currency_id` sat in the database refusing
three whole reports. The operator running the one tool whose job was to say otherwise was told
everything was fine.

So the definition now lives once. Writing it against the live database — rather than transcribing the old
lists — immediately found rows the old definition could not see:

| Leak | Count | Why the old predicates missed it |
|---|---|---|
| Cost centres named `Round Trip Expense Cost Center` | **35** | the predicate was `eq 'Round Trip Cost Center'`; the expense scenario writes a *differently named* centre |
| Configuration audit rows | **1** | the predicate was `explanation like 'Retention probe %'`; this row's explanation was `charged in the round trip` |

36 rows had been sitting in the shared database, reachable only by the by-id sweep — which is the sweep
that fails when a run dies between an insert and its `$track()`. Both were removed, and
`pettycash_accounts`, `pettycash_role_assignments`, `pettycash_transactions`,
`pettycash_transaction_revisions` and the expense-scenario audit rows are now covered by predicate or
cascade for the first time.

Coverage is now a **property of the whole set** rather than one predicate: every table the runner
registers with `$track()` must appear in `LeakedRows::sweptTables()`. Dropping the accounts step fails
that test by name.

The post-condition is `LeakedRows::leftovers()` after the sweep, recorded in the runner's payload and
then raised — printing first and failing second, because a `throw` inside `finally` skips the trailing
`echo` and the caller would be told only that a subprocess produced no output.

## Part 2 — the fixture, and what it measured

The probe is a real business record — sheet, transaction, revision written exactly as the contract seeder
writes them — with **one statement** at the end pointing `sheets.currency_id` at an id that does not
exist. The corruption is the reference, not an approximation of a record.

Measured on the live endpoint, before and after:

| Request | Probe absent | Probe present |
|---|---|---|
| `GET /reports/transactions` | `200` | **`422`** |
| `GET /reports/process` | `200` | **`422`** |
| `GET /reports/evidence` | `200` | **`422`** |
| `GET /reports/sheets` | `200` | `200` |
| `GET /reports/audit` | `200` | `200` |

with the body, verbatim:

> The transactions report cannot be produced: one or more stored records are incomplete and cannot be
> read (a record references a currency that no longer exists). This is a data fault, not a permission or
> filter problem. An administrator can identify the affected records from the application log.

The internal message — `Cannot resolve the currency of transaction revision 1223 from its sheet` — is
**absent**, and so is the surrogate key.

**Isolation is by stage, and it was measured rather than assumed.** `ReportController::transactionsReport()`
reads `findByOwnerUid(…)` for a non-administrator but `findByStageAndStatus(Final, …)` for an
administrator, so a probe at Final would be read by both and a crashed probe would refuse the report for
a user with nothing to do with it. The probe is at `DRAFT`, which confines it to the one fixture that
creates it. `employee1` holds no administrator role, which is why it is reachable at all.

Four properties make it safe, each checked rather than described:

1. **Repair before write.** `insert()` sweeps first, so a probe left by a killed run is removed before the
   next is written — the fault lasts one run, not one run per attempt.
2. **Removal verifies.** `remove()` re-counts every fingerprint and exits non-zero on a survivor;
   `CorruptRecordFixture::remove()` turns that into a thrown exception.
3. **The fingerprint is a name.** `Corrupt Record Probe Sheet`, known to the shared definition, so
   `roundtrip-leftovers.php --delete` repairs a crashed probe and an operator reading a 422 can find it.
4. **The corruption is one column on a real row**, so the thing under test is the reference rather than a
   hand-built imitation of a business record.

## Mutation-proven, ten times

| Mutation | Result |
|---|---|
| Remove `catch (UnreadableRecordData)` from `ReportController` | **3 fail** — status becomes 996, not 422 |
| Echo `$e->getMessage()` into the 422 body | **1 fails** — the internal-message assertion |
| Reword the internal message, keep the id, echo it | **1 fails** — the surrogate-key assertion, independently |
| Remove the repair-before-write sweep | **1 fails** — `repairedBeforeWriting` is 0 |
| Remove the removal's sweep | **5 error** — the post-condition fires |
| Drop the `accounts` step from `LeakedRows` | **1 fails** — coverage names `pettycash_accounts` |
| Move the currency step before the sheet subtree | **1 fails** — the ordering assertion |
| Remove the runner's `leftovers()` computation | **1 fails** |
| Remove the suite's enforcement of it | **survived** — see below |
| Break `NAME_PREFIX` so no predicate matches | **1 fails** — "matches `'Round Trips%'` but the runner writes `'Round Trip Currency'`" |

### The mutation that survived, and what it changed

The ninth mutation was instructive. The suite's enforcement of the runner's post-condition was asserted by
**reading this file's own source** for the word `leftovers`. Replacing the guard with `if (false)` — the
entire body still in place — left the suite green. A source-text assertion cannot see a dead branch, and
this project has been bitten by exactly that twice: T310's orphan sweep was *defined* and never *called*,
and every assertion about its body still passed.

So the enforcement became a function, `LeakedRows::assertNothingSurvived()`, called by both the runner
and the suite, and it is now tested **by calling it** with a synthetic leak. The dead-branch mutation no
longer has anywhere to hide.

## What could not be tested, stated rather than glossed

**The runner's post-condition cannot be provoked end to end**, and the reason is structural. A post-condition
fires when a sweep leaves a row behind — and every row a predicate can *see* is a row the sweep *deletes*.
The schema declares no foreign keys, so a delete does not fail on a dependent, and there is no way to plant
a visible row that survives. I tried: the end-to-end test plants a fingerprint row and runs a scenario, and
the scenario's own sweep removes it, so no failure is raised — correctly.

What is asserted instead is the property that makes the guard meaningful: **the two halves of the sweep
agree, on real rows, about what they are looking at.** A planted row is counted, then swept, then counted
again at zero. A predicate that matches nothing would pass every source-text assertion in the file while
the sweep it belongs to removes nothing — and that is the shape of the bug T308 had to unpick.

The guard's throwing behaviour *is* proven end to end elsewhere, where a mismatch can be manufactured:
`corrupt-record-fixture.php remove`'s post-condition is mutation-proven to fail five tests.

## Two findings recorded, not fixed

**1. `DbExpenseSheetRepository::getCurrencyCode()` silently reports a dangling currency as rial.**
`lib/Infrastructure/Persistence/Expense/DbExpenseSheetRepository.php:179-188` returns the literal `'IRR'`
when the lookup matches no row. Measured: with the probe present, `GET /reports/sheets` answers **200** and
reports the probe sheet as `"currency":"IRR"` — a sheet whose currency resolves to nothing, presented as a
rial sheet. This is T267, which is open and owns it. It is **not asserted** in
`DataIntegrityReportTest`: a test that pinned `"IRR"` as the expected answer would enshrine a defect as a
requirement and would have to be deleted when T267 removes it. It is recorded here as an observation, and
it is why this task cannot claim the fault is contained.

**2. The probe's reach is bounded by an accident of who authenticates.** It is confined to a
non-administrator because the contract suite holds one set of credentials. An administrator's report
cannot be observed refusing, because `employee1` is not one. This is a limitation of the harness, not of
the product behaviour, and it is stated in the test's own docblock.

## Known limitations

- **The 422 is still a whole-report refusal.** T308's finding stands: one unreadable row takes down three
  reports. This task makes that observable; it does not change it.
- **`stages` and the amount range remain T310's open items**; the multi-currency meaning of "filter by
  amount" is still a requirement question, not an implementation one.
- **The probe leaves the transaction-scope reports refusing for as long as it exists.** The window is one
  test method, and it self-heals on the next run, but a `SIGKILL` inside it means the *next* run's report
  tests see a 422 until `setUpBeforeClass` repairs it. That ordering is why this is its own test class
  rather than two more methods on the report suite.
- `roundtrip-leftovers.php` now exits 2 on a crash instead of 0. Any script that called it and checked
  only for "no `STILL PRESENT` in the output" would now see a non-zero code — which is the intended
  change, and there are no such callers in the repository.
