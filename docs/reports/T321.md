# T321 — A transaction's audit did not contain its own submission

**Status:** complete, delivered as **resolution (B)**.
`specs/001-pettycash-v1-core/tasks.md:5348`. Closes the gap T320 recorded as undelivered.

## The defect

FR-051 requires that "formal transaction audit **MUST begin with sheet submission**", and US6/AC1 says
submission is "the first formal event" a reader sees.

`SubmitSheet.php:119-120` records the `SUBMITTED` event with `sheet_id` set and `transaction_id => null`
— correctly, since a submission is a fact about a *sheet* that covers every transaction in it.
`entity_type` is `'sheet'` and `entity_id` is the sheet's id, which is the honest scope for that row,
and `data-model.md:314` declares `transaction_id` nullable for exactly this reason.

But `DbAuditEventRepository` filtered on `transaction_id` alone, so that event was unreachable from a
transaction's history. **Measured: a transaction's audit opened with `ROUTED` — the routing that
happened *after* submission — and contained no submission at all.**

T320 fixed the *order* of this timeline and found its own acceptance criterion unreachable, recording
the cause rather than assuming a fix. T321 is that criterion.

## The decision, and why it is a task and not a line of code

The two artifacts disagreed. FR-051 requires the transaction's audit to begin with a fact the data model
scopes to the sheet. The obvious "fix" — set `transaction_id` on the existing event — is **wrong**: a
sheet submission is one fact covering N transactions, so fanning it out records the same submission N
times and contradicts the `entity_type`/`entity_id` snapshot already on the row.

I stopped and asked rather than picking one, because T321 was written to forbid assuming a resolution.
**(B) was chosen**: keep the single sheet-scoped event and widen the read.

The blast radius is narrower than it first looks, and that shaped the fix. The sheet's history table
reads through `findBySheetId`, which filters on `sheet_id` — populated — so it was already correct.
Only the per-transaction timeline was broken.

## The implementation

`DbAuditEventRepository` gained `applyTransactionTimelineScope()`:

```
transaction_id = :id
  OR (transaction_id IS NULL AND sheet_id = :sheetId)
```

**The read and the count both call it.** T319 requires `countByTransactionId()` to filter identically to
`findByTransactionId()`, because a `total` that does not describe its own page is worse than no total.
One shared helper makes the two unable to drift — which is what let the mutation below be caught.

`sheetDbIdFor()` resolves the sheet with one indexed lookup rather than a correlated subquery.
`IQueryBuilder`'s expression API cannot build a subquery without hand-assembling the table prefix, and a
hand-assembled prefix is correct only until the deployment's `dbprefix` differs.

## The tests

`TransactionTimelineSubmissionTest` — **4 tests**, live HTTP, events generated through the real submit
route and real writers (`ContractFixtures` deletes audit rows and inserts none, so an assumed-event test
would walk an empty set).

`AuditTimelineOrderTest`'s three hardcoded sequences now lead with `SUBMITTED`. This is the update T321
called for: T320's assertion was only checking order *within* a list whose first element was wrong, so a
revert of T321 would have slipped past it. **It no longer does** — 6 tests fail when the widening is
reverted.

### Mutations: 2, both killed

| Mutation | Killed by |
|---|---|
| widen the **count only**, leave the read narrow | `testTheTotalCountsTheSheetScopedSubmission`, `total=2` against 1 item |
| revert both sides to `transaction_id` only | 6 tests across both suites |

The first is the one that mattered. It is precisely the drift this design could have shipped, and the
count/read agreement test caught it with a readable failure rather than leaving a plausible wrong total.

The restore was verified **byte-identical** (`diff` clean) — unlike T320's, whose `/tmp` backup had
captured an already-mutated file and silently left the suite at 4 failures.

## What the test could not do, and the finding it produced

T321 asked for "a sheet with two transactions" so the *sharing* of one submission could be asserted.
**The public API cannot build that state.**

`TransactionController::create()` (`:55`) accepts only `expenseDate` and `amountMinor` — there is no
cost-centre parameter — and `SubmitSheet.php:100` refuses to submit a sheet whose any transaction has no
cost centre (`422 "Transaction missing cost center"`). An API-created transaction therefore can never
be routed, so a two-transaction submitted sheet is unreachable.

This is a **real finding and a separate one**: it concerns the create endpoint's surface, not the audit
read, and closing it means adding a parameter to a contract endpoint. **Recorded, not done** — the next
convergence should raise it.

The single-fact property is guaranteed structurally instead: the predicate's `transaction_id IS NULL`
clause makes a sheet-scoped event singleton by construction, however many transactions the sheet later
gains, and it is asserted directly by
`testTheSubmissionAppearsExactlyOnceInTheTransactionTimeline`.

### A test I had to delete rather than write

I intended to assert that widening the *transaction* read did not also widen the *sheet* read and
double-count the submission. **There is no OCS route for sheet audit at all** — `appinfo/routes.php:29`
exposes only `transaction#audit` — which is also why `findBySheetId()` has no production caller. The
assertion could not be written over HTTP, and inventing a route to test it would have been a second
change in a task about a read. It is protected structurally instead: `findBySheetId()` never calls the
widened helper. Recorded here so the absence is not mistaken for an oversight.

## Process notes

- **The contract fixtures are shared per process, not per test.** Without `ContractFixtures::prepare()`
  in `setUp()`, the first test's submit leaves the sheet submitted and later tests fail `422` — a setup
  failure that reads exactly like a product failure. (T320's tests already reseed; I initially
  misread that as a pass-by-luck and was wrong.)
- **`InMemoryAuditEventRepository` is now deliberately narrower than production.** It cannot fold in
  sheet-scoped events: that needs a transaction→sheet lookup and the double holds audit events with no
  transaction table behind it. Its docblock said it was "faithful … the predicate matches
  `findByTransactionId()`'s exactly", which was true and is still true *within the double* — but
  misleading read as a claim about the DB predicate. Corrected to say it mirrors count/read
  **agreement**, not the **inclusion** rule, and that the inclusion rule is pinned over live HTTP.
- **A stray `lib/Infrastructure/Persistence/Audit/audit.bak` was found and deleted.** It was an
  untracked leftover from the T320 restore, which copied *into* the directory rather than over the file.
  That is the actual explanation of the 4-failure mystery at the start of this session: the restore
  never touched the source file. T321's own backup used an explicit file path and a `diff` check.
