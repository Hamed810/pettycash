# T279 — Report the sheet `transactionCount` honestly

**Status**: Complete

## Task

`SheetController::formatSheet()` counted from the `ExpenseSheet` aggregate, which
`DbExpenseSheetRepository` does not compose on read, so every sheet reported `transactionCount: 0`.
A submitted sheet answered `200` with `status: COST_CENTER` alongside a count of zero — a response
that contradicts itself and understates the purchaser's record.

## Fix

A new `ExpenseTransactionRepository::countBySheetId()` carries the count, implemented in
`DbExpenseTransactionRepository` with a `COUNT` through the query builder and mirrored in the
in-memory double. `SheetController::formatSheet()` takes the repository through its constructor;
the AppFramework resolves it, so no service registration changed.

Counting through the repository rather than `count($sheet->transactions())` also avoids loading
every revision just to produce a number — which matters because `DbTransactionRevisionRepository::mapRow()`
runs four queries per revision.

## Why this was not fixed inside T280

T280 centralised the *transaction* payload. The sheet read model is a separate concern, and folding
it into a completed task would have hidden a second, unrelated change inside a CRITICAL one.

## Verification

Live container, fixture sheet with one seeded transaction:

```
status: OPEN
transactionCount: 1        (previously 0)
```

Two live contract tests:

- `testSheetDetailReportsItsRealTransactionCount` — requires the count to reflect the seeded
  transaction, so the self-contradicting zero cannot return.
- `testSheetTransactionCountSurvivesSubmission` — submits the sheet, then requires both
  `status: COST_CENTER` and a count of `1`. The count is derived rather than stored, so this guards
  against a future change that reads a stale snapshot instead of the live rows.

## Known limitation

The sheet payload still diverges from the contract: no `totals` member, and an undeclared
`accountId`. That is **T281**, which depends on **T105** — the indexed `SheetSummaryQuery` projection
that computes the figures. T281 must not be closed with a hardcoded or empty `totals` object, and
this task deliberately did not create one.
