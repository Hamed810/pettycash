## The defect

`DecisionForm.vue` passed `:error-message` to `NcSelect` and `NcTextArea`. **`@nextcloud/vue` 9.x
has no `errorMessage` prop** — it declares `error` (boolean) and `helperText` (string). The
attribute fell through onto each component's root and the message was never rendered.

The consequence is FR-033's acceptance scenario failing in the way that matters: the decision *was*
refused and the submit button *did* go disabled, but nothing ever said why, leaving the manager with a
dead button. Both controls now use `:error` + `:helper-text`.

A sweep of `src/` confirmed `DecisionForm.vue` is the only site passing an invalid `error-message`;
`SheetDetailView.vue:275`'s match is a `data-test` attribute name, not a prop.

This is the same library-surface-mismatch family T283 found in its first slice — components written
against an `@nextcloud/vue` surface that does not exist.

## Test-side defects, corrected rather than worked around

Three of the four failures were not product gaps: the component already computed `explanationError`,
already gated submit on it, and already generated a `commandId` into the payload.

| Defect | Correction |
|---|---|
| `setValue()` on `[data-testid="decision-select"]` throws `cannot be called on DIV` — the real `NcSelect` is a `v-select` whose root is a `div` and whose dropdown opens on real focus, which never happens under jsdom | Choose through the component's `update:modelValue`, the event a real selection emits |
| The submit control is `type="submit"` inside `<form @submit.prevent>`, so `trigger('click')` raises a click and nothing else; and `submitDecision()` awaits the store before emitting | Submit the form and `flushPromises()` |
| The command-ID assertion could never find the header even if the behaviour were missing: the form delegates to store → `reviewsApi` → `mutate()`, and `mutate()` at `src/services/http.ts:67` sets the header | Assert the identity the component *does* own, and assert it looks like a UUID rather than merely being a present property |

The `v-select` finding was reached independently here, having already been found and fixed in
`PurchaserFlow.spec.ts` — which is worth recording: it is a recurring trap, not a one-off.

## An assertion of mine that was wrong

I first had the component pass
`:aria-describedby="explanationError ? 'decision-explanation-error' : undefined"`, reasoning that an
explicit association was better. It is not: the control *appends* a passed `aria-describedby` to the
id of the helper-text element it renders itself, so naming an id of our own leaves a reference
pointing at nothing — a dangling association, worse than none. The attribute was removed and the test
reads the library's own helper-text element through the ids the control names.

## Slice 2 — `PriorDecisionHistory` and `TransactionReviewDetailView`

**No product defect was found in this slice.** All six failures were the test encoding a contract that
does not exist, which is worth stating plainly: it bears on how much of this task's CRITICAL severity
is real, and it means these components are in materially better shape than the `[x]` on T053 implied.

Four were selector mistakes, each answered correctly by the components under a different name:

| Asserted | Actual |
|---|---|
| `[data-testid="decision-item"]` — matches nothing | `decision-item-{id}`, per decision, which distinguishes an earlier decision from a later one |
| `[data-testid="decision-history"]` — never existed | `prior-decision-history`, with `decision-history-list` inside |
| `[data-testid="evidence-download"]` | `evidence-download-btn` |
| `evidence-preview` exists for a PDF | it is an `<img>`, so image-only by construction; the affordance for any *active* evidence is the preview **button** |

Two asserted English words the code cannot produce: `"Advisory"` (the `l10n` mock returns the message
key, as it must for an assertion to mean the same in any locale — T283's correction) and the raw
enums `APPROVE`/`REJECT` (the component renders `reviews.decision.*`).

The weakest of the six — "full details", which only counted items and looked for four names — is now
driven by a loop over both decisions asserting stage, outcome, actor, role, explanation and timestamp,
which is what FR-034 means by full details.

**Three tests added**, for claims the original six never touched: FR-034's advisory rule is
conditional, so both the negative case and the selective case are asserted (a component badging every
decision would have passed the original); FR-060's active state, so a deactivated item is marked,
loses preview, and remains listed per FR-059; and an image evidence previewing inline with a real
`alt`.

### Two of my own mutations were invalid, and were discarded rather than reported as passes

Forcing `isAdvisory` to `true` "passed" on the first attempt **because the edit had not applied**; a
regex-based variant then broke template collection so the suite reported "no tests", which the RED
rules correctly refuse as evidence. Both were re-run as verified single-line edits. The behaviour is
proven: `isAdvisory` forced true fails the two advisory tests; hiding the explanation fails the
full-details test; offering preview for inactive evidence fails the deactivation test. A fourth check —
that the inline `alt` is the file's name — was confirmed by inspecting the rendered element
(`alt="receipt.png"` against the content endpoint) because the mutation broke collection.

## Slice 3 — `CostCenterQueueView`, `SeniorQueueView`, permitted self-review

No product defect in the views. Five of six failures were the same selector-and-string class, and
**the same three meaningless assertions recur** — an `rtl-layout` class name no requirement names, a
`wcag-aa-contrast` class nothing ever sets, and an inline `font-size` attribute the app never uses
(all typography is in style blocks, and T120 moved the app onto a token scale). All three had already
been removed from `PurchaserFlow.spec.ts` in T283 and were still live here.

Each was replaced by the claim the test's *name* makes, checked where it can be decided:

| Test name | Now asserts |
|---|---|
| Persian RTL without horizontal scroll at 390px | `dir="rtl"`, a breakpoint reaching 390px, and no `min-width` forcing the viewport wider |
| WCAG AA status colours/icons | each row's status is readable text, and carries the badge derived from *its own* status (WCAG 1.4.1 — the half that excludes colour-only signalling) |
| ≥12pt font | none of this view's own declarations falls below the floor (T120's rule, per component) |

**The pagination test lied about what it checked** — named "with paginated transactions" while seeding
two items against a page size of 25, so it asserted a single page, and two rows rather than any
paging. It now seeds a 25-item first page of 30 and asserts the control and page indicator, plus the
complementary case: a queue fitting one page offers no pagination. Writing it surfaced a real property
worth recording: **the view renders exactly the page the server sent and does not slice again**.

`should allow senior to decide independently…` looked for a `DecisionForm` inside `SeniorQueueView`.
There isn't one — a decision is taken on the transaction's own page — and
**`allowIndependentDecision` is a prop no view passes and no code reads** (declared at
`DecisionForm.vue:76`, dead). FR-034 is now checked where the decision is taken: the senior reaches
the form, all three choices are available, and nothing in their path asks them to acknowledge the
cost-centre decision — asserted both by the two acknowledgment hooks one might add *and* by the
rendered view containing no such affordance under any name.

The permitted self-review case asserted `queue-item` and a `decision-button` that never existed. It
now asserts what the **client** owns, and says so: the row renders and its action is present, enabled
and named. Whether the decision is *permitted* is the server's call and T045 covers it — a client-side
assertion that the view "allows" the review would claim an enforcement the interface does not perform.

### RED proven by five mutations, each verified applied before its result was read

Slice 2's lesson was two silently-invalid mutations; these were each confirmed to have applied first.

| Mutation | Fails |
|---|---|
| Pagination shown for a single page | the no-pagination test |
| Breakpoint moved to 300px | `expected 300 to be greater than or equal to 390` |
| A 12px declaration introduced | the floor test |
| **The text removed from `StatusBadge`** | the WCAG test with `expected '' not to be ''` — the assertion that finally makes colour-alone signalling detectable |
| The row's action disabled | the self-review test |

### Two of my own assertions, corrected against the source

I expected 25 rows back from 30 seeded items, assuming a client-side page slice the view does not and
should not perform. And my breakpoint check searched `max-width: Npx` only, missing the range syntax
`width <= 390px` the view actually uses — so it reported no breakpoint on a file that declares one.
Both spellings are accepted now, and a range-syntax regression is caught by the mutation above.

## T053 reopened, and why it cannot be closed by this work

T286's own text required reopening `T053`, and it is reopened. The US2 behaviour is delivered and
verified, but **T053's last three clauses cannot be settled in jsdom**: "no horizontal scroll at
390px" needs a layout engine, WCAG AA contrast needs font metrics, and the ≥12pt floor as a
*measurement* needs a real browser. The checkable substitutes are now in place, but a declaration is
not a rendering. Those clauses belong to `T116`'s test file and `T122`/`T123`'s browser and manual
matrices, and T053 must not be checked again until one of those runs.

## The finding worth carrying forward

Of fifteen failing assertions, **one was a product defect** (`DecisionForm`'s non-existent
`error-message` prop, leaving FR-033's mandatory explanation invisible) and **fourteen were the suite
asserting hooks, class names, English words and raw enums the components were never expected to
produce**.

That ratio is the finding. It is the second time in this feature that a red gate of this size turned
out to be mostly measurement error rather than missing behaviour — and the first time (T283) that same
gate was hiding a spec-wide typography violation. So neither number is a reason to discount a red
gate; both are a reason to read what is actually red.

## Note on verification trust

T288 (appended in the same convergence pass) records that PHP contract tests are served by Apache with
`opcache.enable => On` and `revalidate_freq = 60`, so a PHP run started within 60s of an edit can
execute stale bytecode and report a false PASS or a false FAIL. This slice touched no PHP, and its
frontend evidence is unaffected. **Any PHP number taken in this repository must be read with that
constraint in mind until T288 lands.**
