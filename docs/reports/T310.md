**Status:** Complete (1 pre-existing failure unchanged)

## Task

field for them, or the report rows carried no column for a filter to read, so each request was refused.

## Verification

### The six facets, measured on the live endpoint

| Facet | Before | After |
|---|---|---|
| sheets by creator | `422` unevaluable | `200`, narrows; a creator owning nothing gives `total: 0` |
| transactions by cost centre | `422` unevaluable | `200`, narrows on the active revision |
| transactions by expense type | `422` unknown filter | `200`, narrows |
| transactions by amount | `422` unknown filter | `200`, inclusive bounds |
| audit by stage | `422` unknown filter | `200`, narrows |
| audit by date range | `422` unevaluable | `200`, both bounds |
| the six already working | `200` | `200`, unchanged |

**The sixth facet was not in the task's table.** The note recorded `audit by date range` as *working*.
It was not: `dateRange` reads `occurredAt`/`createdAt` and the audit report emitted neither. Measured,
not read off the table — which is the only reason it was found.

### Sources are FR-064's own

A sheet's creator is its `ownerUid`; a transaction's cost centre, expense type and amount all come
from `revision()` — its **own active revision**, not the sheet, because FR-028 allows one sheet to hold
transactions for several cost centres; an audit event's stage and date are the ones on the event. Every
column was already reachable: **no migration, no schema change**, which answers the join-or-schema
question the task posed.

### The guards still guard

A facet on a report with no such column is still refused: `{"amountMinMinor":1}` against
`/reports/sheets` answers 422 naming `amountRange` *and* the columns the rows do carry. Closing the
filter vocabulary did not become a way to obtain an unfiltered report.

### Mutation-proven

| Mutation | Result |
|---|---|

The last row is the one worth keeping. The first version of that test asserted the sweep was

mutating the call away and watching the suite stay green.

## Two live defects found and fixed

Neither belonged to this task's slice and neither had an owner; both were found *by* measuring.

### 1. The round-trip harness orphaned 28 transactions and was refusing a whole report

`roundtrip-runner.php` swept a leaked sheet by title but not the transactions hanging off it, leaving
`pettycash_transactions.sheet_id` pointing at nothing. `resolveCurrencyCode()` walks
revision → transaction → sheet → currency, so with the sheet gone `GET /reports/transactions` answered
**422** while `/reports/sheets` answered 200. 28 orphaned transactions carried 56 revisions.

T308 fixed the *sibling* fault — a leaked sheet whose currency had been swept — and the same blind
spot survived one level down. That is the strongest available argument that "the sweep is correct" was
never established by reading it.

The fix keys off **the orphan itself** (`LEFT JOIN … WHERE s.id IS NULL`), not off the leaked sheet,
because by the time any sweep runs the offending sheet is already deleted. This was verified, not
reasoned: the first version keyed off the sheet and `roundtrip-leftovers.php` still printed
"No leftovers" against 112 broken rows. 112 rows removed; the report answers 200.

A `IS NOT NULL` guard on `t.sheet_id` keeps a transaction with no sheet at all — a different fault —
out of this sweep, so it cannot quietly delete a row broken for another reason.

### 2. `TechnicalLogger::log()` did not exist and one caller used it anyway

`ReportController::accountsByDbIds()` called `$this->logger->log('warning', …)` on the branch where a
charged account no longer resolves. PHP resolves methods at call time, so the file parsed, the suite
stayed green, and the endpoint would have answered 500 with `Call to undefined method` on exactly the
data fault an operator most wants recorded. The method now exists.

## Known limitations

- **T311 remains open and is not addressed here.** The 422 data-integrity path is still unverified by
  a committed test, because verifying it needs a *deliberate* corrupt record. What this task removed
  was the *accidental* corruption that made the path hard to reach — the precondition T311 asks for,
  not the fixture itself.
- **Amount bounds are unit-less integers.** They are minor units of each row's own currency and carry
  no currency. A single report spanning IRR and USD can be compared against one bound, which is
  defensible for minor units but is not a cross-currency amount comparison. Not resolved here because
  it is a requirement question (what "filter by amount" means across currencies), not an
  implementation detail.
- **`stages` and `currencyCodes` are now evaluable on more report types than FR-064 names.** Each is
  answered from a column that report genuinely carries, so the answers are correct; the vocabulary is
  per-row-answerable rather than per-subject-restricted.
- The multi-currency amount concern above, and T275, both remain open.
