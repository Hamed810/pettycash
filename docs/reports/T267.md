# T267 — A broken currency reference is no longer reported as rial

**Status:** Complete (1 pre-existing failure unchanged)

## Task

`DbExpenseSheetRepository::getCurrencyCode()` returned the literal `'IRR'` when a sheet's currency
lookup matched no row, and `src/views/sheets/SheetDetailView.vue` repeated `?? 'IRR'` in eight
`formatMoney()` calls. A sheet whose `currency_id` no longer resolves was therefore reported, stored
and displayed as a rial sheet. The task's own requirement is unambiguous: "the repository must fail
loudly on an unresolvable currency reference and the view must render the absence rather than
substituting a currency."

**The frontend half was already delivered** and the checkbox did not say so. `formatMoney` is now a
shared utility in `src/utils/money` and takes a `Money`-shaped value; `grep -rn "?? 'IRR'" src/` and
`grep -rn "'IRR'" src/` both return nothing. What remained was the repository — and T311 had left the
fixture that makes it observable, and a report test that deliberately did *not* assert it.

## Why this could be done now, and why it was sequenced after T311

T311 built a fixture that plants one real business record and points its `currency_id` at an id that
does not exist, then wrote:

> That is T267, which is open and owns it. It is **not asserted** in `DataIntegrityReportTest`: a test
> that pinned `"IRR"` as the expected answer would enshrine a defect as a requirement and would have
> to be deleted when T267 removes it.

So the precondition was met and the deliberate omission had an expiry condition. T267 is that task.

## Part 1 — the fault reaches three endpoints, and the task names one

Measured on the live endpoint with the probe present, before the change:

| Endpoint | Before | After |
|---|---|---|
| `GET /reports/sheets` | `200`, probe reported `"currency":"IRR"` | **`422`** |
| `GET /sheets` | `200`, probe in the list as `"currency":"IRR"` | **`500`**, `pettycash.error.unexpected` |
| `GET /sheets/{probe}` | `200`, the corrupt sheet as a **rial sheet** | **`500`**, `pettycash.error.unexpected` |
| `GET /sheets/{healthy}` | `200` | `200` — unaffected |
| `GET /dashboard` | `200` | **`500`** |
| `GET /reports/transactions` / `process` / `evidence` | `422` (T308) | `422` |
| `GET /reports/audit` | `200` | `200` |
| `GET /queues/cost-center` | `200` | `200` |
| `GET /transactions/{probe}` | `500` | `500` |

Two rows of that table are not in the task text. `GET /sheets` and `GET /sheets/{id}` read the same
repository and reported the same fabrication, and they are the two a user is most likely to be
looking at. `GET /dashboard` also hydrates sheets, and it had been answering `200` — so the
substitution was hiding a fourth place, one that no existing test covered at all.

## Part 2 — why a 500, and why that is the right answer rather than a regression

This is the part worth being careful about, because replacing a `200` with a `500` reads like making
things worse.

`UnreadableRecordData` extends `LogicException` **on purpose**. T308 wrote the type that way and
documented the consequence: `ReportController` recognises it and answers 422 with a message that
explains itself, while every other caller keeps the classification `OcsErrorMapper` already gives an
unrecognised fault — 500, message withheld, full detail logged. That is not a decision this task
re-made; it is the decision T308 made when it created the type, and T267 brings a second thrower under
it rather than inventing a second policy.

So the trade is: **a wrong number that looks measured** → **a visible failure with the operator-
actionable detail in the log**. For a financial record read in the wrong unit that is not a close
call, and it is the trade FR-021 and Constitution IV require. What the change does *not* do is solve
T308's standing limitation — one unreadable row still takes down the whole read — and `GET /dashboard`
now demonstrates that limitation on a fourth endpoint, which it did not before.

**Generalising the 422 policy to every sheet-reading endpoint is not done here, deliberately.** It is a
real improvement and it is a separate decision: it changes the status of five endpoints, and a test
that pinned `500` would have to be deleted to allow it. The tests below therefore assert the *absence
of the wrong answer* and enumerate the honest statuses, so the follow-on can tighten them without
unwinding anything.

## Part 3 — the test that had to be inverted

`DataIntegrityReportTest::testTheSubjectsThatDoNotResolveTheCurrencyAreUnaffected` asserted, in as many
words, that `GET /reports/sheets` **must not be refused** by this fault. It was written to pin
reachability, not correctness — and it was correct about what it measured while being wrong about what
the measurement should be. T267 removes the substitution, so `/reports/sheets` refuses, and the honest
move is to move the subject rather than to weaken the assertion or delete the test.

`audit` does not resolve a currency, so it now has a constant of its own. That split is worth the
extra line: it turns "the subjects that are unaffected" from a list that has to be edited every time a
subject is reclassified into a list that has to be edited for a *different* reason.

**The leak assertions were made wording-independent, and that was not cosmetic.** They previously
checked for the literal string `Cannot resolve the currency of transaction revision`. The sheet
repository throws a differently-worded message, so the check would have silently stopped covering it —
asserting something true and proving nothing. They now check the *surrogate keys* by value, which is
what the assertion is actually for, and add `danglingCurrencyId` to the set: telling a caller *which*
reference is broken is as much as they need, and the value itself belongs in the log.

## Part 4 — an assertion that was too weak, and the mutation that proved it

The first version of the two new tests asserted `assertNotSame('IRR', $entry['currency'])`. That reads
like the requirement and is not: it passes against an implementation that substitutes **`USD`**
instead — a different wrong number, in a different unit, from the same line of code. There is no
currency this record is entitled to be shown as, because it does not have one.

The strong form is: **a `200` may not carry this record at all.** Both tests now assert that, and both
mutation-prove it against the `USD` substitution. The report test's `'"IRR"'` check is kept as a
*second*, narrower guard on the specific historical answer, because it documents what the defect
looked like rather than what the rule is.

## Part 5 — mutation-proven, four times

| Mutation | Result |
|---|---|
| Repository: the `'IRR'` fallback is restored | **4 fail** |
| Repository: a *different* wrong currency (`'USD'`) is substituted | **4 fail** |
| Repository: the throw happens but the exception is swallowed | **10 error** |
| Controller: `/reports/sheets` no longer translates the fault into a 422 | **4 fail** |

The second row is the one worth keeping. It is the mutation that killed the first version of the
test, and it is the reason the assertion is shaped the way it is.

## What could not be tested, stated rather than glossed

**A genuinely dangling `currency_id` cannot be produced by the application.** The schema declares no
foreign keys, and the probe is the only way to make one — which is a harness artefact, not a claim that
the fault is reachable in production. What *is* reachable without a probe is the ordinary case: a
currency row that is deleted or deactivated out from under a sheet, which is a configuration action the
application permits. The fixture reproduces the *shape* of that; it does not reproduce the operator.

**The admin path is not covered.** The contract suite holds one set of credentials for a non-
administrator, so the `findByStatus(...)` branches that only an administrator reads — the dashboard's
administrative summary, and the administrator's own view of the sheets report — are not exercised with
the probe present. `/reports/sheets` is covered for the non-administrator branch only. The repository
throws from a single place, so the branch does not change the outcome, but that is reasoning and not
measurement, and it is stated as such.

**`/dashboard` is asserted by no test.** It is in the table above because it was measured, not because
a test pins it. Its new 500 is a consequence of the same single throw and would be caught by a test
written for it; writing one is the natural first half of the follow-on that generalises the 422 policy.
