# T332 — `total` was the page size

**Status:** complete
**Date:** 2026-10-04
**Phase:** 55 — Convergence (seventeen wire-level gaps between the contract, the server, and the client)

## The defect

```php
// lib/Application/Expense/SheetService.php:91-93, before this task
// For total count, we need to add a method to the repository
// For now, we'll estimate from the returned items
$total = count($sheets);
```

`$sheets` is the **already-paged** result of `findByOwnerUid($ownerUid, null, $offset, $pageSize)`.
`SheetController::index()` (`lib/Controller/SheetController.php:62-76`) passes `$result['total']`
straight into the response's `total`, which `PageMeta`
(`specs/001-pettycash-v1-core/contracts/ocs-api.yaml:930-936`) requires and `src/types/api.ts:2`
declares. So with 40 sheets and a page size of 25, page 1 answered `total: 25` while printing 25 of
its own rows, and page 2 answered `total: 1` — one row, described as the whole of the caller's history.

The code said so itself, which is the strongest available evidence that this was known and unfinished:
the repository had no count read, so the estimate stood in for one.

## Why nothing caught it

Below 25 sheets, `count($sheets)` **equals** the owner's real count. Every fixture in the repository
holds fewer sheets than one page carries, so the suite was green and was green correctly: the defect is
only observable when the owner holds more records than a page can return. That is why this task's
acceptance criterion asks for more than one page, and why it is satisfied by an integration test rather
than by a contract test over the existing fixtures.

## Changes

### `lib/Domain/Expense/Repository/ExpenseSheetRepository.php`

`countByOwnerUid(string $ownerUid, ?SheetStatus $status = null): int`, documented against the rule
`AuditEventRepository::countByTransactionId()` states for the audit page and
`AccountService::listMovements()` documents for the account page: `total` counts the scoped set, not
the page.

`$status` exists for **predicate parity**, not because a caller needs it. A count filtered differently
from the read it describes is worse than no count — it looks authoritative and contradicts the rows
printed beside it. That is why `DbAuditEventRepository` routes both sides through
`applyTransactionTimelineScope()` (its docblock records T321 widening both together), and this method
takes the same shape for the same reason. **No endpoint binds a status filter** — that is T333, untouched.

### `lib/Infrastructure/Persistence/Expense/DbExpenseSheetRepository.php`

`COUNT(*)` through the query builder, cast from `fetchOne()` because `COUNT` is `BIGINT` and arrives as
a string on some drivers. The `owner_uid`/`status` predicate moved into a private
`applyOwnerScope()` that **both** `findByOwnerUid()` and `countByOwnerUid()` call, so there is no second
copy of the `status` comparison in the class.

### `tests/TestDoubles/InMemoryExpenseSheetRepository.php`

The same treatment: the filter moved into a private `ownedBy()`, used by both methods. A double whose
count and read disagreed would let a bug through the unit suite and fail only against MariaDB.

### `lib/Application/Expense/SheetService.php`

`listSheets()` reads the count from the repository. Nothing else about the method changed: same
signature, same window, same `items`.

## Tests

`tests/Integration/Persistence/roundtrip-runner.php` gained a `sheetlist` scenario, and
`tests/Integration/Persistence/RepositoryRoundTripTest.php` four tests over it.

**Why a runner scenario.** `tests/bootstrap.php` wires in-memory doubles, and loading `lib/base.php`
into that process would replace the global server — which is why `RepositoryRoundTripTest` reaches MariaDB
through a subprocess (`roundtrip-runner.php`) that prints what it observed while the assertions stay in
the test file. A bug in the runner therefore cannot turn a broken repository green by agreeing with
itself.

**What the scenario does.** Writes a currency, an account and **26 sheets** for one owner against a page
size of 25 — one full page, one row beyond it, and a page past the end — then calls the real
`SheetService` over the real `DbExpenseSheetRepository` for pages 1, 2 and 3, and reports:

- `rawOwnerRowCount` — a plain `COUNT(*)` over `pettycash_sheets`, issued as SQL;
- `ownerScopedCount` — the same question through `countByOwnerUid()`;
- `openCount` / `submittedCount` — the two status-scoped counts (20 + 6 of the 26);
- `otherOwnerCount` — an owner holding nothing;
- each page's `itemCount`, `total` and ids, plus one unbounded read of the same scope.

**Why the SQL count and not the repository's own count.** An assertion of the form "the service agrees
with `countByOwnerUid()`" is satisfied by two halves of the same defect agreeing with each other — which
is exactly the shape `count($sheets)` had. The comparison is against the table.

**Why a probe owner.** `PROBE_OWNER_UID = 't332-sheet-list-probe'`, not `$actorUid`. `employee1` is the
user `ContractFixtures` seeds, so an owner-scoped count taken over it would be the fixture's sheets plus
the scenario's, and every figure would depend on which scenario ran first. `pettycash_sheets.owner_uid` is
a plain 64-character column with no foreign key, so a uid naming no Nextcloud user is a legal value. The
count is therefore an exact number rather than a comparison between two answers that could be wrong
together.

**Cleanup.** The 26 sheets carry `LeakedRows::ROUND_TRIP_SHEET_TITLE`, so the existing fingerprint sweep
removes them along with the scenario's currency and account; each insert is also `$track()`ed for the
by-id sweep. No new table is written, so
`testEveryTableTheRunnerWritesHasAFingerprintThatCanRemoveIt` still holds without a change to
`tests/Support/LeakedRows.php`. The runner reported no `leftovers` key, which is its own post-condition
(`LeakedRows::assertNothingSurvived`) passing.

## The frontend claim in this task's text does not match the source

The task states: *"The frontend computes page count from `total`, so the last 15 sheets are unreachable
through the pager and the 'N results' count under-reports by construction."*

**Verified against the current source, and not accurate.** There is no pager on the sheet list:

- `src/stores/sheets.ts:31` records `pagination.value.total = response.total` and `:62` increments it
  after a create. That is the only reader of the field's value anywhere in `src/` — **nothing** derives a
  page count or a result count from it.
- `src/views/sheets/SheetListView.vue` calls `sheetStore.loadSheets()` with no arguments
  (`:20-25`, so page 1, size 25) and renders `sheetStore.sheets` (`:118`). The file contains no
  `pagination`, no `pageCount` and no page navigation at all.
- The four queue views do compute `Math.ceil(total / pageSize)` — `CostCenterQueueView.vue:117`,
  `SeniorQueueView.vue:120`, `ReturnsQueueView.vue:119`, `FinanceQueueView.vue:118` — and
  `AccountView.vue:158` paginates movements. **The sheet list is not among them.**

So the narrower, true consequence is: a purchaser with more than 25 sheets sees the first 25 and has no
control to ask for page 2. That is a **missing pager**, a frontend gap that exists identically whether
`total` says 25 or 26 — and it is not T332's, which owns the number the server reports. No frontend file
was changed, and none was expanded into one to make the narrative true.

## Known limitations

- **`GET /sheets` still binds only `page` and `pageSize`.** The five filters `contracts/ocs-api.yaml:332-346`
  declares are unbound, so `total` is the count of everything the caller owns rather than of a narrowed
  set. T333 owns that, and its ledger already states the required order: **filter-then-count**. Fixing
  the count first, as here, is what makes that ordering possible.
- **`SheetController::index()` was left alone.** It still takes `int $page = 1, int $pageSize = 25` as
  bare ints, so it does not use `PageBounds`: a `page` of 0 computes a negative offset and a `pageSize`
  above 100 is honoured. Migrating it is a separate change from the count, and `PageBounds`'s clamp/refuse
  rules would alter the endpoint's behaviour for requests T332 does not concern. Not done here, and not
  needed by it.
- **The count is a second query.** `listSheets()` now issues a `COUNT` and a paged read. The
  `AccountService::listMovements()` precedent deliberately chose the opposite trade — read the whole
  ledger once and slice it in memory — which is cheaper and simpler but does not survive an owner with
  thousands of sheets. Two queries is the right shape here; the comment explaining that choice lives in
  the repository method.
- **No contract test asserts this.** A `GET /sheets` contract assertion over the existing fixtures would
  pass with the defect in place, because the fixtures fit in one page. The only honest level for this is
  the one used.
