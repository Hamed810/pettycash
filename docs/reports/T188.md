# T188 Implementation Report — Account Persistence Correctness

**Feature**: PettyCash V1 Core Workflow (`specs/001-pettycash-v1-core`)
**Cycle**: Autopilot implementation cycle 2
**Status**: Complete for the two defects T188 names. Pessimistic row locking remains with T060/T129.

## The 500 on `POST /sheets`

`DbAccountRepository` built its joined projection as a single raw select string containing five
inline aliases. `IQueryBuilder::addOutputColumns()` handles any select string containing ` as ` with
`[, $column] = preg_split('/ as /i', $column)` — an **unbounded** split that keeps only the second
segment. The projection was therefore truncated into a single malformed alias and MariaDB rejected
it with `1064 ... near '.`name` as`. The failure surfaced as an unhandled `DbalException` and a
500 from `POST /sheets`.

Fixed by building the projection with `selectAlias()`, which quotes the column and the alias
separately. Applied through one `applyProjection()` helper so the four read paths cannot drift apart.

## Two further defects behind the same query

Removing the syntax error exposed the next layer, and both were real:

- **`c.public_id` does not exist.** `pc_currencies` has no `public_id`, and `data-model.md` defines
  `Currency` with only `code`, `name`, `minor_unit` and the audit columns — currencies are
  referenced by code, not by an external UUID. The migration was right and the repository was
  wrong, so the column was dropped from the projection rather than added to the schema.
- **`mapRow()` destroyed the aggregate's identity.** `PettyCashAccount::$id` is the public UUID
  string and `$dbId` is the surrogate key, but `mapRow()` assigned the integer primary key into
  `$id`. Beyond violating the property type, this replaced the public identity every caller
  resolves accounts by. `save()` compounded it by choosing `findById((int) $account->id)` over
  `findByPublicId()` on the basis of a truthy `$id`. Both now key off `dbId`.

## Movement written against a guessed account

`DbAccountMovementRepository::save()` wrote `account_id = 1`, annotated *"This needs to be
properly resolved"*, and the unused `getAccountIdFromMovement()` helper looked up
`pc_accounts.public_id` using the **movement's own** id. Every movement would have been attributed
to whichever account happened to hold the key `1` — silent, unrecoverable ledger corruption, and
the exact "exactly-once consumption" guarantee T059/T061 depend on.

`AccountMovement` now carries `accountPublicId`. Both named factories (`createCharge`,
`createConsumption`) already received the `PettyCashAccount`, so the field is populated there and
**no call site changed** — including all seven existing test usages. The adapter resolves the
surrogate key from that public UUID and throws if the account is absent, so the surrounding
transaction aborts rather than writing a wrong ledger row.
