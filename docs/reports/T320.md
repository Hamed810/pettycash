# T320 — The audit timeline was newest-first

**Status:** complete, with one acceptance criterion of the task left undelivered and recorded below.
`specs/001-pettycash-v1-core/tasks.md:5278`.

## The defect

`DbAuditEventRepository` ordered `occurred_at DESC` on all four timeline reads. US6/AC1
(`spec.md:213-216`) says *"submission is the first formal event and every later official event is shown
in chronological order"*, and SC-006 repeats it. Submission — which by definition happened first — was
rendered last.

The inconsistency was visible on one screen: `DbTransactionRevisionRepository:56` already ordered
`revision_number ASC`, so the sheet view listed the oldest revision first and the newest event first at
the same time.

It could not be found by a failing test. The audit table in `SheetDetailView.vue:255` is
`v-if="false"` with no data binding, so the endpoint's order had no user-visible symptom, and no test
asserted an order. The requirement was **unexercised rather than met**.

## The tiebreak was the substance

`occurred_at` is stored at second granularity — every writer formats `Y-m-d H:i:s` — and a submit
followed by two approvals lands inside one second routinely.

**The first version of my ordering test passed against the reversed implementation.** With all three
events sharing one second, the `occurred_at` sequence was *ascending* while the events themselves were
backwards. A timestamp comparison could not detect the defect at all.

The repository now orders `occurred_at ASC, id ASC` via one `inTimelineOrder()` helper. `id` is a
monotonic autoincrement, so it *is* the insertion order, and it makes the sequence total — so T319's
paged walk cannot repeat or skip an event at a page seam. The test asserts the **event-type sequence**
as well as the timestamps: the half that discriminates.

## The three reads, decided as the task required

The task said to decide `findByActorUid` and `findByDateRange` on their own merits rather than sweep
them in. Both decisions are recorded in the method docblocks.

| Read | Decision | Why |
|---|---|---|
| `findByTransactionId` | **ASC** | US6/AC1's timeline |
| `findBySheetId` | **ASC** | US6/AC1's "history table"; renders beside revisions that already come back `ASC` |
| `findByDateRange` | **ASC** | Same event stream over a bounded window. No caller, so nothing is pinned — but leaving it reversed hands the next caller the identical defect, and the signature does not distinguish a timeline from a range |
| `findByActorUid` | **left `DESC`** | `ReportController:518` is its only caller and the report machinery does not re-sort. A bounded report read newest-first is conventional, and **no artifact states an order for reports** — US6/AC1 and SC-006 are about the timeline, and FR-065/FR-066 speak of report *contents*, not sequence. Changing it would be a silent behaviour change to a completed surface (T106, T112) on a requirement that does not reach it |

## Two test-design corrections

**Events are generated, not assumed.** `ContractFixtures` deletes `pettycash_transaction_audit` rows and
inserts none, so a test expecting events would walk an empty set and prove nothing.

**Decisions, not edits.** The first helper tried to add events with `PATCH` after the submit, and every
test failed `422 "Cannot update transactions in a submitted sheet"` — which is correct: FR-026 forbids
editing after submission and the correction path is the only exception. A decision is a post-submission
event, which is what a chronology needs. Using two approvals at two stages also produces a second event
type, so the ordering is checked *within* a type as well as across types.

## Not delivered: the acceptance criterion this task got wrong

T320 required the first item to be "the transaction's `SUBMITTED` event". **It cannot be**, and the
reason is a different root cause in a different method.

`SubmitSheet.php:121` writes the `SUBMITTED` event with `'transaction_id' => null`, because submission
is a sheet-level fact. A read filtered on `transaction_id` therefore never sees it, and the
transaction's own history opens with `ROUTED` rather than with the submission that caused it — which is
exactly what FR-051 forbids:

> Formal transaction audit **MUST begin with sheet submission**

and what US6/AC1 states for the timeline. Measured: the first event is `ROUTED`, not `SUBMITTED`.

This is **not fixed here**, for two reasons. Folding it in would make this task untestable as an
ordering change, and it would put a decision about sheet-versus-transaction event scope — a question
about what `FR-051` means for a sheet-level fact — inside a one-line sort.

`grep -niE "transaction_id.*null|sheet-level|submission event|formal transaction audit" tasks.md`
returns nothing relevant, so **no task owns it**. The tests assert the current first event (`ROUTED`) and
name the gap in their docblocks rather than quietly assuming a fix. **The next convergence should raise
it as its own finding.**
