# T265 — Real Accounts in the Purchaser Sheet Form

**Task ID**: T265
**Status**: complete
**Date**: 2026-09-25
**Spec Kit feature**: `001-pettycash-v1-core`

## Problem

`src/views/sheets/SheetFormView.vue:36-44` returned two invented accounts under the comment
`// TODO: Load from accounts API`:

```ts
accounts.value = [
    { id: 'acc-1', currency: 'IRR', balance: 1000000 },
    { id: 'acc-2', currency: 'USD', balance: 5000 }
]
```

The form therefore always submitted `accountId: 'acc-1'`.
`SheetService::createSheet()` calls `AccountRepository::findByPublicId('acc-1')`, which returns
`null`, and the service throws `InvalidArgumentException('Account not found or access denied')`,
surfacing as HTTP 400. The US1 MVP "create a sheet" journey could not be completed in the browser at
all, and no invented account identifier could be allowed to reach the persistence layer.

## Blocker resolved first

T265 could not be started when selected: it needs `account#index`, and `AccountController` did not
exist. Early Convergence (Phase 30) recorded that dependency and pointed at **T087**. This pass
delivered the account read slice that unblocks it — the configuration and charging halves of T085
and T087 remain open and untouched.

## Files changed

| File | Change |
|---|---|
| `lib/Application/Account/AccountService.php` | **New.** `listForUser()` projects the caller's active accounts into the shape `contracts/ocs-api.yaml` requires: `Account` (`id`, `userId`, `balance`, `active`, `version`) carrying a `Money` balance (`amountMinor`, `currency`, `minorUnit`). `minorUnit` is read from the configured `Currency` aggregate, never from a built-in table. Validates `page >= 1` and `1 <= pageSize <= 100`. |
| `lib/Controller/AccountController.php` | **New.** `index()` with `#[NoAdminRequired]`, routed by the pre-existing `account#index` route. Accepts no identifier that could read another user: a `userId` naming somebody else is refused with 403 rather than ignored. Validation failures go through `OcsErrorMapper::validation()`; everything else through `map()`. |
| `src/services/accountsApi.ts` | **New.** `listAccounts()` over the OCS accounts endpoint. No `userId` is ever sent. |
| `src/stores/accounts.ts` | **New.** Pinia store with `accounts`, `loading`, `loaded`, `error`, `hasAccounts`, and `availableCurrencies` (the currencies of the accounts actually held, per FR-021). |
| `src/views/sheets/SheetFormView.vue` | Invented accounts removed. Reads the store, derives `currency` from the selected account, formats each balance at its own currency's configured scale instead of dividing by a fixed 100, and renders the loading, empty, and error states. |
| `tests/Integration/Account/AccountServiceTest.php` | **New.** 6 tests over the read projection. |
| `tests/Frontend/Component/PurchaserFlow.spec.ts` | Store mocked so the picker's new data source is supplied. |

### Live verification

`GET /api/v1/accounts` against the running instance returned **HTTP 200** and the exact contract
shape, with `minorUnit` read from configuration rather than guessed:

```json
{"items":[{"id":"4444...","userId":"employee1","balance":{"amountMinor":100000000,"currency":"IRR","minorUnit":0},"active":true,"version":0},
          {"id":"8888...","userId":"employee1","balance":{"amountMinor":100000,"currency":"USD","minorUnit":2},"active":true,"version":0}],
 "page":1,"pageSize":25,"total":2}
```

The same endpoint probed with `?userId=admin` returned **HTTP 403**, confirming the scoping is
enforced server-side rather than by the client.

## Known limitations

- Only the active-account projection is exposed. Listing inactive accounts belongs to the finance
  and administration surface owned by T085 and T088, and was deliberately not faked from a partial
  query.
- `tests/bootstrap.php` loads only the Composer autoloader and never Nextcloud's `lib/base.php`, so
  no test in the PHPUnit suite can reach the real database. The new test therefore covers the
  service projection, not the SQL layer; **T236** is the open task that adds the real-MariaDB
  harness, and duplicating it here would have been duplicate work.
- Three of the other account routes (`account#create`, `account#charge`, `account#movements`) and
  the eleven configuration routes still return HTTP 500 because their controllers do not exist.
  Those are T087; T272 will make the drift fail the suite once they land.
- The Vue suite remains red under T164/T175. No test was changed to match broken behaviour: the
  store mock supplies the component's new data source, and the pass/fail counts are unchanged.
