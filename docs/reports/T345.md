# T345 — Make the app's Composer dependencies autoloadable in the deployed app

**Status:** delivered
**Task:** `specs/001-pettycash-v1-core/tasks.md` T345 (Phase 56)
**Date:** 2026-10-05
**Layers touched:** none of the four application layers. Deployment wiring (new `composer/autoload.php`),
one architecture test, one corrected comment.

---

## What the task asked for

`POST /exports` with `fileFormat: xlsx` answered HTTP 500 for every sheet, because
`PhpOffice\PhpSpreadsheet\Spreadsheet` was unresolvable in the deployed app. The task offered two fixes and
asked for one to be chosen and recorded, plus a check that fails when `lib/` uses a `vendor/` namespace not
autoloadable under the web SAPI.

## Both offered fixes were unusable

### (a) `appinfo/app.php` — a no-op on Nextcloud 34

The task proposed adding `appinfo/app.php` requiring `../vendor/autoload.php`. That file is no longer loaded.
`grep -rn "app\.php"` across `/var/www/html/lib/` and `/var/www/html/core/` returns two hits, and neither is
an `include`:

```php
// lib/private/App/AppManager.php:490
if (is_file($appPath . '/appinfo/app.php')) {
    $this->logger->error('/appinfo/app.php is not supported anymore, use \OCP\AppFramework\Bootstrap\IBootstrap on the application class instead.', ['app' => $app]);
}

$coordinator = Server::get(Coordinator::class);
$coordinator->bootApp($app);
```

The file is checked for existence solely to log an error about it, and the app is then bootstrapped without
reading it. Implementing (a) would have produced an inert file, an error on every app load, and the
original 500 — while the diff read as a fix.

### (b) `config.vendor-dir` — correct, and not taken

Every NC 34 core app ships `composer/autoload.php` — 21 of them. `apps/files/composer/` is
`{autoload.php, composer/{autoload_real.php,…}, composer.json}` with `"config": {"vendor-dir": "."}` and
Composer's project living inside `composer/`. So (b) is the convention and it works.

It was declined on scope rather than merit. It relocates 105 locked packages and rewrites `composer.json`,
`tests/bootstrap.php:5`, `scripts/dev/composer`, `scripts/dev/phpunit`, `phpunit.xml`, `psalm.xml:2,6`,
`eslint.config.js:8` and `tests/Integration/Persistence/roundtrip-runner.php:60`.
`docs/development/composer-ownership-migration.md` §5B had already rejected that same operation as unsafe
during a registry outage. That outage has since cleared — `repo.packagist.org` answers `200` again — but
the Composer download cache still holds **0** package archives, so (b) remains a real option and is now a
**smaller** one than it was.

## What was delivered: a tracked `composer/autoload.php` shim

`OC_App::registerAutoloading()` (`lib/private/legacy/OC_App.php:116`) makes one check:

```php
if (file_exists($path . '/composer/autoload.php')) {
    require_once $path . '/composer/autoload.php';
} else {
    \OC::$composerAutoloader->addPsr4($appNamespace . '\\', $path . '/lib/', true);
}
```

It needs **one file at one path** and does not care which layout produced it. So the new
`composer/autoload.php` satisfies the server's `file_exists` and hands back the `vendor/autoload.php`
Composer already generates:

```php
return require $pettycashAutoload;
```

`return require`, not `require_once`, because a generated `autoload.php` returns its loader
(`return ComposerAutoloaderInit…::getLoader();`) and Nextcloud discards the value while the guard test
asserts against it. `autoload_real.php` is itself idempotent, so a second inclusion returns the same
loader.

Nothing moved. No dependency was relocated, re-fetched or re-resolved. `composer.json`, `composer.lock`,
`tests/bootstrap.php`, `scripts/dev/*`, `phpunit.xml`, `psalm.xml` and `eslint.config.js` are untouched.
`composer/` is not gitignored (`git check-ignore` exits 1), so the shim is tracked — which matters,
because `vendor/` **is** ignored and the deployed app is precisely the case where nothing requires the
autoloader by hand.

`php-cs-fixer` covers only `lib/` and `tests/`, so the shim is outside the linted set, consistent with it
being a loader stub rather than application code.

## The required check, and why it is not a contract test

The task's own reasoning was right and is worth keeping verbatim in the task file: *"a contract test would
not catch it either, because the CLI loads the autoloader the test bootstrap asks for, and that is the whole
reason this survived a green suite."*

`tests/Unit/Architecture/DeployedAutoloadReachabilityTest.php` asserts against the `ClassLoader` that
`composer/autoload.php` **returns**, using `findFile()` — which consults only that loader's own classmap and
PSR-4 prefixes and never falls through to the ambient autoloader. `class_exists()` is exactly the assertion
that passed for the whole life of this defect.

Four tests:

1. **The entry point exists** at the path `registerAutoloading()` probes, and is not a Composer-generated
   file. The `@generated by Composer` marker being absent is the collision guard: if someone sets
   `vendor-dir` to `composer/`, Composer overwrites the shim, and this fails with that instruction.
2. **Every third-party class `lib/` imports resolves through that loader.** `OC\`, `OCP\`, `OCA\` and `Psr\`
   are excluded, each with a reason — the first three come from the server or the PSR-4 fallback, and
   `Psr\` from Nextcloud's own `3rdparty`, which is why `Psr\Log` works today.
3. **The scan is not vacuous** — the self-check the other two architecture tests (`LayerBoundaryTest`,
   `RouteDispatchCompletenessTest`) carry, for the same reason: a regex over source that stops matching
   reports nothing while proving nothing. It asserts `PhpOffice\PhpSpreadsheet\Spreadsheet` specifically,
   so a change to the exclusion list or the pattern fails loudly instead of shrinking the set to nothing.

**Mutation-verified in the direction that matters.** With `composer/autoload.php` moved aside the file is
RED: `testTheDeployedAutoloadEntryPointExists` fails naming the defect, and the reachability test errors on
the missing require. Restored afterwards. It is not a test that passes either way.

## The shim's own two branches, both exercised

| State | Behaviour | Verified |
|---|---|---|
| `vendor/` present | returns `Composer\Autoload\ClassLoader`; `findFile('PhpOffice\PhpSpreadsheet\Spreadsheet')` → the real on-disk path | container `php -r` |
| `vendor/` missing | stderr message naming the missing file and `composer install`, returns `NULL`, **survives without fatal** | container, isolated copy without a sibling `vendor/` |

The non-CLI branch emits a 500 JSON body via `http_response_code()` rather than throwing, because the file
is required during app bootstrap before the AppFramework error handler exists.

## One adjacent false statement removed

`tests/Integration/Persistence/roundtrip-runner.php:55` asserted:

> Nextcloud core loads `<app>/vendor/autoload.php` for every enabled app (OC_App::registerAutoloading),
> which is why the app can use PhpSpreadsheet under Apache.

This is the same false premise as option (a), in a comment that would have led the next reader to the same
wrong conclusion, and it **inverted the real asymmetry**: the runner and PHPUnit both load the autoloader by
hand, while a real request does not. Corrected in place, with the asymmetry restated so the line is not read
as redundant.

  run without `vendor/` at all — so nothing is newly required of a deployer.
