# T288 — PHP verification immune to Apache's opcode cache

**Task**: T288 (HIGH) — **complete**
**Feature**: PettyCash V1 Core Workflow (`specs/001-pettycash-v1-core`)
**Date**: 2026-09-26

## The problem, reproduced

`scripts/dev/phpunit` reported 190 tests / 937 assertions / 1 failure (T275) at rest. Nothing about
that run was untrustworthy, but nothing proved it either, and the way it was reached did not.

The container runs `opcache.enable => 1` with `opcache.revalidate_freq => 60`, and
`opcache.enable_cli => 0`. PHPUnit runs in the CLI SAPI, where the cache is off, so **unit and
integration tests always recompile and cannot be affected**. The OCS contract tests are the opposite:
they issue real HTTP requests through `OcsTestClient` (`tests/Contract/Controller/OcsTestClient.php:32`),
so `lib/` is loaded by Apache's `mod_php` through the cache.

The result is that a run started within 60 seconds of an edit can execute the previous bytecode, and
the CLI SAPI has no way to notice. Both directions are possible, and both were measured here with a
canary that threw unconditionally from `SheetPayloadFormatter::totals()`:

| `lib/Infrastructure/Http/SheetPayloadFormatter.php` | settle | `scripts/dev/phpunit --filter SheetTotals` | truth |
|---|---|---|---|
| canary — throws | no | 13 / 13 passing | **false PASS** |
| correct | no | 2 failures | **false FAIL** |
| canary — throws | yes | 2 failures | correct |
| correct | yes | 13 / 13 passing | correct |

The middle two rows are the ones that matter. Correct code failed two contract tests, and the
failure mode was indistinguishable from a real regression: `null` where `100000` was asserted, which
is exactly the shape of a genuine defect. An agent that trusted it would have "fixed" working code.

T288's own record of a four-test false FAIL that then passed unchanged is the same event seen from
the other end, which is why the task said both directions were possible rather than only the one it
had caught.

## The fix

`scripts/dev/phpunit` now calls `scripts/dev/opcache-settle` before it runs, and fails the run if
the wait cannot be computed. `scripts/dev/opcache-settle --status` reports without blocking and
exits 3 while a wait is outstanding. `AGENTS.md` gains an **Opcode Cache Settling (MANDATORY)**
section, so an agent meets the constraint before it produces a number rather than after.

### Why it waits instead of resetting

The task allowed either a helper that clears the SAPI cache or a documented settle requirement. A
reset is not reachable from here, and establishing that was itself worth recording:

- `opcache_reset()` only affects the SAPI it is called in. `php -r 'opcache_reset();'` through
  `scripts/dev/in-container` runs in the CLI SAPI and resets nothing that serves a request.
- Dropping a script into the document root does not work either. `/var/www/html/.htaccess:216` is a
  front-controller config — `RewriteCond`s narrow the allowed extensions and everything else falls
  through `RewriteRule . index.php`. A dropped `opcache-probe.php` returned the Nextcloud 404 page
  rather than executing. Confirmed by probe, not assumed.
- The remaining route is `apachectl -k graceful` or a container restart, which is shared environment
  state. It was not used, and is not needed.

So the helper waits, and waiting is not a compromise here — it is sufficient by proof. With
`opcache.validate_timestamps => 1`, a cached entry is served without touching disk only while
`now - t_last_check < revalidate_freq`, and `t_last_check` is a moment at which the file's mtime was
already correct. A *stale* entry therefore requires `t_last_check < mtime`, and hence requires
`now < mtime + revalidate_freq`. The contrapositive is the rule implemented: once
`now > mtime + revalidate_freq`, nothing stale can be served. `opcache.max_accel_time` is unset, so
there is no second, shorter TTL, and `opcache.file_update_protection` (2s) only stops caching freshly
written files, which errs towards recompiling.

The values are read from the container rather than hardcoded, and `opcache.enable` and
`opcache.validate_timestamps` are both required to be `1` — if timestamp validation were off, no
amount of waiting could help, and the helper exits non-zero instead of pretending otherwise.

### Scope

`lib/` and `appinfo/` are what Apache loads for this app. Directories are scanned as well as files, so
a create, rename or delete updates the parent directory's mtime and is covered. Editing `tests/`,
`docs/`, the frontend or the scripts costs nothing, because none of it is loaded by the SAPI.

### The helper cannot report a false "settled"

The interesting failure mode for a verification helper is reporting success without checking, so
each value it reasons about is validated before use rather than trusted:

- An empty command substitution inside `$(( ))` evaluates as `0`. A failed `find` would therefore
  have produced a deadline in the past and an immediate, confident "settled" — the same class of
  false pass this task exists to remove. `newest_mtime` and `now_epoch` now reject non-numeric output
  and a failed `docker exec`, and the caller aborts.
- A final confirmation is read back *after* the wait instead of being assumed from the loop's
  comparison, so the reported state is a measurement.
- Every pass re-scans, so an edit made while the helper was already waiting extends the wait rather
  than being missed.

Nine paths were exercised with a stubbed `in-container`, all as intended: container unreachable,
empty settings, unreadable mtimes, settled, unsettled `--status` (exit 3),
`validate_timestamps=0` (exit 1), opcache disabled (exit 0), missing `revalidate_freq` (exit 1),
unknown argument (exit 2).

`read_setting` is a bash loop rather than a JSON parse so that a mandatory step in every PHP
verification run does not depend on a JSON parser being installed on the host.

## Also covered: e2e

`tests/E2E/purchaser-submit.spec.ts` reaches the app at `http://localhost:8080`, so Playwright also
executes `lib/` through Apache's cache and had the same exposure. `npm run test:e2e` now settles first
via a `pretest:e2e` hook, and `AGENTS.md` says so in the frontend section where an agent running e2e
will see it.

## Known limitations

- **The wait costs up to 61 seconds**, once per edit to `lib/`/`appinfo/`, and zero when nothing has
  changed recently. This is the price of not touching the shared container. If restarting Apache is
  ever approved, a reset would remove the cost entirely; the arithmetic above would then be a
  belt-and-braces check rather than the mechanism.
- **The wait is a bound, not a lock.** A contract run that itself triggers a `lib/` write would not be
  covered, and the contract tests do not write PHP. Editing `lib/` from inside a running test process
  is not something this repository does.
- **`npm run test:e2e` is red on a pre-existing harness defect**, not on this task. `playwright.config.ts`
  defines no `storageState` and no `globalSetup`, so the suite drives the app unauthenticated and
  every test times out waiting for `[data-test="create-sheet-button"]` after Nextcloud redirects to
  the login page. Verified pre-existing by re-running with this task's changes stashed: identical
  failure. No open task covers it, which is recorded in the completion report as a task-state gap.
