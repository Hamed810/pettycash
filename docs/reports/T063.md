# T063 — account creation and charging (contract tests and implementation)

**Status**: complete
**Feature**: PettyCash V1 Core Workflow (`specs/001-pettycash-v1-core`)

## What it was

`appinfo/routes.php` declares four account routes. `AccountController` implemented two, so
`account#create` and `account#charge` resolved to a method that did not exist and answered **HTTP
500**. A declared route answering 500 is worse than an absent one: the contract says the endpoint
exists, a caller can construct the request, and the failure arrives as a server error rather than as a
404 that would have said plainly that nothing had been built. Nothing noticed, because the only account
assertions were reads.

## Three decisions worth stating

**Who may open an account.** The caller may open their own; an administrator may open one for another
user (FR-013's "manage … accounts **for users**"); anyone else naming another `userId` is refused.
`userId` is the only identifier in this controller that comes from the request rather than the trusted
session, so it is the only one that could open an account for an arbitrary uid — and an endpoint that
did would be an account-minting oracle.

**Who may charge.** FR-015 says **finance** charges an account, so the charge requires the `FINANCE`
role; an administrator is admitted as well, because FR-013 puts account funding with administrators
and the spec's own journey has the same person doing both. That reading is recorded here because it is
an interpretation, not a quotation.

**Ownership is deliberately not the rule for a charge.** The first draft of that test asserted that
another user's account must be refused, on the reasoning that the ledger is the most sensitive read in
the application. That is FR-015's opposite — it says finance charges "a **selected user** petty-cash
account", so charging somebody else's account is the normal case. The test now asserts the 404 for an
account that is not there, and the reason the first draft was wrong is recorded in the test so the
correction is not itself undone later.

## The catch order was the bug

`InvalidArgumentException` extends `LogicException`, so a single `catch (\Exception …)` — added to turn
an unparseable `occurredAt` into a field error — silently caught the stale-version failure too and
answered 422 where the contract requires 409. A caller told "reload and retry" by a 422 has no way to
know that. The specific catches now come first, and the request's own shape is validated in the
controller where the field names are still known.

## Fixture work this needed

- **A third currency.** The acting user already held an IRR account and a USD account, and FR-014
  allows one per currency, so *every* create collided with the seed and the endpoint could only be
  observed in its refusal. A 409 was the first thing these tests saw, and reading that as "creation is
  broken" would have been the wrong conclusion.
- **Created accounts are removed on every seed.** `pettycash_accounts_user_currency_uniq` makes an
  opened account permanent, so without this the endpoint's behaviour depended on whether the suite had
  run before.
- **The movement cleanup covers every account the user holds**, not only the primary one. A charge
  against the USD account leaves its movement behind just as a settlement against the IRR account does,
  and a surviving movement describes a balance its account no longer holds — which broke two existing
  read tests until it was widened.

| remove both duplicate guards | fails **1** |

The last three are the useful results.

**The finance gate is implemented, correct, and unverified.** The contract user is a finance officer,
and the only state granting the `FINANCE` role is `finance` — which the charge tests *have* to prepare,
precisely because the rule is real. So no HTTP request in this file can be a refusal. This is a harness
gap (one credential, one identity), not a product one, and is recorded as **T291** rather than papered
over with a weaker assertion.

**The duplicate-account 409 rests on one of two guards, not both.** Either alone produces the same
answer, and only removing both breaks it. The pre-check is the clearer path to the conflict; the catch
is the one that survives two concurrent opens of the same pair, since both can read "no account" and
then both insert. Both stay, and this report does not claim either is independently pinned.

## Known limitations

- The FR-015 actor gate has no failing test available (T291).
- The two duplicate-account guards are mutually redundant for the observable 409, so a future change
  could remove one without any test noticing.
- `AccountService` still builds the account and movement arrays inline, alongside the
  `AccountPayloadFormatter` T057 added — unchanged by this task, and still recorded as T289.
