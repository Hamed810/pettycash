# T246 / T247 / T248 Implementation Report — Live-Data Persistence Defects

**Feature**: PettyCash V1 Core Workflow (`specs/001-pettycash-v1-core`)
**Cycle**: Autopilot implementation cycle 4
**Status**: All three complete and verified against the running container.

These three defects were found by cycle 3, when T221 seeding finally gave the contract suites real
records to exercise. None of them was reachable before: with an empty database every request
short-circuited on a missing record.

## T246 — every inserted aggregate claimed primary key 1

`QueryBuilder::executeStatement()` delegates to `IDBConnection::executeStatement()` and returns the
**affected-row count**. Seven repositories did `$insertId = $qb->insert($table)->...->executeStatement()`
and then assigned `$entity->dbId = (int) $insertId`, so every newly created aggregate was told it
had id `1`.

The visible symptom was `Integrity constraint violation: 1062 Duplicate entry '1-1'` on the
`pc_transaction_revisions(transaction_id, revision_number)` unique key: the new revision was written
against `transaction_id = 1` — whatever transaction happened to be first — instead of the one just
inserted. Accounts, decisions, evidence rows and public links were silently mis-attributed the same
way, which is precisely the audit-integrity failure Constitution IV forbids.

Fixed with `$qb->getLastInsertId()`. Note that `IQueryBuilder::insertId()` does not exist in
Nextcloud 34 and `IDBConnection::lastInsertId()` is deprecated in favour of
`IQueryBuilder::getLastInsertId()`, which is the API used.

### A consequence worth recording

Fixing T246 exposed a chicken-and-egg the placeholder code had been hiding.
`TransactionService::createTransaction()` writes the transaction with a null `active_revision_id`,
then the revision, then the transaction again to set the back-link. The second `save()` began by
loading the full aggregate, and `mapRow()` requires an active revision — which does not exist yet at
that point. `save()` now resolves the current `lock_version` through a narrow `findLockVersion()`
projection instead of hydrating the aggregate, which is both correct and cheaper.

## T247 — evidence upload could never succeed

`putEvidence()` writes through the AppData filesystem, and `EvidenceService::uploadEvidence()`
immediately called `getChecksum()`, which read the same file back through AppData *inside the
still-open workflow transaction*. The filecache read runs on a different connection that cannot see
the uncommitted row, so every valid upload ended in
`RuntimeException: AppData file not found` after a burst of `dirty table reads` warnings.

A checksum is a pure function of the bytes, so depending on a cross-connection read of an
uncommitted row was never necessary. `PrivateFileStore::getChecksum(string $key)` is replaced by
`checksumOfContent(string $content)`; the Nextcloud adapter, the in-memory double and the service
were updated together. Evidence upload now returns 201 against a real record.

## T248 — revision update wrote columns the table does not have

`pc_transaction_revisions` has `created_at`/`created_by` and no `updated_at`/`updated_by`; the
update branch wrote both. This is the third instance of a repository diverging from the migration
and `data-model.md` (after `pc_currencies.public_id` and `pc_sheets.created_by`), and it is why the
portability and schema checks alone did not catch it — the checks verify constructs, not agreement
with the migration.

## Verification details

Probing the live API directly showed the application is now returning *correct* rejections rather
than failures, which is what distinguishes a fixed defect from a masked one:

- `PATCH /transactions/{id}` with `expectedVersion: 0` → 422 `Revision is incomplete`
- `PATCH /transactions/{id}` with `expectedVersion: 1` → 422 `Stale version` (optimistic concurrency working)
- `POST /transactions/{id}/decisions` → 403 `User not authorized for this review stage`
  (the contract-test user holds no review role, so this denial is correct)

## Known limitations

The remaining 16 failures are **test-side**, not application defects, and remain open under T221:

- the suites send `expectedVersion: 1` while the seeded records are at version `0`;
- the decision cases need a cost-center-manager role assignment and a transaction actually awaiting
  cost-center review — the single seeded draft transaction cannot be both a draft and in review;
- `testDeleteEvidenceReturns200WithDeactivatedMetadata` and
  `testGetEvidenceContentReturns200WithStream` still address a non-existent evidence id, which now
  must be captured from a real upload.
