# T329 — Report filters reach the server under one name and one vocabulary

**Status:** complete
**Date:** 2026-10-03
**Phase:** 55 — Convergence (seventeen wire-level gaps between the contract, the server, and the client)

## The defect

`GET /reports/{reportType}` was returning the **unfiltered** report for every request the frontend
made, while the filter bar rendered as though the user's filter had been applied.

Two independent causes, and fixing only the first would have converted a silent wrong answer into a
`422`:

**Axis 1 — encoding.** `reportQuery()` (`src/services/reportsApi.ts`) wrote each populated filter as
its own query parameter. `ReportController::show()` binds a single `string $filters = ''`
(`lib/Controller/ReportController.php:100`) and JSON-decodes it, and an empty value yields a bare
`new ReportFilter($page, $pageSize)`. So `$filters` was always `''` and every filter was discarded
before any rule ran.

**Axis 2 — vocabulary.** `ReportFilters` (`src/types/reporting.ts`) and
`ReportFilterFactory::ACCEPTED_FILTERS` had **zero** name overlap — not even `dateFrom`/`dateTo`
against `from`/`to`. Once the encoding was fixed, every filter the UI could produce would have been
refused as an unknown key, which is what `ReportFilterFactory`'s closed vocabulary does by design.

The same wrong object also travelled into `POST /exports` as `ExportRequest.filters`, which
`ExportController` hands to the same factory.

## Where the defect actually was

Entirely client-side. The server was already correct and already covered: `ReportFilterFactory` owns
one closed vocabulary for both endpoints, and `ReportAndExportControllerTest` asserted the facets, the
refusal of unknown names, the misspelling case and the export parity. This was found by reading the
code that builds and reads the value, not by a failing test.

That is the same trap Phase 55 recorded for T327: the frontend specs stub `@nextcloud/axios` and hand
the store a hand-written fixture, so a green frontend suite is not evidence that a wire is connected.
Two of the frontend tests here asserted the broken encoding and **passed**, because they agreed with
`reportQuery`.

## The id-space decision

`data-model.md` states the rule this task had to apply:

> Every externally addressable aggregate uses an immutable UUID `public_id`; numeric `id` values
> remain internal join keys.

A filter named `costCenterDbIds` therefore publishes an internal join key across the API boundary and
asks a client for a surrogate key it cannot otherwise obtain.

**Decided (with the user, before implementation):**

- **`costCenterIds` / `expenseTypeIds` added to the accepted vocabulary**, taking **public UUIDs**.
  `lib/Application/Reporting/FilterIdentityResolver.php` resolves them to the surrogate keys
  `ReportQuery` filters on, following the `ChargedAccountScope` pattern already in that namespace.
- **The `*DbIds` spellings were kept, not replaced.** T306 and T309 pinned them in the contract tests
  and `ExportController` accepts the same object; removing them would be a breaking contract change
  made as a side effect of fixing a client, which no task authorises. Both spellings union into the
  same `ReportFilter` field.
- **An unresolvable public id is refused with a 422 naming it**, never dropped. Dropping it would
  return the superset while the caller believed the filter applied — the exact failure the closed
  vocabulary exists to prevent.

## `period`

Not given a fourth encoding, as the task required. It is not in the accepted vocabulary, and T312
remains blocked on the open `/speckit.clarify` question about whether `period` joins FR-064's set or
stands in a declared relationship to a date range.

- `ReportPeriodPreset` keeps the full V1 vocabulary.
- **`REPORT_OFFERABLE_PERIODS` is new and holds only `custom`** — that is what the filter bar offers.
- The preset is no longer part of `ReportFilters` at all; it is component state, so the request cannot
  claim a filter the server cannot answer.

Offering the Jalali presets today would have re-created this task's own defect: the user picks
"month", nothing is sent, and the unfiltered report is rendered.

## Two further defects found while implementing

1. **`ReportQuery::RULE_REQUEST_NAMES` did not know the new names.** A request that had *passed* the
   closed-vocabulary check was then refused by `assertFilterIsEvaluable()` naming `costCenterDbIds` —
   a word absent from the request and from the accepted-filter list shown to the caller two lines
   earlier. Both spellings are now named for both rules.

2. **A docblock claimed a guard that did not exist.** `ReportQuery::RULE_REQUEST_NAMES` documented
   itself as "Asserted against `ReportFilterFactory::ACCEPTED_FILTERS` in
   `ReportFilterFactoryTest::testEveryRequestNameIsAnsweredByARule`". That test was never written. It
   is written now, and it iterates `ACCEPTED_FILTERS`, so the next name added to the vocabulary without
   a rule able to refuse it by the caller's own name fails there instead of shipping.

### RED-state validity

The new contract tests were written against behaviour that did not exist (`costCenterIds` was refused

assertion on missing behaviour, not by collection or configuration failure. Zero skipped, zero
incomplete.

## What the tests assert, and why the contract test carries the weight

`testAStatusAndADateRangeInOneRequestReturnOnlyRowsSatisfyingBoth` asserts an **exact set equality
against a locally computed intersection** over real HTTP, and **first** asserts that each facet on its
own strictly narrows the unfiltered report.

That ordering is the whole test. Without it, "both facets applied" and "one facet applied" produce
identical output and the test measures nothing — which is exactly how the original defect survived
T306's one-facet-at-a-time coverage. The status and the window are both derived from the returned rows
rather than hardcoded, because the report is built from whatever the fixture and preceding tests have
left behind.

The public-id spelling is asserted over HTTP to select **the same rows** as the surrogate-key
spelling. That is what makes the id-space decision testable rather than a claim in a docblock. The
unresolvable case is asserted over HTTP too, because what it guards is the answer being a `422` rather
than a `500`.

## Known limitations

- The filter bar's cost-centre field is **free text**, not a picker, so FR-064's cost-centre facet
  needs a user to paste a UUID. That is T088's configuration UI and was deliberately not widened here.
- `actorUids`, `eventTypes`, `currencyCodes`, `createdBy` and `expenseTypeIds` are accepted and pruned
  correctly but have no input in the filter bar yet. They were reachable in the old type and reachable
  in none of the UI, so no affordance was removed.
- The Jalali period presets remain unimplemented and unoffered. That is T312, blocked on
  `/speckit.clarify`.
