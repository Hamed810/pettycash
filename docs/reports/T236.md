# T236 — the real-MariaDB harness, and the nine repositories it found broken

**Task**: T236 (complete)
**Feature**: PettyCash V1 Core Workflow (`specs/001-pettycash-v1-core`)
**Date**: 2026-09-27
**Preceded by**: `docs/reports/T289.md`, `docs/reports/T291.md` (US3 finance/account slice)

## The task

Constitution V requires automated integration tests for persistence, revisions and audit records "when
a suitable harness exists". T236 recorded that no such harness existed: every test substitutes one of
13 `InMemory*` doubles, so **no test in the repository had ever executed a real SQL statement against
the production repositories**. It named two concrete symptoms and a diagnosis.

Both symptoms were already fixed by earlier passes — `DbAccountMovementRepository` no longer
hardcodes an account id, and `DbAccountRepository` uses `selectAlias()` for its currency columns. The
diagnosis was the part that held.

## Why a subprocess, and why the assertions are not in it

`tests/bootstrap.php` wires a lightweight container of in-memory doubles and never loads Nextcloud's
`lib/base.php`. Loading it into the PHPUnit process would replace the global server and break every
other suite — which `seed-contract-fixtures.php` had already established and documented.

So the round trips run in `tests/Integration/Persistence/roundtrip-runner.php`: bootstrap the server,
build the fourteen repositories, save an aggregate, read it back through the repository's own join
keys, print the observed values as JSON, delete every row it created. `RepositoryRoundTripTest`
asserts on that JSON.

The split is the point. If the runner asserted, a bug in the runner could agree with itself and turn a
broken repository green. With the assertions in PHPUnit, a failure names the figure MariaDB actually
held.

The runner also has to establish an identity itself: every `save()` stamps `created_by` from
`CurrentUser::uid()`, and `NextcloudCurrentUser` throws rather than invent one. It resolves the user
and puts it in the session, the way an `occ` command does.

Four scenarios — `configuration`, `account`, `expense`, `command` — so four bootstraps, covering all
fourteen repositories. The file runs in 0.75 seconds.

## What it found

Nine repositories were defective. **Three of them could not write a single row.**

| Repository | Defect | Consequence |
|---|---|---|
| `DbCostCenterRepository` | wrote `manager_uid` + `senior_manager_uid` | every cost-center write failed |
| `DbRoleAssignmentRepository` | wrote `lock_version` on insert and update | every role-assignment write failed |
| `DbCostCenterRepository` | omitted `public_id` (`NOT NULL`, no default) | failed on the constraint |
| `DbExpenseTypeRepository` | omitted `public_id` | failed on the constraint |
| `DbRoleAssignmentRepository` | omitted `public_id` | failed on the constraint |
| `DbAuditEventRepository` | assigned neither surrogate key nor `publicId` | an appended event was unfindable |
| `DbCurrencyRepository` | `mapRow()` never assigned the surrogate key | a re-read currency looked unpersisted |
| `DbWorkflowDecisionRepository` | `save()` never assigned `publicId` | unfindable by public id |
| `DbEvidenceRepository`, `DbEvidenceLinkRepository`, `DbExpenseSheetRepository`, `DbExpenseTransactionRepository`, `DbTransactionRevisionRepository` | same `publicId` gap | five more rows unresolvable |

Concretely, live against the shared database:

```
INSERT INTO oc_pettycash_cost_centers … Unknown column 'manager_uid' in 'INSERT INTO'
INSERT INTO oc_pettycash_role_assignments … Unknown column 'lock_version' in 'INSERT INTO'
```

Cost-centre, role-assignment and expense-type administration **could not have written a single row**.
They are latent rather than live only because the endpoints that would call them are still open
(`T087`). Had `T082` landed first, it would have failed on first use — and the contract suite would not
have shown it, because no contract endpoint writes configuration either.

## Two fixes are removals, and the approved artifacts decided the direction

**A cost centre has no manager.** `data-model.md` gives `CostCenter` `id`, `public_id`, `code`,
`name`, `description`, the validity window, `active`, the audit columns and `lock_version` — and
states the relationship as *"Has effective-dated cost-center-manager and senior-manager **role
assignments**"*. `ManagementReviewService::getManagedCostCenterCodes()` already resolves a reviewer's
scope through `RoleAssignmentRepository` and never through the cost centre.

So `CostCenter::$managerUid`/`$seniorManagerUid` and the port's `findByManagerUid()` /
`findBySeniorManagerUid()` were **removed rather than given columns**. Keeping the fields while
nothing persisted them would be the worse version of the same defect: `T082` would create a cost
centre, pass manager uids, and watch them disappear. The test now asserts the relationship that
replaced them — a senior-manager assignment scoped to a cost centre resolves back to it, which is the
join the review queue depends on.

**`RoleAssignment` has no `lock_version`** — not in `data-model.md`, and not in the table:
`Version010000Date20260920000000.php:64` passes `auditColumns($table, false)`. The repository was
writing it anyway. Removed, with the omission explained in place so it is not "corrected" later.

**`AccountMovement` is the one repository deliberately left alone.** It is `final readonly`, so its
database identity cannot be assigned after construction — and that is right, not an omission: a
movement is a fact, and the caller gets a new instance carrying the surrogate key from `mapRow()`.
`findByCommandId()` is the lookup that must work, since it is the path a replayed command takes, and
it is asserted.

## Verification that this is not a vacuous pass

| Mutation | Result |
|---|---|
| `manager_uid` back in the cost-centre insert | **fails 5** — the round trip reports `Unknown column 'manager_uid'` |
| `supersedes` reads back the surrogate key instead of the public UUID | **fails 1** — `testASecondRevisionSupersedesTheFirstByPublicId` |

The first proves the harness executes real SQL. The second proves the assertions bite on stored
*values*, which a suite asserting only "no exception" would have missed entirely.

## Shared-database hygiene, and what it cost

The runner deletes every row it creates, in a `finally`, in reverse insertion order. It needs **two**
sweeps, which the first version of this file learned the hard way.

Sweeping by surrogate key is precise but incomplete: a row is only registered once its id resolves, so
a failure *between* the insert and the registration leaks it. The first runs leaked **32 rows** into
the shared MariaDB. All were removed with `roundtrip-leftovers.php --delete`, which matches only
fingerprints this runner writes and so cannot touch a contract fixture row. That helper is kept,
because a shared environment needs a way to check. The fingerprint sweep now runs as well, so a crash
anywhere still cleans up; a post-run check reports "No leftovers".

Per-run uniqueness is load-bearing for the same reason. `pettycash_account_movements.command_id`,
`pettycash_evidence_links.token_hash` and `pettycash_command_results.command_id` are all UNIQUE, and
all three repositories are deliberately idempotent per command id. A fixed value therefore made every
run after the first a **silent no-op** — the row was never written, and the runner then reported a row
sitting in the database since the previous run. That is the most dangerous shape a test can have: it
would have gone green while measuring nothing.

## Known limitations

- The harness covers the repositories, not the services. It proves a row can be written and read
  through its own join keys; it does not prove a workflow is atomic (T129 owns that).
- The scenarios assert linkage through surrogate keys where the aggregate carries a public UUID, and
  separately assert that the UUID is what comes back — because "it returned *something*" is exactly
  the class of bug that survived here.
- `roundtrip-leftovers.php` is an operational helper, not a test. Nothing asserts that leftovers stay
  at zero; the runner's own two sweeps are what guarantee it.

## Not repaired here, on purpose

`AuditEvent` carries `entityType` and `entityId`, and `AuditWriterService` writes both keys — but
`pettycash_transaction_audit` has **neither** column, and `DbAuditEventRepository` never writes
either, so on the transaction-audit path they are silently discarded. `T253` is open and owns exactly
this reconciliation for configuration audit; it has been extended to cover the transaction table
rather than duplicated, because the reconciliation has to be applied to the migration, the writer, the
aggregate and the data model together, and that is a decision, not a repair.
