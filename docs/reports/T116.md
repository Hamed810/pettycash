# T116 — The RTL / responsive / accessibility gate

**Status:** complete. `specs/001-pettycash-v1-core/tasks.md:761`.
`tests/Frontend/Component/RtlAccessibility.spec.ts` — 9 tests, **6 pass, 3 fail by design**.

## Why red is the deliverable

T116 is a test-*authoring* task ("Write failing RTL/responsive/accessibility tests"). A valid RED is
the finished work: tests execute, assertions execute, **0 skipped, 0 incomplete**, and every failure is
a defect in the product rather than in the gate.

That distinction is the whole point of this file, and it is stated in its own docblock: **jsdom has no
layout engine and no font metrics.** It cannot tell you whether an element overflows a 390px viewport,
it cannot compute a WCAG contrast ratio, and a computed `font-size` is always merely the declared
value. So this gate does *not* claim to verify FR-071's "≥12pt" or FR-072's browser support by
measurement, and it says so rather than asserting a proxy that means nothing.

## The three failures, and the 13 findings behind them

| Test | Findings |
|---|---|
| no physical direction properties | 7 declarations, 4 files |
| errors announced in a live region | 2 files |
| components do not pin direction | 4 files |

**Physical direction in RTL views.** `text-align: right` on `.nc-table th/td` in
`SheetDetailView:419` and `SheetListView:214`; `margin-right: 0.5rem` in `SheetDetailView:465`,
`SheetListView:267`, `TransactionDetailView:627`, `TransactionListView:207`. These are correct *by
coincidence* of the current direction, which is what makes them defects — they break the moment a block
renders LTR, and they defeat the browser's own bidi handling for mixed content.

**Unannounced error states.** `AccountView:30` and `FinanceReviewView:39` render a detached
`<p class="…__error-message">{{ error }}</p>` as an entire failed-load state, with no `role="alert"`
and no `aria-live`. Nothing associates it with anything and nothing announces it, so a screen-reader
user who triggers a communication failure is told nothing happened.

**Direction pinned inside components.** `DecisionForm:146`, `EvidenceList:48`,
`PriorDecisionHistory:94`, `RevisionInfo:97` each declare `direction: rtl` while the other review
components do not. Pinning direction duplicates the view's declaration and makes the component unusable
in the opposite direction.

## The gate is satisfiable — verified, not asserted

A test that can only fail proves nothing, so this was measured rather than claimed:

- Converting **all 7** declarations to their logical spelling turned the alignment test **green**.
- Reverting was confirmed with `diff` against `HEAD`.
- A single-declaration mutation moved the count **7 → 6**, confirming the gate detects the exact
  declaration rather than merely the file.

## Two of my assertions were wrong before the code was

Both are recorded because the wrong assertion was the more dangerous kind: it would have **demanded a
defect**.

**1. I required a breakpoint reaching 390px. The app uses the mobile-first enhancement ladder.**
`SheetDetailView` has a single-column base and adds a second, fourth and eighth column at
`width >= 480px`, `>= 768px` and `>= 1024px`. **Every one of those breakpoints is above 390px and the
view is still correct there**, because the base case is the mobile one. My check only scanned
`max-width`, so it read a correct pattern as broken. Enforcing it would have pushed authors to add dead
CSS — the meaningless-proxy failure T283 documents. Replaced with the negative claim (nothing forces
the layout wider, asserted separately) plus a check that every `@media` uses a spelling the browser
understands, since a typo silently disables an entire block.

**2. My `@media` recogniser missed the colon form.** `(max-width: 600px)` uses `:`, range syntax uses
`>=`; I accepted only the latter and flagged a correct rule. Both are now accepted.

## A false positive I removed was worse than a missing one

The live-region check keyed on the string `error-message`, so it flagged `DecisionForm.vue` — **the one
component whose comment explains that `@nextcloud/vue` 9.x has no `error-message` prop**, i.e. the file
T286 had already corrected for exactly that bug. A gate that reports its own documentation as a defect
teaches its reader to ignore it.

Comments are now stripped before scanning. `DecisionForm` is also legitimately absent for a second
reason: it delegates the message to the control's own `error` + `helperText` pair, so the library
associates the text with the input, unlike the two views that render a detached paragraph.

## What this does not do, and does not claim

- **Contrast**: asserted only that status is rendered as *text* — the half that actually excludes
  colour-only signalling (WCAG 1.4.1), and the same proxy T283 validated after removing a
  `wcag-aa-contrast` class assertion that nothing ever set. A contrast ratio needs font metrics.
- **≥12pt**: delegated to `tests/Frontend/typography.spec.ts`; asserting it here too would duplicate
  the app-wide gate for no extra signal.
- **Rendered overflow, focus trapping, announcement**: need a real browser.

**The browser-dependent matrices remain genuinely outstanding**: T122's three-browser run and T123's
manual RTL / accessibility / representative-user matrix. **T116 completing therefore does not unblock
T053**, which is gated on T116 *and* T122 *and* T123 and must not be checked until the rendered half
has actually run.
