## Why authorization ordering is the substance of the task

`contracts/exports.md` states two rules that are one rule: "export authorization is identical to
interactive view authorization", and "every report query is role-scoped **before** filtering,
aggregation, or **file generation**".

The ordering is the part that fails quietly. A service that generates a file and then declines to
return it has still written the export to disk — outside the authorization boundary, even though
nobody is shown it. For evidence that is precisely the material FR-060 protects.

So `testARefusedExportProducesNoArtifactAtAll` asserts **absence**, not just an exception: no artifact
in the store, no scratch file on disk. A test asserting only the thrown exception would pass for the
defective ordering.

## PDF is refused, not half-produced

`format: pdf` is in the contract's enum but T109 is blocked (no dependency-owned font; the only
Persian-capable font is a system font, so nothing portable is available). `generate()` refuses PDF with
the recorded reason rather than emitting a document that cannot render the contract's Persian. A
missing format is a recorded gap, not a silent empty file.

## Defects found and fixed during this task

1. **The ZIP path would have produced a valid, empty archive.** `generateZip()` passed
   `fn (): ?string => null` as the evidence reader. The archive exporter treats `null` as
   "unreadable", so *every* entry would have been omitted and the result would have been a
   well-formed ZIP with an empty manifest — exactly the "manifest that looks like evidence but is not"
   failure T110's result object exists to prevent. Fixed to read through the real `PrivateFileStore`.

2. **CSV left a copy of every export in the system temp directory.** `TransientExportStore::persist()`
   streams *out of* the scratch file and does not delete it, so the scratch's lifetime belongs to
   whoever created it — which was `generateCsv()`. Fixed with a `finally`, so a failed persist cannot
   leak either.

3. **`InMemoryPrivateFileStore::read()` returned `''` for a missing key; the real adapter throws.**
   `AppDataEvidenceStore::read()` converts `NotFoundException` into `RuntimeException`, and that is
   precisely the exception `ExportService::readEvidence()` catches to omit an unreadable member. The
   lenient double made the catch unreachable, so the "omitted rather than archived empty" guard was
   untested. The double now matches production. Only this task's test used it, so nothing else moved.

### Real-adapter evidence

The `exportservice` scenario runs in a subprocess against a real `IAppData` and a real
`AppDataEvidenceStore`, because the two claims that matter are filesystem claims:

- **The build scratch is actually removed.** Observed by diffing
  `sys_get_temp_dir()/pettycash-export-*` around a CSV generation: **no leaked file**. Only a real
  `tempnam()` file can show this; a double cannot.
- **A genuinely absent evidence key is omitted, not archived empty.** Verified against the real
  store, which throws: `absentRowCount === 0` and the archive is a valid zip with no evidence member.
- A real evidence member archived byte-identically (`real-evidence-bytes`), with the manifest's
  Persian actor name intact — read by extracting the member from the **deflated** archive, not by
  scanning the raw bytes.
- A refused purchaser export left the real exports folder byte-for-byte unchanged.

## Known limitations

- PDF export is refused, not implemented (T109, font sourcing). This is a deliberate refusal, not a
  silent gap.
- `XlsxExporter` is reached from the runner only after loading the app's `vendor/autoload.php`.
  Nextcloud core does this per app at runtime (`OC_App::registerAutoloading`), which is why the app
  works under Apache; the runner bypasses that by loading `lib/base.php` directly.
- `AppDataEvidenceStore::put()` does not strip a leading `evidence/` segment from its key the way
  `findFile()` does, so a prefixed key passed to `put()` lands at a double-prefixed path that
  `read()` cannot reach. Nothing in `lib/` calls `put()` — evidence is written through
  `putEvidence()`, which is consistent — so this is latent in an unused method, not a live defect.
  Worth a note for whoever adds the first `put()` caller.
