## Transaction strategy

One `TransactionManager::transactional()` call per mutation, containing the mutation **and** the audit
append, in that order:

```
transactional(function () {
    $before = $beforeSnapshot();      // read before the write
    $result = $mutate();
    $after  = $afterSnapshot($result);
    $audit->appendConfiguration([...]);
    return $result;
});
```

Both directions of FR-017 then hold structurally: a refused audit propagates out of the same closure
the mutation ran in, so the transaction rolls back; a mutation that throws never reaches
`appendConfiguration()`.

Emitting the audit *after* the commit would have satisfied "an audit event exists" and failed both.
Mutation **M5** moved the append outside the transaction and was killed by 12 failures.

**Nesting.** `record()` opens a transaction, so a configuration mutation called from inside another
`transactional()` would nest; Doctrine DBAL increments its counter and, without savepoints, an inner
`rollBack()` discards the whole outer transaction. That fails in the conservative direction — a refused
configuration audit inside a larger operation rolls back more than strictly necessary rather than
committing an unrecorded change. No current call path nests.

## Audit payload shape

```php
$audit->appendConfiguration([
    'id'         => Uuid::random(),
    'entity_type' => 'currency' | 'cost_center' | 'expense_type' | 'role_assignment' | 'finance_assignment',
    'entity_id'   => <natural key>,
    'event_type'  => ConfigurationEventType::…->value,
    'actor_role'  => Role::Administrator->value,
    'explanation' => $changeReason,
    'before'      => $beforeSnapshot(),     // NOT before_json
    'after'       => $afterSnapshot($r),   // NOT after_json
]);
```

Two deliberate choices:

- **`before` / `after`, never `before_json` / `after_json`.** `AuditWriterService` reads the former and
  encodes them itself; a payload spelled the latter stores the literal `"[]"` in both columns and
  discards the values permanently, because FR-053 makes audit rows append-only. That is not
  hypothetical — two real callers did it.
- **`entity_id` is the natural key** (currency `code`, cost-centre `code`, expense-type `title`,
  `FINANCE:<user>`), not `publicId`. `pettycash_currencies` has **no `public_id` column at all**, and the
  in-memory doubles mint none, so a public-id subject would be null for one resource and "sometimes
  null" everywhere — unaddressable rows.

**The payload carries no `actor_uid` and no `occurred_at`.** `AuditWriterService` resolves both from
`CurrentUser` and its own clock, and it is right to: an `actor_uid` arriving in a payload would be a
value the caller could have chosen. The `$actorUid` the services take *authorizes* the write; recording
it would make two identities indistinguishable. `actor_role` **is** passed, and only because the writer
defaults it to `PURCHASER` — otherwise every configuration change in the product would be attributed to
a purchaser.

## changeReason handling

- Threaded as a new optional `?string $changeReason = null` parameter on `CostCenterService::create()`,
  `CostCenterService::transferManager()`, `ExpenseTypeService::create()`,
  `ExpenseTypeService::updateByTitle()` and `ExpenseTypeService::deactivate()`. All are trailing
  optional parameters, so no existing caller changed.
- `FinanceAssignmentService::create()` already required it and **discarded** it; T084's report flagged
  that as limitation 2. It now reaches the audit history — verified against MariaDB: the stored events
  for `FINANCE:employee1` read `explanation` = `round trip: appointed with an open window`,
  `… revoked from the shared queue`, `… revalidated after revocation`.
- `CurrencyService::create()` / `update()` gained **no** parameter, because `CurrencyWrite` has no such
  field. Adding one would let a caller supply an explanation the contract never accepts.

## A latent test-isolation defect this task exposed

Three T084 real-database assertions failed once T086 was added. **They were wrong, not the service.**
T084's unit logic still passed 24/24.

The round-trip runner counted every `FINANCE` row belonging to `PETTYCASH_TEST_USER` — which is also the
contract suite's actor, and `seed-contract-fixtures.php` seeds it a `FINANCE` assignment of its own
(`id 196`, window `2025-08-27..2026-09-30`). So the expected totals tracked **whether the contract suite
had been seeded**, i.e. the order the suites ran in. It surfaced only because T086 changed how often the
suite runs.

The fixture row's window excludes today, so it could not have caused an extra *insert* — which is how I
established the failure was in the assertion and not in T084's logic. Fixed by scoping the count to the
public ids the run itself created. Re-running the full suite (which seeds the fixtures) confirms it is
now order-independent.

## Gaps discovered and intentionally left out of T086

1. **No cost-centre update exists.** `configuration#costCenterUpdate` is a registered route and
   `CostCenterWrite` carries a `changeReason`, but `CostCenterService` has no update method. T087's
   prerequisite table assigns `costCenterUpdate` to **T082**, which marked itself complete without one.
   **T087 cannot make that route answer real data** until the service method exists. This is the one
   thing standing between the current state and a working eleventh route.
2. **A null explanation is persisted as `''`.** `DbAuditEventRepository::rowValues()` line 377 binds
   `$event->explanation ?? ''` while every other nullable column there binds a real NULL. `''` and NULL
   are indistinguishable and neither can be told apart from "an explanation was given and it was blank".
   It is **asserted rather than worked around** so a future change cannot pass unnoticed; changing shared
   audit persistence is not this task's to do.
3. **Currency rows have no `public_id` column at all**, unlike every other configuration table. It is why
   `entity_id` uses natural keys.
4. **No contract read endpoint exists for configuration audit** — only `/transactions/{id}/audit`.
   `entity_id` is therefore written but read by nothing except `ChargedAccountScope` for `ACCOUNT_CHARGED`.
   A configuration-audit screen will need one.
5. **`CurrencyService::listForCaller()` is administrator-gated**, unlike `CostCenterService`'s and
   `ExpenseTypeService`'s listings which require only an authenticated caller. Pre-existing (T081); not
   T086's to change, and loosening a sibling's authorization would be a security decision of its own.
