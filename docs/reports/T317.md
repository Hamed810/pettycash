# T317 — Pass `X-PettyCash-Command-ID` into `TransactionService` and make both writes replay-safe

**Status:** Complete.

**Report date:** 2026-09-29

---

## Summary

`contracts/ocs-api.yaml` declares `CommandId` as `required: true` and both transaction-write operations
`$ref` it: `POST /sheets/{sheetId}/transactions` at `:436` and `PATCH /transactions/{transactionId}` at
`:466`. `TransactionController` read the header at `:56` and `:126`, echoed it through both error paths,
and then dropped it — neither service method took a `$commandId`, and `TransactionService` held no
`IdempotencyService` at all.

The header was therefore honoured on four endpoints and silently ignored on the two that create and edit
the revision FR-042 names explicitly.

## The defect, measured

The RED state was five failures, each for the right reason:

| Test | Before | Cause |
|---|---|---|
| create without header | **201** | the contract-required header was never enforced |
| update without header | **200** | same |
| replayed create | **different transaction** | a second transaction really was created |
| same id, different body | **201** | no conflict detection — it was a second create |
| replayed update | **422 stale-version** | a **second revision was written** |

The last one is the clearest evidence and the reason this mattered. `updateTransaction()` creates a new
revision on every call, so a replayed `PATCH` wrote a second `TRANSACTION_CHANGED` audit event and bumped
the version — and the retry surfaced as a confusing stale-version error rather than as a duplicate.
`expectedVersion` was not a substitute: it refuses a *concurrent* edit, but a sequential retry of a request
that already succeeded passes it, because the client resends the version it originally read.

FR-053 makes those audit rows permanent, so the duplicate was not recoverable.

## The pattern followed

`SubmitSheet::execute()`, as instructed: `transactional()`, then `execute()`, then re-read the aggregate
by public id. I checked whether the repository proved a different pattern was required; it did not. The
other three wrapped handlers each use this same shape.

Two consequences of that shape are load-bearing on a **create**, and both are easy to get wrong:

- **The id is generated inside the closure.** It was previously minted before the `transactional()` block.
  On a replay the closure never runs, so an id minted outside would be a fresh value for a row that was
  never written, and re-reading by it would return `null` for a command that in fact succeeded. The closure
  now returns the id it used, and `execute()` hands that same value back on a replay — so there is exactly
  one source for "which transaction did this command create".
- **Validation moved inside with it.** The sheet lookup, ownership check and status check now live in the
  closure, because on a replay they must not run: re-validating a command that already succeeded is how a
  replay turns into a spurious refusal.

`updateTransaction()` needed the same treatment for a stronger reason, since it creates a new revision on
every call.

## Status code for a missing header: 400, and why

The repository contained **two conflicting precedents** for the identical field error:
`SheetController::submit()` uses `validation()` (422) and `ReviewController` uses `badRequest()` (400).

I resolved it on principle rather than by picking one:

- A missing **required parameter** is a malformed request → 400. This is what `ReviewController` returns,
  and `ManagementReviewControllerTest::testRecordDecisionMissingCommandIdReturns400` already pins it.
- Invalid **body fields** stay 422. That is what this controller already returns for a missing
  `expenseDate` or `amountMinor`, and no existing behaviour changed.

So the split is by kind, not by which precedent was closer. Both operations are silent in the contract's
`responses` block, so neither status is contradicted by an artifact.

## Changes

- **`lib/Application/Expense/TransactionService.php`** — `IdempotencyService` injected; `$commandId` added
  to both signatures; both bodies wrapped; the audit events now record the real `command_id` instead of
  `null`.
- **`lib/Controller/TransactionController.php`** — both operations validate the header and forward it.
- **`lib/AppInfo/Application.php`**, **`tests/bootstrap.php`** — one DI argument each.
- **`tests/Integration/Expense/TransactionServiceUpdateTest.php`**,
  **`tests/Integration/Audit/AuditEventCoverageTest.php`**,
  **`tests/Integration/Workflow/TransactionRevisionPersistenceTest.php`** — direct constructions and call
  sites updated.

**The `command_id` correlation is the part with lasting value.** T213 had to make the column nullable
(`Version010400Date20260920000000`) because these two paths had no command id to record. They now do, so
an audit event can be correlated to the request that caused it, and the nullable column is correct for
both the wrapped and unwrapped cases rather than being a permanent workaround.

## Tests

7 new tests, all of which failed first for the stated reason:

- `PurchaserFlowControllerTest` — missing header on create (400), missing header on update (400), replayed
  create returns the original transaction, same id with a different body is 409, replayed update does not
  bump the version.
- `AuditEventCoverageTest` — `REVISION_CREATED` and `TRANSACTION_CHANGED` each carry the command id that
  produced them.

### Mutation proof

| Mutation | Caught by | Failures |
|---|---|---|
| Force `IdempotencyService`'s replay branch off | 3 replay/conflict tests | 3 |
| Remove the header validation (both sites) | 2 missing-header tests | 2 |
| Revert audit `command_id` to `null` | **initially not caught** | 0 |

The third is the one worth reporting. Setting `command_id` back to `null` left **all five T317 tests
green**, because the replay assertions prove the *write* happens once and say nothing about what the event
*records*. The two correlation tests were added specifically to close that, and the mutation was re-run and
killed. A green suite that cannot see a reverted field value is the failure mode this project has hit
repeatedly, and it was caught here only because the mutation was run at all.
