# T250 — The preflight gate runs, and reports what is actually there

**Status:** Complete. No application code touched.

## Task

`scripts/preflight.sh` exited 1 on every invocation. The task's diagnosis was exact and this task
verified every part of it rather than taking it on trust:

> the step invokes `mariadb -u"$MYSQL_USER" -p"$MYSQL_PASSWORD" "$MYSQL_DATABASE"` inside `docker-db-1`
> where `MYSQL_USER`, `MYSQL_DATABASE`, and `MYSQL_PASSWORD` are all unset — the client is called as
> `-u -p`, the server answers `ERROR 1045 (28000): Access denied for user '-p'@'localhost'`, the `|| fail`
> branch fires, and `sh scripts/preflight.sh` exits 1 on every invocation.

Measured before the fix:

```
$ sh scripts/preflight.sh; echo "exit=$?"
PHP 8.5.9 OK
Nextcloud 34.0.2 OK
ERROR 1045 (28000): Access denied for user '-p'@'localhost' (using password: NO)
preflight: read-only database inspection failed
exit=1
```

`docker exec docker-db-1 env | grep -i mysql` shows why: the official MariaDB image publishes
`MARIADB_USER`, `MARIADB_PASSWORD`, `MARIADB_ROOT_PASSWORD` and `MARIADB_DATABASE`, and **no
`MYSQL_*` variable at all**. The step asked for three variables that do not exist.

The task also says the filter "`table_name LIKE 'oc_pcash_%'` … matches 0 rows in the shared

## The prefix question belongs to T252, so the gate reports it

`T252` — still `[ ]` — owns reconciling the legacy-table premise, and it names T250 as one of the two
safety guards derived from the wrong prefix. So the fix deliberately does **not** choose a side:

```
MIGRATIONS|oc_migrations
OBSERVED|oc_pc_customers
... (11 rows)
preflight: 11 table(s) present, 1 migration table(s) present
preflight: WARNING - spec.md:333 declares the legacy tables are oc_pcash_* and none exists, while
oc_pc_* tables do; T252 owns the reconciliation
```

Both prefixes are queried and both are reported. A preflight that silently adopted one would hide the
disagreement the reconciliation exists to settle; a preflight that *failed* on it would turn a
documentation defect into a blocked build and reproduce the always-red gate this task was raised to
fix. The warning goes to stderr and does not affect the exit code.

## A gate with no test is how this broke, so the test is the deliverable

`preflight.sh` is not run by `make check`, not part of `npm run check`, and no CI configuration exists
— which is precisely why a permanently-red script looked exactly like a healthy one. `preflight.test.sh`
asserts six properties, and two of them exist to stop the test from being satisfied by a script that
does nothing:

1. exits 0 on a healthy environment;
2. `oc_migrations` appears — **the step reached the database** (a script that deleted the step passes an exit-code check);
3. `oc_pc_projects` appears — it found the *right* tables, not merely that it ran;
4. the `oc_pcash_*` warning appears — the disagreement is surfaced, not silently resolved;
5. the reported count **equals** the rows listed;
6. the database password does not appear in the output.

## Four bugs in my own test, all found by mutation

The test was written, then attacked, and the first version was wrong four separate ways. Every one
would have shipped as a passing test.

1. **`check "…" "$([ $? -eq 0 ] && echo 0 || echo 1)"`** — `$?` inside `$( )` is the *substitution's*
   status, not the command's. Every assertion was reading the exit status of the arithmetic it had
   just run, which is always 0. **Every assertion passed unconditionally.**
2. **`set -eu` aborted at the first failed probe**, so a broken gate produced an exit code and no
   explanation, and a run that died at assertion one never reported assertions two through six —
   exactly when a second problem is hiding. Now `set -u` alone, with `|| probe=$?` on each probe.
3. **The password-leak check was inverted.** Written `grep … && probe=0 || probe=1`, it passed
   *exactly when the secret leaked*. The mutation that printed the password survived. An assertion
   whose polarity is wrong is worse than no assertion, because it is indistinguishable from one that
   works.
4. **The count assertion was a lower bound.** `-ge` means "the claim accounts for the listed rows", and
   a gate printing `999` sailed through it while listing eleven. Now exact: `claimed -eq listed`.

Bug 3 and bug 4 are the same shape as the defect T250 was raised for — an assertion that cannot fail —
reproduced in the fix for it.

## Known limitations

- **Assertion 6 checks the output, not the host process table.** The fix keeps the password off the
  host command line by expanding it inside the database container, and that is *not* observable from
  the test — a value passed as `docker exec -e FOO=…` never appears in a host argument list either.
  What the assertion can prove is that the secret is not printed, which is the half that reaches a log
  or a terminal scrollback. The other half rests on reading the script.
- **The test needs `docker` and the two containers running.** It is not part of `make check` and cannot
  be: `check` runs PHP inside the container, where `docker` does not exist. It is a host-side gate,
  run directly.
- **Nothing in CI runs either script.** `.github/workflows/` does not exist; that is T239, and until it
  is built both this gate and its test are manual. That is the structural reason a permanently-red
  script went unnoticed, and it is not fixed here.
- **T252 is still open**, so the warning this gate now prints will keep printing until the artifacts
  are reconciled. That is the intended behaviour, not a bug.
- The PHP suite is byte-identical: **745 tests, 3351 assertions, 1 pre-existing failure** (T275).
