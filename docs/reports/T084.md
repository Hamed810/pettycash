## Two repository methods were unavoidable

No pre-existing lookup could serve the contract, which is why the port grew:

- `GET` needs active **and historical** rows for one role. All three existing lookups filter
  `active = true` **and** a supplied date. `findActiveByRoleAndCostCenter()` cannot return a finance row
  at all: it takes `int $costCenterId`, and a finance assignment has `cost_center_id` NULL by
  definition. → `findAllByRole(Role $role)`.
- The update-or-insert decision needs "does this user already hold the role **today**". `findAllByRole()`
  applies no date; the other three cannot see a *switched-off* row. → `findCurrentByUserAndRole()`,
  which matches on the validity window and deliberately ignores `active`.

## The two design decisions the contract forces

**`POST` is an upsert that can also revoke.** The contract declares `GET` and `POST` for this resource
and **no** `PATCH`, no `DELETE`, while `FinanceAssignmentWrite.active` is **required**. So `POST` must
add, correct *and* revoke; if it merely inserted, a finance officer could never be removed through the
approved API. This is also why no `expectedVersion` is required, unlike `CurrencyService::update()` and
`ExpenseTypeService::updateByTitle()`: there is one row per user, so two administrators converge on the
same row instead of each writing a divergent branch. Adding `PATCH` here is a contract change.

**`active` and the validity window are different questions, and are kept apart.** A window that has
*ended* is a historical claim, so re-appointment **inserts** a new row and the old one survives — that
is what makes the contract's "historical" half real. A row that is merely *inactive* is the same
assignment switched off, so it is **updated in place**; a second row would claim the officer held the
role twice over one window.

This distinction was not guessed. It arrived as a **failing test**: the first implementation used
`findActiveByUserAndRole()`, which treated a revoked row as absent, so re-appointing produced a second
row and `testAnInactiveAssignmentDoesNotBlockARevivalOfTheSameUser` failed with 2 ≠ 1.

## `changeReason` is validated and then deliberately unused

`minLength: 1` is enforced at this boundary — an empty explanation is unrecoverable once the write is
accepted. Nothing persists it: `data-model.md` gives `RoleAssignment` no reason column, and FR-017's
"explanation" belongs to the *separate configuration audit history*, which is **T086**. The parameter
looks unused because it is. **When T086 lands, this is the string it must record.**

## A latent calendar-day hazard

`valid_from` / `valid_to` are DATE columns and `isValidOn()` is inclusive of `valid_to`. Comparing a
*time of day* against midnight declares an assignment ending `2025-12-31` expired at `00:01` that day —
a whole day early. Every date this service builds is anchored at **UTC midnight on the calendar day the
clock reports**, so the in-memory and MariaDB paths agree on every boundary.
`testValidityIsEvaluatedByCalendarDayNotByTheInstantItWasAsked` pins it.

## A bug I introduced and caught

The first real-database assertion read
`($row['cost_center_id'] ?? 'absent') === null`. `??` returns its fallback for a key that is **present
and null** — precisely the value under test — so a correctly NULL `cost_center_id` reported as absent
and the assertion failed. Now `array_key_exists`. It is worth naming because the failure *looked* like a
data defect and was a test defect, and the `??`-vs-null confusion recurs in every row-reading helper in
this repository.

## Known limitations

1. **One current assignment per user is only half-holdable.** The write always converges on the single
   current row, but `pettycash_role_assignments` carries only `pettycash_role_assignments_user_active_idx`,
   a **non-unique** index on `(user_uid, role, active)`. A concurrent double-POST could still leave two
   current rows, because two writers can both read "no current row" and both insert. Closing that needs a
   unique index (e.g. partial on `(user_uid, role) WHERE active`), which is a migration and not this
   task's to add. **Flag for whoever owns the configuration schema.**
2. **`changeReason` is discarded** until T086 exists. A write accepted today records no explanation
   anywhere.
3. **Reads are gated on authentication only**, not on the administrator role. Unlike `CostCenterService`
   and `ExpenseTypeService`, this service has no purchaser-form consumer justifying an open read, but no
   artifact restricts the roster either — narrowing it would invent a requirement. The smaller claim was
   taken deliberately.
4. **No contract or HTTP test.** T079 owns the failing OCS contract tests and T087 owns the controller
   that would answer them; until both exist, T084's transport shape is verified only against the contract
   document, not over HTTP.
