## T212 — two silent data corruptions, both measured

The caller supplies a **public id** for both references. `updateTransaction()` said so — the full-edit
branch did `findByPublicId($expenseTypeTitle)` on it. The parameter was nevertheless *named*
`$expenseTypeTitle`, and the partial-edit branch then used the name.

`TransactionRevision::complete()`'s sixth parameter is `string $expenseTypeTitle`, assigned straight to
`$this->expenseTypeTitle`. So:

**1. A UUID stored as a title.** A `PATCH` that supplied a cost centre and an expense type but omitted
the description took the partial branch — which was gated on *all three* being present — and wrote the
caller's UUID into the expense-type-title column. Measured: the test asserts the title is
`'Original Expense Type'` and the code produced `88888888-8888-4888-8888-888888888888`.

**2. A new id with the previous centre's snapshot.** The partial branch took the caller's *new*
cost-centre id while reusing the *current* revision's `costCenterCode` and `costCenterName`. Measured:
`'CC-200'` expected, `'CC-100'` stored — a revision claiming to be CC-200 by id and CC-100 by name.

Both are worse than the failure they replaced, because the finance queue reads these columns and
neither value looks wrong. FR-037 requires code and name to be **snapshotted**, and a snapshot of a
different record than the one referenced is not a snapshot.

The fix resolves each reference independently and snapshots from the record it resolves.

## T211 — the behaviour was already correct; the *coverage* was not

This is the honest finding, and it is the opposite of what the task text implies.

`canReview()`'s last two branches are **byte-identical**:

```php
if ($context->actorUid === $context->ownerUid) {
    return in_array($requiredRole, $context->roles, true)
        && in_array($costCenterCode, $context->costCenterCodes, true);
}
return in_array($requiredRole, $context->roles, true)
    && in_array($costCenterCode, $context->costCenterCodes, true);
```

FR-002 *permits* self-review when role, scope and stage permission are independently held, so ownership
adds no further condition and there is deliberately no ownership check. **That is a correct rule.** The
problem is that writing it as two identical branches under a comment claiming a distinction invites the
edit that adds one — and the direction that edit naturally goes is the dangerous one: silently
forbidding self-review for exactly the multi-role user FR-002 names, and emptying every queue for a
manager who is not the owner.

**Nothing could catch that.** Every pre-existing review test either had the reviewer as the owner or
used the Finance stage, which returns before these branches. There was **no test in which a non-owner
reviewed at all.** Measured, not asserted:

| | `CanReviewTest` (new) | `AuthorizationServiceTest` (pre-existing) |
|---|---|---|
| Mutation: collapse to owner-only | **killed, 3 reported** | **GREEN** |

That row is the whole task. The new file is the missing evidence; the branch collapse is the cleanup
that makes the rule visible instead of implied.

T211's first clause — "extend `canReview()` for Correction stage" — also had the branch with **no test
at all**. It is now pinned in both directions, including that a manager with the right role *and* the
right scope still cannot correct somebody else's record, which asserts the branch's ordering as much as
its rule.

## Five errors in my own test, all found by taking the RED seriously

T212's first run errored on all seven tests — a setup failure, not a RED:

1. `ExpenseType::create()` takes three arguments; I passed six.
2. `CostCenter::create()` takes five; I passed seven.
3. The revision double has no `all()`, so the revision-count assertion used `findByTransactionId()`.
4. `save()` refuses a revision without `transactionDbId` — the NOT NULL guard working as intended.
5. Reading private properties directly instead of via `description()`, `costCenterId()` and
   `expenseTypeTitle()`.

And one that was a *false* RED rather than a noise: `TransactionRevision::draft()` takes the public id
as its first argument and stores it in the private `$id`; `publicId` is a separate column. The double's
`findByPublicId` reads it, so the immutability assertion was silently looking up nothing. Had I read a
green run as "immutability is fine", that test would have asserted nothing forever.

## Known limitations

- **T212's tests are unit-level against the in-memory doubles.** They isolate *which* branch stored
  which value, which is where the defect was, but they do not prove the endpoint refuses or accepts
  anything. A contract test for `PATCH /transactions/{id}` with a cost centre and an expense type but
  no description would pin it end to end; that needs a draft transaction fixture whose revision is
  already complete, and it is not written.
- **T211 changed no behaviour**, so the suite total moved by the new tests and by nothing else. Anyone
  reading "T211 delivered" should read it as "T211 is now *verifiable*", not as "T211 was broken".
- **`canView()` is untouched and still returns true for any actor holding any role**, regardless of
  ownership or scope. That is a broader reading of visibility than FR-003's wording suggests, and it is
  **not** T211's subject — T211 names `canReview()` only. Recorded here because it was read while
  looking, and it deserves its own task rather than a footnote.
- T213, T214, T215 remain open in the same cluster, and T215 is marked `(unrequested)`: the temporary
  Vue mocks are still present and still aliased.
