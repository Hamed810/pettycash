# T306 — Narrow an export's rows by `ExportRequest.filters`

**Status:** Complete (1 pre-existing failure unchanged)

## Task

T302 made `ExportRequest.ids` authoritative and refused an export that carried no selection. It left
the other half of the same object untouched. `ExportController::rowsForSelection()` read `filters` for
exactly one purpose — the boolean "did the caller ask for something" — so:

- a request carrying `ids` **and** `filters` received the ids, unfiltered, with nothing in the
  response saying the filter had been discarded;
- a request carrying **only** `filters` was not refused at all. It produced a `200` with
  `rowCount: 0`, `byteSize: 0` and an empty body — the T302 defect, reopened on the filter half and
  invisible, because an empty artifact is what "I was asked which sheets and I have none" looks like.

The task's own note said a `filters`-only request *was* refused. Measured, it was not. That is the
only part of the task's description that was wrong, and it is the part that mattered most.

## Part 2 — one rule, two callers, and why it is not the controller's

T309 put the closed vocabulary and its coercion in `ReportController` as private members. The obvious
way to give the export the same rule was to write it again, and that is the shape of the T307 defect:
the filter and the rows each had a private idea of the vocabulary and neither matched the other. So the
rule moved to `ReportFilterFactory` and `ReportController` was left holding only what is genuinely its
own — the fact that `filters` arrives here as a **query parameter**, and therefore as a JSON string,
which it decodes before handing the object over. `POST /exports` receives a JSON body and hands its
array over directly. The encoding differs per endpoint; the rule does not.

`testNoNameTheReportAcceptsIsUnknownToTheExport` is the guard on that. It iterates
`ReportFilterFactory::ACCEPTED_FILTERS` and asserts the export never answers "Unknown filter" for any
of them. Iterating the *constant* rather than a hand-copied list means a name added to the vocabulary
without an export test fails here, and a name removed without removing the case also fails — both
directions of the drift this class exists to prevent.

## Part 3 — `narrow()`, and why an export must not page

`ReportQuery::applyFilter()` was private, so the export could only have re-implemented it. It is now
exposed as `narrow()`, and `paginate()` is expressed in terms of it, which is what keeps the two from
becoming two definitions.

The export asks for `narrow()` rather than `paginate()` because a paged export is wrong twice at once:
`rowCount` understates the selection, and the artifact omits authorized records the caller named —
which is what FR-068 forbids outright. `testNarrowingReturnsEveryMatchingRowRatherThanAPageOfThem`
filters 250 rows down to 125 and asserts all 125 come back, because a `narrow()` that sliced to
`pageSize` would pass any test written against a handful of rows.

`narrow()` reindexes its result even when no filter is set. Psalm called that call redundant — both
callers do pass lists — so the test that covers it was rewritten to hand it a genuinely gapped array
(`array_filter` without `array_values`), which is what a caller that removed rows for its own reasons
would pass. The reindex is now a proven guarantee rather than a suppressed warning: the artifact writer
iterates by position, and a preserved gap becomes a blank line that a spreadsheet reads as a record
with no values.

## Part 4 — a filter narrows, it does not create

The two refusals now say different things, and the difference is the point:

> A 'csv' export of resource 'sheets' needs a selection: pass ids. Exporting every sheet is not
> implemented, and answering with an empty artifact would misreport it as an empty result.

> A 'csv' export of resource 'sheets' cannot be narrowed by 'filters' alone: a filter selects from a
> set of records, and passing ids is how the set is chosen. Exporting every sheet in your scope is not
> implemented, so this request is refused rather than answered with an artifact that omits the
> selection entirely.

A client author reading the first learns it sent too little; reading the second learns it sent the
wrong half of a two-part selection. Before, both produced the same `200` with `rowCount: 0`.

## Part 5 — the transaction export now carries what FR-068 asks for

FR-068 requires group exports to support "**cost center transactions**". The transaction export's rows
carried no cost centre, so `costCenterDbIds` was unanswerable and the facet was lost — the export and
the report had two different ideas of what a transaction row is, which is the drift T307 had to unpick
on the report side. The export row now carries the same six columns the transactions report carries,
read from the transaction's **own active revision** for the reason FR-028 gives (one sheet may hold
transactions for several cost centres):

```
id,ownerUid,stage,status,sheetId,createdAt,costCenterDbId,costCenterCode,expenseTypeDbId,expenseTypeTitle,amountMinor,currency
```

**This widens the artifact.** The flat `transactions` CSV's columns are not fixed by any contract
(`contracts/exports.md` fixes the complete-sheet XLSX layout, which is a different resource), and no
test pinned them, so nothing broke — but a recipient who scripted against the old six columns will see
six more. It is recorded here rather than buried because it is a deliberate change to an output, not
an internal refactor.

## Part 6 — an empty result must still name its columns

Making a filter narrow to nothing reachable created the first correct route to a zero-row artifact, and
that route produced a headerless file. `ExportService::generate()` now takes the resource's declared
columns and passes them to the CSV and XLSX writers, which emit them even with no rows:

- `ids=[sheet]` + a filter that excludes it → `200`, `rowCount: 0`, **64 bytes**: the header.
- `ids=[txn]` + `costCenterDbIds: [999999]` → `200`, `rowCount: 0`, **127 bytes**: twelve column names.

The columns are stated as constants on the controller rather than derived per request, because they
are also the vocabulary a filter is evaluated against — and a row builder that computed its own
columns and a filter that computed its own vocabulary would be the same drift, one level up.

## Part 7 — a refusal that named a filter the caller never sent

Asserting that the unanswerable-facet refusal names the *request* key exposed a real gap rather than a
test artefact. `ReportQuery::FILTER_FIELD_KEYS` is keyed by internal rule name, and two of those are
not request names: a caller sends `amountMinMinor`/`amountMaxMinor` and `from`/`to`, never
`amountRange` or `dateRange`. T310 introduced `amountRange` and the name leaked straight into the
message:

> This report cannot be filtered by `amountRange`: its rows carry `id`, `title`, …

A client is shown a twelve-name accepted-filter list and then told its filter is unavailable under a
thirteenth name that appears nowhere in it. `RULE_REQUEST_NAMES` now maps each rule to the names a
caller may have sent, and the refusal quotes **all** of them — a caller who sent `to` is not told about
`from`. The unit test drives every accepted name through a refusal and asserts the message contains
that name, so a filter added to the vocabulary without a rule here fails rather than becoming a name
the application accepts and then refuses by a name nobody sent.

### The one that survived, and what it changed

Replacing the list check in `ReportFilterFactory::fromArray()` with `if (false)` — the entire body
still in place — left the suite green. Both tests written for it asserted only that a list is
*refused*, and a list is refused either way: `array_keys(['statuses'])` is `[0]`, so the closed
vocabulary catches it and answers `Unknown filter "0"`. Both tests were satisfied by a refusal that
named an integer the caller never sent and pointed at an accepted-filter list containing their
`statuses`.

That is the T311 lesson again in a new dress: a test that asserts an outcome is not the same as a test
that identifies *which* rule produced it. Both tests now assert the shape of the refusal — that it says
"object" and "list", that it quotes what was sent, and that it does **not** say "Unknown filter" — and
the mutation is killed. `describe()` was also changed to render an array as JSON, because "not a list;
got array" tells a client nothing about what it sent.

## Known limitations

- **Enumerating a whole resource is still refused**, for `sheets` and for `transactions`. FR-068's
  "reporting periods" is the other half of the clause this task does not reach: `from`/`to` are
  honoured, but the *predefined calendar periods* — month, quarter, year — are not in the vocabulary
  and a client sending one is refused as an unknown filter. That is the safe direction and it names
  what to send instead, but it is not support. The refusal is a requirement answer, not a code answer:
  "month" is ambiguous without a definition (current calendar month? last 30 days?) and a calendar
  needs a timezone, so the choice belongs in `spec.md`, not in a controller.
- **`report`, `audit` and `evidence` still refuse any selection**, filters included. Unchanged by this
  task; the message still names the resources that work.
- **The sheet and transaction export row builders are separate from the report's**, and now agree by
  construction rather than by sharing code. A future change to a report's columns will still have to be
  made twice. Extracting a shared row projection is a larger refactor than this task, and getting it
  wrong would silently break `testEveryRowUsesOnlyTheColumnsTheReportDeclares`; the duplication is
  recorded here rather than left to be discovered.
- **A filter that matches nothing is a `200` with `rowCount: 0`**, not a refusal. This is deliberate
  and consistent with the report path, which answers `total: 0` for a genuine negative. It is
  distinguishable from the T302 defect only because the filter is now applied — an empty artifact whose
  filter was never read is no longer reachable on these resources.
- The amount bound is still unit-less minor units (T310's open item), and T275 and T267 remain open.
