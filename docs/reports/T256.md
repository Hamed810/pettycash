# T256 — Resolve a revision's amount currency from its sheet

**Status**: Complete

## Task

Stop hardcoding the currency when hydrating a revision's amount in
`DbTransactionRevisionRepository::mapRow()`, which built
`Money::of((int) $row['amount_minor'], CurrencyCode::fromString('IRR'))` under the in-code
comment `// Placeholder - would need to get from sheet`.

## Why it mattered

`pettycash_transaction_revisions.amount_minor` is stored with no currency of its own, and
FR-021 makes the sheet the authority for its transactions' currency. Assuming `IRR` meant a
10.00 USD charge stored as `1000` was read back as IRR 1000. Because `minor_unit` is itself
per-currency configuration, the same integer denotes a different real amount in every
currency, so the defect corrupted every total, finance settlement, and export derived from a
revision loaded through this repository, and contradicted the FR-040 requirement that
consumption is recorded against the account matching the sheet currency.

## Implementation

`resolveCurrencyCode()` walks the authoritative chain with the Nextcloud query builder —
`pettycash_transaction_revisions` → `pettycash_transactions` → `pettycash_sheets` →
`pettycash_currencies` — and reads `c.code`. It is anchored on **both** the revision id and the
transaction id so a row cannot be hydrated against a mismatched pair.

An unresolvable currency raises a `LogicException` naming the revision rather than falling back
to a default. That is deliberate: silently substituting a currency reintroduces exactly the
corruption this task removes, and it matches the file's existing `requireTransactionDbId()`
policy, which throws rather than write a placeholder that would orphan the row. No raw SQL and
no vendor-specific constructs were introduced, so `npm run check:portability` stays green.

## Verification detail

`TransactionController::formatRevision()` renders `amount.currency` straight from
`$rev->amount()->currency()`, so the contract test reads the value that `mapRow()` produced,
through the real repository, against real MariaDB rows. The in-memory test doubles bypass
`mapRow()` entirely, which is why this could not be covered by the existing integration suite.

## Known limitations

- The response's `amount.minorUnit` is still derived from a presentation-layer lookup table
  (`TransactionController::CURRENCY_MINOR_UNITS`). That is a separate defect owned by T266 and
  was deliberately not touched here. The new test asserts `minorUnit === 2` for USD, which the
  table happens to get right; it is a regression guard, not a fix.
- The remaining ten contract failures are unchanged and unrelated to currency resolution.

## Operational note

Apache in the shared container runs `opcache.revalidate_freq = 60`, so an edit to `lib/` is not
visible to the HTTP layer for up to a minute. The live contract tests will appear to fail
against code that is already correct during that window. This cost real debugging time during
this task and is worth remembering before concluding that a fix did not work.
