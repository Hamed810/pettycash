# T072 — Evidence revision links and removal semantics

**Status:** complete. `specs/001-pettycash-v1-core/tasks.md:544`.

## What this is

"Update evidence services so correction uploads retain originating revision links and post-submission
removal deactivates rather than deletes." Two clauses. Both were broken. The second had been broken
in a way that no existing assertion could see.

## Clause 1 — the revision link was a constant

`EvidenceService::uploadEvidence()` wrote `1` into `origin_revision_id`, with the comment:

```php
1, // revision db ID - will be enhanced with proper revision tracking
```

and `1` into the audit event's `revision_id` too. Every evidence row in the application claimed
revision 1 permanently — including rows uploaded *during a correction*, which by definition attach to a
later revision. FR-050 makes the active revision determine current information and FR-048 keeps each
revision's history intact, so which revision an item belongs to is the difference between a
reconstructable history and one that cannot say what was corrected when.

The controller compounded it: it passed `$transaction->revision()->number()` — a **sequence number** —
into a slot that needed the **database** id. Different identifier spaces, so it could only ever match a
revision by coincidence.

`uploadEvidence()` now takes `?int $originRevisionDbId` and the controller passes `revision()->dbId`.

Measured RED, before the fix — two uploads against two different revisions of one transaction:

```
Failed asserting that 1 is not identical to 1.
```

## Clause 2 — submitted evidence had its content destroyed

`EvidenceController::destroy()` called `deleteDraftEvidence()` for **every** transaction, and that
method deletes the AppData binary. The comment above the call read:

> "For simplicity, we'll deactivate in both cases - the service handles the actual file deletion for drafts"

That "for simplicity" was the defect. FR-058 requires submitted evidence to be "marked inactive rather
than physically removed and its history remains visible", and `workflow.md`'s Correction Contract
clause 6 lists "evidence history" among what must remain unchanged.

`EvidenceService::deactivateEvidence()` — the method written for exactly this case, with a full
before/after audit event — **had no callers at all**.

### Why it survived so long

The evidence *row* is deactivated either way, so a row-level assertion cannot tell a deletion from a
deactivation. Over HTTP neither can anything: `GET /evidence/{id}/content` answers `403` once the
evidence is inactive. The two states are indistinguishable through the entire API surface.

So the content assertion had to be a **unit test against the file store**
(`EvidenceRemovalContentRetentionTest`, using `InMemoryPrivateFileStore` so "the bytes are still there"
is checked by the bytes), and the **routing** is pinned separately through `deactivationReason` — which
the two service methods write differently and which `formatEvidence()` returns in the response.

## The boundary is the sheet, not the transaction

The first routing attempt keyed on `$transaction->status === TransactionStatus::Draft`. The contract
test caught it, and the reason is worth recording:

> after `POST /sheets/{id}/submit` the sheet leaves `OPEN` while the transaction still reads `DRAFT`

Submission routes the transaction to a stage without rewriting that field. A transaction-status check
therefore sends every submitted transaction down the draft path — **the original bug, restored**.

Routing is now on the sheet's status. That is also the right unit on the merits: FR-025 and FR-058 both
tie evidence removability to submission, and submission is a property of the sheet. It mirrors what
`TransactionService::deleteTransaction()` and `deleteDraftEvidence()` already ask.

An unresolved parent is treated as *not* draft. The safe reading of a failed lookup is the restrictive
one, because deleting a binary on the strength of a lookup that failed is the irreversible half of the
decision.

## A third defect, found on the way

Replaying a post-submission deactivation answered **`500 UNEXPECTED_FAILURE`**.

`deactivateEvidence()` returned the `Evidence` **object** from inside its `IdempotencyService`
closure. That service stores responses as JSON and reads them back with `json_decode(..., true)` — so a
replay produced `['evidence' => [...array...]]` and the `: Evidence` return type threw. The mapper
withholds internal messages, so it surfaced as an opaque failure on a transaction whose evidence had in
fact been deactivated correctly.

The closure now stores only the evidence id and the aggregate is re-read after the block — the same
shape T317 settled for the transaction commands.

## A test that asserted the old behaviour was updated, not bent

`EvidenceDeactivationAuditShapeTest::testDeactivationIsStillRefusedForEvidenceThatIsNotActive` asserted
that deactivating already-inactive evidence threw. That was correct under the design T213 wrote it for,
when a post-submission deactivation was treated as a one-way transition.

It is now wrong, because T318 settled `DELETE /evidence/{id}` as a **repeatable** command exempt from
`X-PettyCash-Command-ID`, and the post-submission branch is that same operation. `deactivateEvidence()`
is effect-idempotent instead: a repeat returns the stored state without re-running `deactivate()`,
which would otherwise rewrite `deactivatedAt` to the retry instant. The test now asserts *that*, with
the reasoning recorded in place.

## One contract test was removed rather than kept failing

I first wrote `testPostSubmissionRemovalIsNotTheRepeatableDraftRemoval`, asserting the submitted path
refuses a repeat while the draft path accepts one. That encodes a **design decision**, not a
requirement, and it contradicts T318. It was replaced with
`testPostSubmissionRemovalIsRepeatableWithoutRerecordingTheDeactivation`, which asserts what HTTP can
actually see, and the content difference moved to the unit test.

| Mutation | Killed by |
|---|---|
| restore `origin_revision_id` to the constant `1` | `testAnUploadIsLinkedToTheRevisionItWasUploadedAgainst` |
| force the draft branch for every transaction | `testTheRecordedReasonShowsWhichRemovalActuallyHappened` |

**One mutation initially survived, and it was a hole in my tests.** Forcing the draft branch for every
transaction left the suite green: the unit test calls each service method directly, so it never
exercises the *wiring*, and no contract test could see the file. `testTheRecordedReasonShowsWhichRemovalActuallyHappened`
was added to close it, using `deactivationReason` as the observable.

## Known limitations

- `deactivateEvidence()` still records `sheet_id => null` in its audit event; the service holds no
  sheet repository. Pre-existing and documented in the T213 report, unchanged here.
- The evidence predicate now trusts `transaction_id` (widened in the correction work against
  `data-model.md:248`). If that was meant to be revision-scoped, the model needs amending, not the code.
- `testGetEvidenceContentReturns200WithStream` remains red.
- `ResubmitCorrection.php:135` still has an undefined `$explanation`; unrelated and untouched.
