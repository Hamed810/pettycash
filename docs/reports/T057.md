## What T057 asked for, and what it turned out to be

T057 asked for contract tests over the shared finance queue and the finance decision responses. The
tests are the deliverable; the finding is that the finance approval path **had never worked over HTTP
at all**, and three separate defects stood between a finance officer and a settlement.

## The four defects, and how each was proven

Each was found by the new tests, not by inspection, and each was then proven load-bearing by a
mutation that was verified to have applied before its result was read.

### 1. No workflow decision was ever persisted

`ManagementReviewService::recordDecision()` and `FinanceSettlementService::recordDecision()` each
carried a `// Persist transaction and decision` comment directly above
`$this->transactionRepository->save($transaction)`. That adapter writes the transaction row and
nothing else. `DbWorkflowDecisionRepository` was registered in `Application.php`, injected into
`TransactionPayloadFormatter` for reads, and **never called for a write by any code path in `lib/`**.

The transaction's status therefore advanced while `pettycash_workflow_decisions` stayed empty at every
stage of the workflow, and the audit event's `decision_id` was the `null` an unpersisted aggregate
carries. FR-043's transaction history and FR-036's decision trail were unreachable through the
application, and only the fixture rows made any contract assertion about them pass.

Both services now persist the decision through the domain port, **before** the audit event so the
event's `decision_id` is a real surrogate key.

*Mutation*: removing the save fails **9** of the 21.

### 2. A finance approval answered 422 for every input

`DbAccountMovementRepository::save()` resolves the movement's `source_decision_id` from the decision's
public UUID, and the consumption was recorded *before* the decision was saved, so the resolution ran
against a decision that did not exist. With the save restored, a second defect appeared underneath it:

```
SQLSTATE[22001]: String data, right truncated: 1406 Data too long for column 'public_id'
```

`PettyCashAccount::consume()` built the movement's public id as `$this->id . '-' . $commandId` — 73
characters for two UUIDs, in a column of 36. Every charge had the same construction, so the unbuilt
`account#charge` endpoint (T063) would have failed identically. A UUID is minted instead; the command id
is stored in its own column, which is what a replay already looks up.

*Mutation*: restoring the composed id fails **9** of the 21.

### 3. The decision response was not a `DecisionResult`

`contracts/ocs-api.yaml:507-511` answers the decisions endpoint with the decision that was recorded,
the transaction it was recorded on, and `accountMutation`. The controller answered with a bare
`TransactionDetail`, so the decision just taken was absent from the response and so was the money that
moved. The frontend was already written against `DecisionResult`: `src/stores/reviews.ts:93` reads
`result.transaction`, so the finance review view replaced the transaction it was showing with
`undefined` after every decision.

Both services now return a `DecisionOutcome`; the controller builds the contract's shape and omits
`accountMutation` for a reject, a return and every non-finance stage, rather than emitting an empty
mutation that would claim money moved when none did.

*Mutation*: dropping `accountMutation` fails **3**.

### 4. A replayed finance decision was answered 409

The idempotency payload included the workflow stage, and the controller routes a decision by the
transaction's **current** stage — which the first attempt has already advanced. A client retrying
after a timeout therefore hashed a different payload and was told `Command ID was already used with a
different payload`, i.e. that its command had been reused for different work, when it had in fact been
applied. The stage is not part of what a command means; the transaction and the decision are, and both
remain in the payload, so a genuine reuse is still a conflict.

*Mutation*: restoring the stage fails **1** (the replay test).

## Two smaller ones

- `ReviewController::fieldErrorsFor()` matched `'explanation'` with `str_contains` against messages
  that begin with a capital "Explanation required for reject or return". The match is case-sensitive,
  so the one field error it exists to attach never fired and a missing explanation came back as a bare
  422 with a sentence and no field to highlight. *Mutation*: `str_contains` fails **1**.
- `ExpenseTransaction::applyDecision()`'s finance branch set the status and the final outcome but never
  advanced the stage, so a settled transaction reported `stage: FINANCE` beside
  `status: COMPLETED_APPROVED` — decided while still saying it awaits the decision — and
  `recalculateStatusFrom()` orders `FINANCE` before `FINAL`, so a sheet of decided transactions could
  not be told from one still in review. The cost-centre and senior branches already advanced it.
  *Mutation*: dropping `stage = Final` fails **1**.

## The fixture lies this pass had to remove

Two of them, and both were the seeder's fault rather than the code's.

**The finance queue was never observable.** `ManagementReviewControllerTest::testFinanceQueueReturns200WithPagedTransactions`
asserted 200 against a fixture in which no transaction awaited finance review. An empty queue
satisfies a shared queue, a per-cost-center queue and a broken one equally, so the assertion proved
nothing about the property FR-034 names. The new `finance` state seeds three transactions at the
finance stage, each carrying a different claim, and the acting user is granted a `FINANCE` role scoped
to no cost center — in that state only, because a role gate cannot be tested by a fixture that always
passes it.

**The ledger claimed a settlement that had not happened.** The seeded consumption named the *working*
revision. `pettycash_account_movements_consumption_uniq` is unique on `source_revision_id` — which is
what makes FR-040's "exactly one consumption" an enforced fact, and which also means a revision the
ledger already claims can never be settled. The finance approval failed on a duplicate key, and the
only honest reading of that fixture was a ledger row standing in for a settlement that had not
happened. The settled expense is now its own sheet, transaction and revision at `FINAL`, out of every
queue, and the seeder deletes settlement-written movements on every state so the ledger does not depend
on whether the finance suite ran first.

A third fixture fact worth knowing: **a seeder failure is silent.** The `finance` state produced no
manifest and exit 0, and `ContractFixtures` reports that as "seeding produced no output" rather than as
a schema error. The cause was a `created_by` column on `pettycash_sheets` that the table does not
have. The seeder's own comment already records this failure mode; it cost time again.

## Known limitations

- **A replayed finance decision does not report `accountMutation`** (T290). The decision and the
  transaction are correct and nothing is spent twice, but the stored command result predates the
  member, so the reply of a retry omits the account effect.
- **The account/movement projection now exists in two places** (T289). `AccountService` still builds
  both arrays inline because making it delegate to `AccountPayloadFormatter` would invert the layer
  dependency. The formatter's docblock records this so the duplication does not read as an accident.
- **`scripts/dev/phpunit` writes one row per settlement into `pettycash_command_results`** and nothing
  prunes it. Not a defect, and not a task: the growth is bounded by the number of decisions taken.
