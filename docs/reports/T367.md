# T367 — Resolve rows for `resource: evidence` and `resource: audit`

**Status:** delivered
**Task:** `specs/001-pettycash-v1-core/tasks.md` T367 (Phase 58)
**Date:** 2026-10-06
**Layers touched:** Application (`lib/Application/Reporting/`), Presentation (`lib/Controller/`),
wiring (`lib/AppInfo/Application.php`), tests.

---

## What the task asked for

`POST /exports` answered **422 unconditionally** for `resource: evidence` and `resource: audit` — in the
selected case *and* the unselected one — so no request shape produced an artifact for two resources the
contract declares (`ocs-api.yaml:1322` enum: `sheet, sheets, transactions, report, audit, evidence`) and
the client offers (`src/types/reporting.ts` maps `evidence: ['csv','zip']`, `audit: ['csv','xlsx','pdf']`).
Because `ExportController` passed a literal `[]` for the archive entries and nothing in the application
constructed an `EvidenceArchiveEntry`, `generateZip()` was unreachable and removing the refusal alone
would have produced "a valid, empty ZIP with an empty manifest".

## The finding that reshaped the task

**The row producers already existed.** `ReportController::evidenceReport()` and `::auditReport()` were
built and tested for `GET /reports/{reportType}`, and `ReportQuery::SUPPORTED_TYPES` already listed both
types. So the work was *not* to write two row producers — it was to stop refusing them.

Copying them into `ExportController` would have put one scope rule in two places. That is the T307 shape
this repository has been bitten by repeatedly, and `ReportController::__construct()`'s own docblock
records the precedent: `ReportFilterFactory` was moved out of that controller for exactly this reason —
"a filter name that meant one thing here and another there is the T307 shape again".

Both producers now live in `EvidenceSelectionQuery` and `AuditSelectionQuery` (Application layer) and
**both controllers call them**.

## What was genuinely new

`EvidenceArchiveEntry` needed four facts the evidence row does not carry — revision number, sheet public
id, sheet title, uploader display name — resolved by joining evidence → transaction → revision and
→ sheet, plus a directory lookup.

That is why the entry producer lives in the **query**, not the report: the report pages over up to
`BOUND` rows and would pay those lookups per row for columns FR-064 does not ask it for, whereas an
export resolves a bounded set of named ids.

## Three findings worth keeping

### 1. A hand-written positional DI list answered an empty `200`

`Application.php` builds both controllers by hand — `registerService(ReportController::class, fn => new
ReportController(...))` — so adding two constructor parameters without adding them to those lists
**shifted every later argument along**. Position 7 received `ExpenseSheetRepository`, the container
handed `ExportController` a `DbExpenseSheetRepository` where it declared `EvidenceSelectionQuery`, and
**every export answered an empty `200`** whose only trace was a TypeError in `nextcloud.log`.

Two diagnoses came first and were both wrong:

- *"Nextcloud's container falls back to resolving by parameter name and guessed."* Refuted by querying the
  booted app directly: `EvidenceSelectionQuery` resolved correctly by type; `evidenceSelection` by name
  correctly threw `QueryNotFoundException`.
- *"`readonly` classes break PHP 8.5 lazy ghosts."* Refuted by removing `readonly` and re-testing.

The real cause was visible in `Application.php:592-624` once I read it instead of the container.

This is the repository's own lesson applied to a new case: **how the code is loaded** is a correspondence
no suite asserts — and here it was an argument list maintained by hand.

### 2. `array_filter()` against a two-argument predicate → `ArgumentCountError` → 500

The scope predicates are `callable(row, scope)` — the shape `ReportQuery::paginate()` calls them with —
so handing one straight to `array_filter()` (one argument) raised from inside the closure. Found only by
reading `nextcloud.log` for the actual exception; the response body said `pettycash.error.unexpected` and
nothing more. Fixed with `scopedRows()`.

### 3. Filtering by id silently dropped unresolvable ids — worse than a refusal

The first implementation filtered rows to the caller's ids. A caller naming three audit events, one of
which is not theirs, would have received a well-formed artifact carrying **two**, with `rowCount: 2` and
nothing anywhere saying the third was dropped.

That is T302's "accepted and discarded" in its row form, and it is worse than a refusal because the
number looks *measured*. `narrowToNamedIds()` now accounts for every named id and refuses otherwise.
A **missing id and a foreign id give the same answer**, so a caller cannot probe for the existence of
records they may not see (FR-003).

## The empty-manifest guard, and where it had to live

`ExportService::generateZip()` now refuses an empty entry list *before* building. The placement is the
point, and the code says why: downstream of `build()`, an empty entry list and an archive whose members
all failed to read are **the same object**, so refusing there would also refuse a real selection whose
files were unreadable — a different answer, and the wrong one.

## Verification over HTTP, on the deployed app

| Request | Before | After |
|---|---|---|
| `resource=sheets, fileFormat=csv` | `200` | `200` (unchanged) |
| `resource=audit, fileFormat=csv` | **`422`** | **`200`** |
| `resource=evidence, fileFormat=csv` | **`422`** | **`200`** |
| `resource=evidence, fileFormat=zip` + ids | **`422`** | **`200`**, a real archive |
| `resource=evidence, fileFormat=zip`, no ids | `422` | `422` ("needs a selection") |
| `resource=report, fileFormat=csv` | `422` | `422` (still no projection) |

**The ZIP is opened and read back, not trusted from its status code** — the failure being guarded against
is an archive that is well-formed and empty. `PK` magic asserted, manifest member present, exactly one
non-manifest member, and that member's bytes asserted to contain the uploaded content. The manifest name
comes from `EvidenceArchiveExporter::MANIFEST_NAME` rather than a literal, so a rename cannot make the
test count the manifest as an evidence file.

**Mutation-verified in the direction T367 names.** Replacing the entry call with a literal `[]` — the
exact shape of the empty-manifest defect — turns the archive test **RED** with the guard's own message:
*"A 'zip' export needs the evidence entries to archive; none were resolved."*

## One existing test rewritten, not deleted

`testAResourceWithNoRowSourceIsRefusedRatherThanAnsweredWithAnEmptyArtifact` asserted that `report`,
`audit` **and** `evidence` all refuse. Two of those three now answer, so keeping the assertion would pin
this task's own defect in place. It now covers `report` alone — still the one resource with no projection
— and a companion test asserts the other direction. Asserting symmetry across all three would fail on
correct work, the same mistake Phase 36 recorded for a different file.

## Not done, recorded rather than implied

- **T366 stays open.** This task made `generateZip()` reachable, which closes the shared root cause T366
  named, but T366's own defect — `completeSheet()` having no caller, needing six real projections per
  sheet — was not touched.
- **FR-074's oversized-file refusal is not covered at the endpoint.** The ceiling is asserted through the
  exporter's real constant and the endpoint is asserted to hand it real entries, but an endpoint-level
  oversized fixture would need a >100 MB upload. T110's unit tests still carry that path.
- **`SELECTION_BOUND` is 1000**, applying to the unselected enumeration case only; a named selection is
  resolved id by id and is not bounded by it.
- **`pdf` remains refused** by the pre-existing `pdfUnavailableReason`, pending T109's font work — so the
  client's `audit: ['csv','xlsx','pdf']` offer is answerable for csv/xlsx only.
