## The defect, as found

`TransactionController::audit()` returned `new DataResponse($formatted)` where `$formatted` was a
flat `array_map` list. `contracts/ocs-api.yaml:581` declares the operation's `200` as
`#/components/responses/AuditPage`, which at `:913-922` is `PageMeta` — `page`, `pageSize`, `total`,
all `required` — plus `items`. Every one of those keys was absent, and `:574-575` declared `Page` and
`PageSize` that reached no code.

The endpoint was owner-only via `TransactionService::getTransaction()`. **That is T093's**, not this
task's, and was not touched.

## Three design decisions worth stating

### 1. `PageBounds`, not a third copy of the bounds

The contract declares `Page`/`PageSize` **once**, in `components/parameters` (`:766-772`), and
`$ref`s them into every paged operation. They are one rule with many call sites — which is exactly
how this defect happened twice already: T106 records the report surface returning `items`/`offset`
where the contract says `PageMeta`, and T319 is the same failure on the audit page.

`ReportFilter` already encodes these numbers. It was **left alone**, because it carries a dozen
report-specific filters (date range, status, currency, cost centre, actor, event type, amount
bounds) that mean nothing to an audit page — sharing its numbers is right, sharing the class is not.
`PageBoundsTest` asserts the two agree on every bound *and* on the refuse/clamp behaviour of each
out-of-range request, so the extraction cannot quietly become a fork.

### 2. `total` counted in the database, and why `count($items)` is the trap

`findByTransactionId()` is bounded by `setMaxResults`, so its return value can only describe the
window it was given. `countByTransactionId()` was added to the port and counts with a predicate
identical to the find's — a count filtered slightly differently from the read it describes is worse
than no count, because it looks authoritative and is not.

`count($items)` was mutation-tested and is caught, but it is the failure that matters here: it
produces a response carrying **all four required keys**, answering **200**, while telling a paginated
client the history ends at the end of page 1. US6/AC1 requires every official event to be reachable,
so that field is what makes the rest reachable.

### 3. `page`/`pageSize` are nullable, not `int`

Per T225: the AppFramework `Dispatcher` coerces an absent query parameter to `null` and would throw
an unhandled `TypeError` *before* the method body runs — a `400` with an empty body and no `ocs`
envelope, which is the exact failure T225 removed from this same controller. Absence is resolved
inside the body, where `PageBounds` applies the contract's own defaults.

## What was deliberately not done

- **Authorization is untouched.** The endpoint stays owner-only. Correcting it is `AuditQueryService`'s
  work (T093); widening the gate here would put a second, divergent authorization decision in the
  controller.
- **`GET /transactions/{id}/revisions` is untouched, and now guarded.** It has the identical
  bare-array shape and is **correct** — `:567` declares a plain `Revision` array with no `PageMeta`.
  `testTheRevisionsEndpointStillReturnsABareArray` exists so "make the audit page conform" cannot
  slide into "make every list conform". Wrapping it was mutation-tested and fails that test.
- **No contract was amended.** The contract was right; the code was wrong. That is the whole task.
- **`testListAuditReturns200WithAuditPage` was left passing and still asserts only the status.** It
  was left as-is on purpose rather than edited into passing — it is the evidence for *why* the gap
  read as covered, and the four new tests read `ocs.data` where it stops at `ocs.meta`.

The 5 unit failures were the missing `countByTransactionId()` method itself.

**One authored test was wrong on its first run.** The paging walk asserted `total >= 1` and passed
against a fixture that seeds **no** audit rows — the walk saw nothing and "passed" vacuously. Fixed by

`pettycash_transaction_audit` rows, so a test depending on them proves nothing and one depending on a
prior suite's writes is order-dependent — the failure the fixture exists to remove, stated the same
way at `ReportAndExportControllerTest:36-43`.

**One production file was updated for a test failure, deliberately.** `RetentionPolicyTest` asserts
the audit port's exact method list as data. Adding `countByTransactionId()` broke it. The list was
updated with a note explaining why a read was added — that test's stated purpose is to make growing
an append-only port a *visible, deliberate act*, and the diff is exactly that.

### Mutations, all killed

| Mutation | Killed by |
|----------|-----------|
| `count($items)` as `total` | `testPagingTheAuditWindowReachesEveryEventExactlyOnce` (`1 is not >= 3`) |
| ignore `page` (offset hardcoded to 0) | `testPagingTheAuditWindowReachesEveryEventExactlyOnce` |
| revert to the bare `array_map` response | all 4 new contract tests |
| offset from the *requested* page size, not the clamped one | `PageBoundsTest::testTheOffsetFollowsTheClampedPageSizeRatherThanTheRequestedOne` (`5000 !== 100`) |
| `pageSize < 1` clamped instead of refused | `PageBoundsTest::testAPageSizeBelowTheMinimumIsRefused` + the agreement test |
| wrap the **revisions** response in `PageMeta` | `testTheRevisionsEndpointStillReturnsABareArray` |

The offset mutation is the subtle one: `page=2&pageSize=5000` must start at offset 100. Computing it
from the requested size starts at 5000 — past the end of most result sets — so the endpoint answers
200 with an empty page and a `total` saying there is more.

## Known limitations

- The transaction audit page is still owner-only; T093 owns that correction.
- Ordering is still newest-first (`orderBy('occurred_at', 'DESC')`), unchanged. US6/AC1 says
  "chronological order", which reads as oldest-first. Preserved deliberately: changing it alters
  existing behavior beyond this task's scope, and a client written against today's output would see
  its history reorder. **Worth a maintainer decision** — flagged, not decided here.
- `testGetEvidenceContentReturns200WithStream` remains red. Pre-existing, unrelated, needs its own
  task.
