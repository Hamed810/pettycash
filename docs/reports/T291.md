# T291 — the FR-015 charge actor gate, and the provisioning decision that is left

**Task**: T291 (partly advanced; still open)
**Feature**: PettyCash V1 Core Workflow (`specs/001-pettycash-v1-core`)
**Date**: 2026-09-27
**Follows**: `docs/reports/T289.md` (one definition of the account payload shapes)

## What the task asked for

T063 implemented FR-015's actor gate — only `FINANCE` or an administrator may charge an account — and
**removing it fails nothing**. The task diagnosed why: the contract suite's single credential is a
finance officer, so no request in it can be one the rule refuses. It named the missing piece as *a
second acting identity holding no `FINANCE` role, authenticated as that user*, and classified that as
a harness gap belonging with the other multi-identity work rather than something to assert around.

## What was done

The rule is covered where it can fail.
`tests/Integration/Account/AccountChargeAuthorizationTest.php` (7 tests, 14 assertions) exercises
`AccountService::charge()` — the method the gate is written in — with an arbitrary actor uid and an
arbitrary set of role assignments:

| Test | What it holds |
|---|---|
| `testAnActorWithNoFinanceRoleIsRefused` | the refusal, by an actor who **owns the account** and holds no role |
| `testARefusedChargeRecordsNothingAndLeavesTheBalanceAlone` | the refusal is atomic: no movement, balance untouched |
| `testAFinanceOfficerMayCharge` | the first permission the rule grants, and the control for the refusal |
| `testAnAdministratorMayCharge` | the **second** permission, which a refusal-only test would not notice losing |
| `testAManagerRoleIsNotEnoughToCharge` | a different real role is still a refusal |
| `testAnExpiredFinanceRoleIsRefused` | an effective-dated role that has ended is not a permission |
| `testAFinanceRoleThatIsNotYetEffectiveIsRefused` | one that has not started is not a permission either |

The two permission tests exist because a gate that refused *everybody* would satisfy the refusal test
perfectly — the failure mode
`AccountControllerTest::testTheCallersOwnSecondAccountIsStillReadable` exists to rule out for the
ownership check, repeated here for the role check. The manager-role test exists because a gate written
as "does this actor have any role" passes all four others.

## Mutation checks

| Mutation | Result |
|---|---|
| Remove the FR-015 gate entirely | fails **5** |
| Drop only the administrator branch | fails **1** (`testAnAdministratorMayCharge`) |
| Ignore the effective-date window when resolving roles | fails **2** (expired, not-yet-effective) |
| Make `hasRole()` stop requiring `$assignment->active` | **passes — see below** |

All mutations were reverted and the suite re-run green.

## The one thing not covered, and why that is correct

`AccountService::hasRole()` tests `$assignment->active` as well as `$assignment->role`. Mutation 4
shows no test reaches it, and that is not a gap: it is unreachable **through the port**.
`DbRoleAssignmentRepository::findActiveByUserUid()` filters `active = true` in SQL, and
`RoleAssignment::isValidOn()` returns false for an inactive assignment, so the double filters it too.
A test of the third check would be a test of a double violating its own contract, which measures the
double rather than the product.

The effective window *is* covered, and it is a different thing — mutations 3 and 4 are different
mutations, and the window one fails two tests while the `active` one fails none.

## What is still open, and why it was not simply written

The endpoint-level half: whether `POST /accounts/{id}/charges` answers **403** to a caller without the
role, over real HTTP, as a real second identity. This is genuinely unblocked by code:

- `OcsTestClient::create()` reads exactly one credential pair from `getenv()`.
- `.env.testing` is gitignored, so a second credential cannot be committed — the suite would depend on
  a local provisioning step.
- Authenticating as a second user means minting an app password against the **shared** Nextcloud
  container (`occ user:auth-tokens:add`), and deciding *which* existing user is the non-finance actor.

That last point is a maintainer decision rather than an implementation detail, and per `AGENTS.md` a
shared-environment write needs approval. It is the same single-identity limit that blocks `T171` and
the Playwright chain (F5 in the Phase 38 findings), so the decision should be made once for all of
them.

The `AccountWriteControllerTest` charge refusals that do exist — a stale version, an unknown account, a
missing command id — all reach the same `OcsErrorMapper::forbidden()` arm, so the 403 mapping itself is
already exercised; what is missing is a refusal that arrives through the *actor* gate.

## One correction made along the way

`tests/Contract/Fixture/seed-contract-fixtures.php` headed its `FINANCE` grant with "granted only in
the `finance` state" and then said, two paragraphs later, that it is not withdrawn in the other states
and does not have to be. The code grants it **unconditionally**.

This is the comment a reader of T291 most needs to be right about, because the whole task exists
because a fixture that always passes a role gate makes the gate's refusals unobservable — and the
comment claimed the opposite shape. Corrected to state the grant is unconditional, and to say why that
is precisely why this gate is covered in-process rather than over HTTP. The true and useful part of
the original comment — that `canReview()` resolves the required role from the transaction's own stage,
so holding `FINANCE` changes nothing about a cost-centre or senior decision, which is why the grant
need not be state-scoped — is kept.
