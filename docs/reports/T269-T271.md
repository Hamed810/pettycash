# T269, T270, T271 — Decision endpoint contract conformance

**Status**: Complete (all three)

These three defects sat in one method, `ReviewController::decide()`, and were completed in a single
implementation pass because fixing one exposed the next.

## T269 — the caller's command id was discarded

`decide()` did `$commandId = (string)Uuid::random()` instead of reading the
`X-PettyCash-Command-ID` header. Minting a fresh UUID per request means `IdempotencyService` can
never match a replay, so:

- a replayed decision is recorded a second time, with a second immutable `WorkflowDecision` and a
  second business audit event;
- the `pettycash_workflow_decisions` unique index on `command_id` can never fire;
- on the finance path this endpoint is the entry point to settlement.

`contracts/workflow.md` line 15 and `research.md` Decision 7 both make the client-generated UUID
the idempotency guarantee.

Fixed by reading the header the way `TransactionController::decide()` already does.

### Why 400 and not 422 for a missing header

`testRecordDecisionMissingCommandIdReturns400` asserts 400, and T269 states 400. That is also the
right distinction: a request that never carried a required header is **malformed** (400), whereas a
header that is present but unacceptable is **invalid** (422). `OcsErrorMapper::badRequest()` was
added for this so the response still carries the `Error` schema — `code`, `message`, `fieldErrors`,
`commandId` — and the typed frontend client reads both shapes identically.

Note the small tension this exposes: `contracts/ocs-api.yaml` lists only 201, 403, 409, and 422 for
`POST /transactions/{id}/decisions` and declares no 400. The contract is not wrong about 422, but it
is incomplete about 400. Left for T124's contract validation to reconcile rather than edited here.

## T270 — `\ValueError` escaped the `Exception` handlers

`Decision::from($decision)` is a backed-enum lookup that raises `\ValueError`, which extends
`\Error`, not `\Exception`. The three handlers never saw it and the caller got 500 instead of a
validation error.

Fixed by isolating the enum lookup in its own `try` that catches `\ValueError` and returns 422 with
a `VALIDATION_FAILED` code and a `decision` field error, and by ending the main handler in
`catch (\Throwable $e)` through `OcsErrorMapper::map()`.

The same latent defect was fixed where the task recorded it, and in two places it did not:

| Location | Before | After |
|---|---|---|
| `ReviewController::decide()` | `catch (Exception)` ×3 | `\ValueError` handled; `catch (\Throwable)` |
| `QueueController::index()` | `catch (Exception)` around `WorkflowStage::from()` | `catch (\ValueError\|\TypeError)` |
| `ReviewController::index()` | `catch (Exception)` → bare 400 | `catch (\Throwable)` → mapper |
| `ReviewController::returns()` | `catch (Exception)` → bare 400 | `catch (\Throwable)` → mapper |

The last two were not named in any task; they had the same bypass and were fixed in the same pass
rather than left to be rediscovered.

## T271 — validation failures bypassed the error mapper

`InvalidArgumentException` produced `new DataResponse(['error' => $e->getMessage()], 400)` — no
stable code, no field errors, contradicting `contracts/workflow.md` line 79.

Now routed through `OcsErrorMapper::validation()`. A new `fieldErrorsFor()` helper attaches the
offending field by matching the service message, so the caller gets `explanation`,
`expectedVersion`, or `stage` rather than only a sentence. A blank `decision` is also validated up
front through the mapper, matching `TransactionController::decide()`.

## Known limitations

- `ReviewController::decide()` still derives the target service from the transaction's current
  stage rather than from an explicit stage parameter, so a client cannot state which stage it
  believes it is deciding. That is a design question the contract does not settle, and no task
  raises it.
- `getMinorUnit()` in this controller remains a hardcoded presentation-layer currency table
  (T266). It was left untouched; the new tests do not depend on it.
