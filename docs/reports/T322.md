# T322 — The E2E account had no data, and the contract seeder destroyed it when given one

**Status:** complete. `specs/001-pettycash-v1-core/tasks.md`. `tests/E2E/seed-e2e-fixtures.php`.

## The defect

`seed-contract-fixtures.php` pins every fixture identifier in a `const FIXTURE_IDS` array (line 90:
`11111111-…` through `99999999-…`). It is a **single-user** fixture set by construction. Running it for a
second user does not create a second set — it **overwrites the first**, because both users end up
owning the same `public_id`s.

Measured sequence: seeding `pettycash-e2e` reported success and `GET /accounts` answered `total: 2`; a
later `scripts/dev/phpunit` run re-seeded `employee1`; the e2e account's accounts were **gone**, and the
sheet form rendered `sheets.noAccounts` with the account `NcSelect` disabled
(`:disabled="loadingAccounts || !hasAccounts"`, `SheetFormView.vue:176`).

I also caused this collision myself mid-session, which is how it was found: I seeded the e2e user,
overwrote `employee1`'s fixtures, reported the e2e account as having "2 accounts" without noticing those
were `employee1`'s own rows, and had to re-seed to restore the contract suite. The number was right and
the meaning was wrong.

## The fix, and why it is a separate seeder

`tests/E2E/seed-e2e-fixtures.php`, with its own namespace — `e2e00000-…`, a visibly different shape from
`11111111-…` so any row's owning suite is identifiable at a glance. It seeds a currency, cost centre,
expense type, account, two role assignments and a draft sheet.

**Not a parameter of the contract seeder.** Two suites writing overlapping rows *is* the bug. `T278`
already made the contract seeder a true reset for the contract suite's benefit; parameterising its IDs
would put the two one `git grep` from colliding again, and the collision is silent — both runs "succeed".

### Isolation is asserted, not intended

`assertDoesNotDisturbOtherUsers()` snapshots every row outside `E2E_IDS` before and after, and exits
non-zero naming the offender. Mutation-verified: modifying a foreign account in place produced

```
This seeder must not touch rows outside its own ID namespace, but it changed:
  pettycash_accounts:44444444-4444-4444-8444-444444444444
```

`otherUsersUntouched: true` is a claim the seeder **checks**, not one it prints.

## The failure mode that mattered most

The first version compared `public_id` + `updated_at`. **`pettycash_sheets` has no `updated_at` column.**
The resulting `DbalException` was swallowed by Nextcloud's CLI error handler, which logged it to
`nextcloud.log` and **terminated with status 0** — every run reported success, printed nothing, and
wrote no rows. The only way to find out was to read the server's log by hand.

Two more schema errors surfaced the same way once visible: `pettycash_sheets` has `status` (not `state`)
and `lock_version` (not `version`); `pettycash_expense_types` has **no `code` and no validity dates**,
which also made the `E2E-` code prefix I had written unnecessary for expense types — though still
required for cost centres, where `code` is unique and the contract seeder owns `CC-100`.

So the columns were read out of the schema, not assumed. And the snapshot carries the **owner** column
per table (`owner_uid`/`user_uid`) plus `lock_version`, because `public_id` alone would not have caught
the bug even had it worked: the collision *re-owned* existing rows, changing the owner while leaving the
key and row count untouched.

### The lasting change

A top-level `try`/`catch` plus a `set_error_handler` that promotes warnings, so the seeder reports
class, message and origin and exits 1. **It cannot exit 0 having done nothing** — the only property that
matters for a fixture, since a seeder that fails open turns every downstream test into a misleading
"missing record" instead of a setup error.

It earned its keep on the first run: `TypeError: Return value must be of type int, string returned`,
because Nextcloud's `IQueryBuilder::PARAM_STR` is a *string* constant and my closure declared `: int`.

## Verification

- Seeder idempotent (re-run reports the same ids); `otherUsersUntouched: true`
- **Collision empirically gone**: after seeding, re-running the contract seeder for `employee1` leaves
  the e2e account intact; both users' accounts coexist
- Isolation guard mutation-verified (exit 1, names the row)
- `scripts/dev/phpunit` 875 tests / 4010 assertions / **1 failure** — T275's pre-existing one, unchanged
- `npm run test:unit` **237/237** (T323–T325 in the same pass took this from 234/237)

## What this does not deliver

The Playwright suite still fails, and the remaining failures are **T171's**, not this task's. The suite
now gets past the account `NcSelect` — previously disabled because the e2e user had no accounts — and
fails later, on `sheet-list-item` not appearing after the create form is submitted. The audit assertion
separately remains impossible until **T098** wires the audit table (`SheetDetailView.vue:246-262` has
no data binding at all).

T322's scope was fixture *data*. It is delivered, and it unblocks T054 and T171 without absorbing
their work.
