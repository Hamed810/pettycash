## What the tests found

The correction path exists and is routed (`appinfo/routes.php:26-28`), and both endpoints answer
`201`/`200`. It is also **inert**. Three of the four contract failures are the three ways US4/AC2 —
"the purchaser changes its business information and resubmits it" — can fail.

### 1. Resubmission activates the wrong revision — the corrections are discarded

`ExpenseTransaction::resubmitCorrection()` (`lib/Domain/Expense/ExpenseTransaction.php:217-219`) calls
`$this->activate($this->activeRevision)`. And `CreateCorrectionDraft::execute()`
(`lib/Application/Expense/CreateCorrectionDraft.php:63-82`) saves the new revision but **never attaches
it to the transaction** — its own comment says "We don't call activate() here", and then it saves the
transaction unchanged.

So `$this->activeRevision` is still the original, and the resubmission activates *that*. Measured:

```
--- Expected  1c6b8519-ba78-4453-aa28-898da99bf117   (the draft just created)
+++ Actual    77777777-7777-4777-8777-777777777777   (the fixture's original revision)
```

The purchaser's corrections are computed, persisted, and then dropped on resubmission. That is the
exact failure US4 exists to prevent, and it is what FR-049 (review restarts with the cost centre
manager) and FR-050 (the active revision determines current information) both forbid.

**No status code could have caught this.** The endpoint answers `200` and returns a well-formed
`TransactionDetail` throughout.

### 2. A correction draft cannot be edited at all

`PATCH /transactions/{id}` refuses with:

```json
{"error":{"code":"VALIDATION_FAILED","message":"Cannot update transactions in a submitted sheet"}}
```

`TransactionService.php:222` requires `$sheet->status === SheetStatus::Open`, and a returned
transaction's sheet is `CORRECTION`. But `contracts/workflow.md`'s Correction Contract clause 2 says
the owner may "create **and edit** the correction draft", and US4/AC2 has the purchaser change the
business information. **There is currently no way to correct anything.**

### 3. `POST /correction` ignores the required command id

`contracts/ocs-api.yaml:523-525` declares `X-PettyCash-Command-ID` required on both `POST /correction`
and `POST /resubmit`. `/correction` answers **201 without it**.

Worth being precise about why this is the opposite of the T318 DELETE case: a replayed resubmission
would activate a revision twice, so both of these are non-repeatable commands under `workflow.md`'s
own definition and the header is load-bearing. The client is currently left unprotected against a
double-clicked button.

### 4. `ReturnsQueueView` leaks an unhandled rejection

`src/views/reviews/ReturnsQueueView.vue:131` awaits `reviewsStore.fetchReturnsQueue()` from
`onMounted()` without catching; `src/stores/reviews.ts:69` rethrows after recording the message. The
rejection therefore has no caller.

`TransactionDetailView.vue:90-95` documents and fixes exactly this pattern in this same application
("none of which has a caller to react to a rejection, so it is absorbed here"), which is what makes
this a defect rather than a style preference.

Vitest reports it as a suite-level *error*, and `AGENTS.md` rules that out as a valid RED state. The
test file captures it through its own `unhandledRejection` listener and asserts on it, so the defect
surfaces as a **named failure** instead of noise. That is the single Vue failure.

## One assertion removed rather than left failing

My first draft asserted that **selecting a superseded revision hides the correction button**. It does
not — and on reading `workflow.md` clause 3 again, that behaviour is defensible: the button reflects
the *transaction's* status, and the draft begins from the **active** revision regardless of which one
the reader happens to be looking at. Asserting it would have been a UI opinion no artifact states.

The test now asserts `FR-048` immutability instead (no control alters a superseded revision), which
the artifacts do state.

## The 21 passing tests are evidence too

They pin behaviour that already holds, so T070–T076 cannot regress it while fixing the failures:

- the draft receives a **new revision identity** and carries the active revision's data forward
  (`workflow.md` clause 3);
- creating a draft does **not** activate it, and leaves the prior revision active (clause 5);
- the prior revision stays unchanged and viewable, and a correction only ever **adds** a revision
  (FR-048, US4/AC3);
- a correction is refused when the transaction is not awaiting correction (clause 1);
- prior revisions survive a resubmission (FR-048);
- the command id **is** required on `/resubmit`, and a replayed resubmission does not activate a
  second revision (the Command Contract);
- every revision carries the `Revision` schema's required members;
- the returned queue lists work, shows an empty state, and offers a retry;
- the detail view opens on the **active** revision and lets a reader inspect a superseded one.

## Notes for whoever implements T070–T076

1. **Fix 1 first.** It is the load-bearing one and it is a two-line domain change: the draft must
   become the transaction's revision. `CreateCorrectionDraft` currently returns a `TransactionRevision`
   that the transaction never references.
2. **Fix 2 is the gate on all of US4.** Until a draft is editable, correction cannot happen at all.
   The sheet-status check in `updateTransaction()` is the wrong place for this rule — it is a
   *transaction* state (`AWAITING_PURCHASER_CORRECTION`), not a sheet one, and the correction stage
   is exactly when a sheet is legitimately not open.
3. **Fix 3 is one line** and matches what T317 did for `POST`/`PATCH`.
4. **Fix 4 is a `.catch()`**, mirroring `TransactionDetailView.vue:97`.
5. `ResubmitCorrection.php:135` references `$explanation`, which is neither a parameter nor captured
   by the closure. `??` suppresses the warning so it evaluates to `''` — latent, not currently
   breaking, and not asserted by these tests because no artifact states what the explanation should be.
