# T255 — Hydrate the business fields the revision read path dropped

**Status**: Complete
**Feature**: PettyCash V1 Core Workflow (`specs/001-pettycash-v1-core`)
**Task**: T255 (Phase 27, CRITICAL) — recorded by the convergence after T221
**Date**: 2026-09-25

## Problem

`TransactionRevision` keeps four business fields as **private** properties:

```php
private ?string $description = null;
private ?string $costCenterId = null;
private ?string $expenseTypeTitle = null;
private bool $evidence = false;
private bool $active = false;   // also never hydrated
```

They are assigned only by `complete()`, the draft-to-submitted domain transition, which is called
from exactly one production site (`TransactionService.php:147`) plus the in-memory test doubles.
`DbTransactionRevisionRepository::mapRow()` set only the promoted *public* properties, so for
**every revision loaded from the database** those accessors returned `null` / `false`.

Three consequences, all reproduced live before the fix:

| Consumer | Effect |
|---|---|
| `ManagementReviewService:110` builds the authorization scope from `costCenterId()` | scope always empty → all 7 decision assertions `403` |
| `ExpenseSheet:62` `assertSubmittable()`; `ResubmitCorrection:87,90,93` | submit and resubmit `422` |
| `save():80,85,100,105` writes `description()` / `expenseTypeTitle()` back | **re-saving a loaded revision overwrites a real description with `''` and the expense type with `NULL`** |

The third is the serious one: silent business-data loss on every write, against the
historical-integrity guarantee in Constitution IV.

## Why a separate `hydrate()`

`complete()` cannot be reused for this. It throws `Submitted revisions are immutable` when the
revision is already active, and a revision read from the database is by definition already
submitted. Reusing it would make the read path depend on a domain transition that is illegal in
exactly the situation persistence is in. `hydrate()` is an explicit storage-restore path and keeps
the domain free of any Nextcloud dependency (ADR-003).

## Resolution decisions

- **`costCenterId` is the cost center's public UUID.** That is what `complete()` receives
  (`$costCenter->publicId`) and what `ManagementReviewService` and `ResubmitCorrection` treat as the
  cost-center identifier. `save()` persists only the numeric `cost_center_id`, so `mapRow()`
  translates the key back with `getCostCenterPublicId()`; without that, the field would still be null.
- **`hasEvidence` is derived, not stored.** `data-model.md` defines the evidence requirement as a
  validation over "active evidence related to the revision/transaction", and
  `pc_transaction_revisions` has no evidence column, so it is computed from active rows in
  `pc_evidence` on each read.
- **The active flag comes from `activated_at`**, which is the only signal the table carries.

## Limitations

- The `orX` call in `hasActiveEvidence()` is on `expr()`, matching the existing pattern in
  `DbRoleAssignmentRepository`; an LSP diagnostic reports it as undefined but
  `IExpressionBuilder::orX()` exists (container line 82) and the test run exercises the path.
- The currency is still hardcoded to `IRR` in the same `mapRow()` — that is T256 and was
  deliberately left out of this change.
- `ManagementReviewService:118` still passes the transaction's own cost-center code as the actor's
  scope and compares it to itself, so the scope check remains unable to deny; that is T257, and it
  is why fixing the null did not by itself close FR-004.
- The container runs `opcache` with `revalidate_freq => 60`, so a PHP edit can take up to a minute
  to reach live HTTP.
