## Complexity Tracking

> No constitution violations to justify. No entry.

The only complexity deliberately introduced is the dual identity of the work (`UI-PUR-*`/`BE-CR-*` cards **and** Spec Kit tasks). It is justified because the audit package is already the owner's working vocabulary and the repository's ADR-002 requires Spec Kit to own durable status; the mapping is the bridge, and `SC-005-001` makes an unmapped card a detectable failure rather than a silent one. A single-ID system was rejected: renumbering would break the owner's existing references, and Spec Kit-only tasks would leave the audit package as a competing status source.

The 2026-10-23 slice adds a second deliberate complexity: a client-side receipt staging queue because the existing evidence endpoint requires a transaction ID. A pre-transaction upload endpoint was rejected because it would introduce an orphan-evidence lifecycle, new authorization, and cleanup work that the owner did not approve. The queue is bounded to the create form, has no server-side state, and fails closed before the transaction exists. The trade is stated in `ADR-007`; the alternative (auto-creating a draft when the form opens) was rejected because it leaves abandoned transactions behind.

The 2026-10-24 amendment adds a third: it implements five cross-layer findings. The complexity is intentional because the defects cross layers — A needs a 001 contract change, D would need a domain decision — and silently "fixing" them in 005 would have violated the spec-before-implementation rule. The implemented scope keeps each finding with one owner, one gate, and testable acceptance instead of an untracked code edit. `T069` was deliberately split: the presentation half shipped under `G-11`, while the domain half waits for `G-13` and is not implemented.
