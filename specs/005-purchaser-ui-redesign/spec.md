## Clarifications

### Session 2026-10-27

- Q: May an `OPEN` sheet's source account change after creation, including to another account owned by the same purchaser, active, and denominated in the sheet's existing currency? → A: **No — the source account is immutable after creation.** The account is selected at creation and MUST NOT subsequently change. The sheet currency is also immutable after creation. While the sheet is `OPEN`, its owner may edit the title only. A title-only PATCH omits `accountId` and preserves the stored account — active or inactive — and currency. There is no account-changing path, no administrator or finance override, and no automatic conversion or reinterpretation of existing transaction amounts. This supersedes the earlier same-currency replacement answer.
- Q: What must happen when a PATCH supplies an `accountId`? → A: **Reject it before persistence.** Only omission is accepted. Any supplied value — including `null`, the current account, an inactive account, or an owned, active, same-currency target — is an attempted account assignment and MUST be refused with `422 VALIDATION_FAILED` and `fieldErrors.accountId`; no title, account, currency, or lock-version mutation is persisted.
- Q: When a sheet's current account has become inactive, may the purchaser still update the title, and may the account be replaced? → A: **Title-only remains allowed; replacement is not.** An inactive existing account MUST NOT block an authorized title-only update; the edit surface displays it accurately and read-only and preserves it.
- Q: Which sheet response payload should declare the authoritative `accountId`? → A: `SheetDetail` only. The public `accountId` is declared on the sheet detail payload used by the edit modal; `SheetSummary` and the Sheets List response remain unchanged and do not carry `accountId`.
- Q: What should happen when a sheet's stored account reference or currency already disagrees with the account record? → A: **Detect and report only.** Reads and writes are refused with `422 DATA_FAULT` until an authorized data fix resolves the record; no silent reassignment, auto-repair, or currency rewrite. Because an update never supplies an account, neither corruption variant is converted to `fieldErrors.accountId`.
- Q: Does the immutable account change where a sheet's transactions are financially settled? → A: No — settlement stays unchanged. Settlement continues to resolve from the transaction owner and the transaction currency under the existing approved rule; `sheet.accountId` is descriptive and is never a settlement instruction.

**Normative source (2026-10-27 reconciliation):** 001 `FR-019`/`FR-021` own the immutable-account
policy. This clarification records the purchaser-surface obligations and references those
requirements; it is not a second policy authority. The previous same-currency replacement policy and
its feasibility conflict are withdrawn; no account-model, schema, constraint, migration, or
second-account fixture change is authorized. The approved Create Sheet modal is unchanged.

### User Story 5 — Submission readiness and accessible, theme-native surfaces (Priority: P2)

A purchaser can see which transactions block submission because of a missing required receipt or another server-enforced field before pressing Submit, and the redesigned surfaces remain keyboard-usable, theme-native, reduced-motion-aware, and readable at 390px.

**Why this priority**: It improves the primary flow without adding a business capability. The evidence tier of the readiness surface is now approved by the 2026-10-23 owner directive and MUST be server-derived; it MUST NOT be guessed or left permanently `unknown`.

**Independent Test**: Open an OPEN sheet whose transaction lacks a cost center or a required receipt; the readiness region names each blocking transaction and the missing field, Submit remains reachable, and the server's 422 agrees. Verify a transaction whose expense type does not require evidence is not blocked for a missing receipt. Open a completed sheet; no readiness region. Emulate `prefers-reduced-motion: reduce`; the workspace opens without animation. Submit an invalid form; `aria-invalid` and a resolving `aria-describedby` are present.

**Acceptance Scenarios**:

1. **Given** an OPEN sheet with an incomplete transaction, **When** readiness renders, **Then** the blocking transaction and the missing server-enforced field are named.
2. **Given** an OPEN sheet with complete transactions, **When** readiness renders, **Then** no blocker is shown and submission succeeds.
3. **Given** a sheet with zero transactions, **When** readiness renders, **Then** the FR-024 blocker is shown and no Submit affordance is offered.
4. **Given** a submitted sheet, **When** it renders, **Then** no readiness surface is shown.
5. **Given** a transaction whose server-derived `evidenceRequired` is true and whose `evidenceCount` is 0, **When** readiness renders, **Then** that transaction is named as missing a required receipt; **Given** `evidenceRequired: false`, **Then** no receipt blocker is shown for it (FR-005-027).
6. **Given** `prefers-reduced-motion: reduce`, **When** the workspace opens/closes or tabs switch, **Then** no animation runs and no information is conveyed only by motion.
7. **Given** an invalid form submission, **When** errors render, **Then** each invalid control has `aria-invalid="true"` and `aria-describedby` resolves to the visible message.
8. **Given** the redesigned surfaces, **When** they render in light and dark themes, **Then** every colour comes from existing Nextcloud theme variables and the focus ring is visible.
9. **Given** the changed styles, **When** they are inspected, **Then** no hardcoded hex colour, local radius constant, or new font-family declaration was introduced.
10. **Given** `@nextcloud/vue` 9.x, **When** the surfaces render, **Then** no Vuetify component or new UI framework is present.
11. **Given** sheet submission or correction resubmission is refused because receipts are missing, **When** the `422` renders, **Then** every `transactions.<transactionId>.evidence` field error is mapped to the named transaction, focus moves to the first blocking transaction or the error summary, and a generic-only failure is not accepted (FR-005-037).
12. **Given** a returned transaction whose expense type does not require evidence, **When** the purchaser resubmits the correction without a receipt, **Then** the resubmission is not refused for that reason; **Given** an expense type that requires evidence, **Then** the resubmission is refused until an active receipt exists (FR-005-036, FR-091).

### Edge Cases

- **Stale version (409)**: the client reloads and lets the purchaser decide; it never field-merges (FR-025).
- **Deleted sheet while the workspace is open**: a clear not-found state, not a blank page.
- **Purchaser with no accounts**: sheet creation still works with `accountId` omitted (FR-020).
- **Deactivated cost center**: the preselect falls back to blank; no error is shown; the draft still saves (FR-022).
- **Sheet with zero transactions**: readiness shows the FR-024 blocker and no Submit control.
- **Missing English catalog**: English labels render raw keys; this is a `REC-01` product gap, not a completed English visual state.
- **Mixed calendar/language**: `fa` + Gregorian and `en` + Persian are legitimate combinations.
- **Deep link to a sheet**: the overlay model must keep the existing route addressable.
- **Nested dialog on mobile**: drilling into a transaction replaces the workspace body; the DOM must contain one dialog, not two.
- **Pagination ties**: identical timestamps must not duplicate or skip rows; this is a backend ordering requirement (`BE-CR-002`).
- **Returned transaction**: correction retains the prior revision and resubmission restarts at Cost Center.
- **Receipts selected before save**: the create form stages them; no upload request is issued until the transaction exists; an upload failure leaves the transaction saved and names the failed file; no empty-ID request.
- **Compact uploader at 390px**: a representative long filename does not wrap character by character, does not overflow horizontally, and the upload/remove controls remain operable; the full filename remains accessible on desktop and mobile, with any truncation accompanied by a usable, keyboard-accessible, touch-accessible way to inspect the full name; existing validation/progress/error behavior and supported accessibility interactions are unchanged.
- **Receipt-required versus receipt-exempt**: only the former blocks submission; a deactivated receipt does not satisfy the requirement; a changed expense-type setting is read at submission/resubmission time.
- **Partial staged-upload failure**: the transaction is not rolled back; retry is available from the edit surface; no orphan evidence row is created when creation itself fails.
- **Bodyless delete success**: a `204` with an empty body is success for a delete; it is not a malformed OCS response and no envelope is synthesized. A data-returning `200` that is an HTML login page remains a malformed response.
- **Delete replay**: the same command id and payload after a lost response returns the original `204`; a different command id after success returns `404` and is shown as already deleted/not found. `expectedVersion` is a concurrency guard, not a replay guard.
- **Draft transaction with evidence**: evidence does not block an otherwise authorized deletion; the server cascade removes the draft evidence rows and stored files. Evidence deletion itself remains effect-idempotent and header-free.
- **Transaction opened from a stale list**: the list summary carries no capabilities; the surface reads `GET /transactions/{id}` and the owning sheet's current state. If the sheet was submitted elsewhere, Edit/Delete disappear after refresh and no write is attempted.
- **Stale capability after a refused action**: a `409`, `422`, or `404` causes a transaction/sheet refetch before another action; the UI does not keep the refused action visible.
- **Preview of a non-inline-safe type**: SVG, HTML, an unknown MIME type, or a missing type is download-only. No iframe, object, image, or blob URL renders it in the Nextcloud origin.
- **Preview failure**: a `403`, `404`, network failure, or unreadable body shows an error and keeps the download action; it does not leave a blank dialog.
- **Legacy draft revisions**: already-stored draft revisions and draft-stage audit events remain in the database; the UI hides them from official history but never deletes, rewrites, renumbers, or backfills them (FR-053). No migration is part of `T069`.
- **Correction draft in progress**: a correction revision that has not been resubmitted is labelled as the working correction, not as a prior official revision; after resubmission it becomes part of the official history.
- **Concurrent list/detail requests**: a list refetch and a detail load may overlap; the detail must keep its loaded data, and a late superseded response must not overwrite a newer payload or clear another request's loading state.
- **Existing corrupted account reference or currency mismatch**: reads and writes are refused with `422 DATA_FAULT` — never a field-level `accountId` error, because no account is supplied — until an authorized data fix resolves the record; nothing is silently remapped, reassigned, or re-denominated (FR-005-019).
- **Fixture residue**: 41/31 transaction counts on the fixture sheets are test residue, not an expected product state; the debug-gated reseed restores 25/30/35/40 before and after a mutating browser run.
- **Dirty working tree**: generated `js/`/`css/` churn and pre-existing user changes must not be staged indiscriminately.
- **Stale generated assets**: the repository tracks build output; a build regenerates it. This is mechanical output, not hand-edited source.

#### Direction, locale, and formatting

A user-facing control to change it is **not authorized** by this feature; the mechanism may exist without a visible toggle.
- **FR-005-005**: Persian RTL, the 390px no-horizontal-scroll floor, visible focus, and keyboard operability MUST remain at least as strong as FR-071 requires. Adding English-LTR support MUST NOT weaken the Persian behavior.

#### Sheet list

- **FR-005-018**: The History tab MUST aggregate the existing per-transaction audit/revision endpoints, MUST render decision values from the event's `after` payload, MUST never render the literal `DECISION`, MUST page the audit feed honestly, and MUST display a per-transaction-aggregation disclaimer. No sheet-wide audit endpoint may be requested or invented.

#### Findings A–E: deletion, transaction surface, preview, history, and loading (2026-10-24 planning amendment)

- **FR-005-039**: A successful purchaser delete is a **bodyless `204 No Content`**. For `DELETE /transactions/{id}` and `DELETE /sheets/{id}`, the client MUST treat a 2xx response with an empty body as success and MUST NOT require, synthesize, or parse an OCS envelope; `pettycash.error.malformedResponse` MUST NOT be shown for a 204. A data-returning response with no valid envelope MUST still be rejected, including a `200` HTML login/proxy page. The transaction delete MUST carry one `X-PettyCash-Command-ID` per delete intent and the current `expectedVersion`; a retry after an unknown outcome MUST reuse that id. Under the approved contract (001 FR-025; 001 `T436`), the same id and payload MUST answer the original 204 even after the row is gone; a different id after success MUST answer 404, which the client MUST present as already deleted/not found and MUST NOT convert into a second success or an unhandled error. `expectedVersion` remains a concurrency guard, not a replay guard. Evidence attached to the draft MUST NOT block the delete; the server cascade removes its draft evidence rows and stored files. Evidence deletion remains effect-idempotent and header-free. A delete confirmation MUST issue exactly one request while in flight.
- **FR-005-040**: A transaction row action MUST open a transaction surface backed by `GET /transactions/{id}` (`TransactionDetail`). The surface MUST source its capability set from `TransactionDetail.allowedActions`; it MUST NOT infer capabilities from `TransactionSummary` (which carries none), from the list row, from a local role, or from a guessed status. While the detail request is in flight the surface MUST show a local loading state; a `404` MUST render a not-found state with a way back/refresh; a network or malformed response MUST offer retry and keep the workspace intact. Opening the surface MUST NOT issue a write. It MUST render the returned active revision, status, version, evidence, and revisions without inventing values, and it MUST satisfy C-07's single-dialog rule and the 390px floor whether it is a workspace layer or the addressable transaction route.
- **FR-005-041**: An action MUST be offered only when **both** the server capability is exactly `true` in `allowedActions` **and** the owning sheet's current server state permits it. Edit and Delete require `canEdit`/`canDelete` **and** `sheet.status === OPEN`. Correct requires `canCorrect` and the transaction's `AWAITING_PURCHASER_CORRECTION` state; it MUST NOT be conditioned on `OPEN`, because a returned transaction lives in a `CORRECTION` sheet. Review capabilities (`canApprove`, `canReject`, `canReturn`) belong to the review surfaces and MUST NOT be presented as purchaser actions. The client MUST read sheet state and transaction state independently: it MUST NOT infer transaction permission from sheet status or sheet permission from transaction status. A `409`, `422`, or `404` from an action MUST trigger a transaction and sheet refetch before another action; a stale action MUST disappear after the refetch. A non-DRAFT transaction MUST offer no Edit/Delete, and a non-returned transaction MUST offer no Correct.

  | Action | Server capability | Additional state | Refusal behavior |
  |---|---|---|---|
  | Edit | `canEdit === true` | owning sheet `OPEN` | refetch; hide if the sheet or transaction moved |
  | Delete | `canDelete === true` | owning sheet `OPEN` | refetch; `409`/`422` explained; `404` = already gone |
  | Correct | `canCorrect === true` | transaction `AWAITING_PURCHASER_CORRECTION` (sheet `CORRECTION`) | refetch; hide if no longer returned |
  | Approve/Reject/Return | review surfaces only | review stage and policy | not a purchaser action |

- **FR-005-042**: Active evidence MUST offer a preview action to an authorized viewer. The preview MUST request `GET /evidence/{id}/content?disposition=inline` and render only when the stored media type is inline-safe: `application/pdf`, `image/png`, `image/jpeg`, `image/gif`, `image/webp`, `image/bmp`, or `text/plain` (parameters dropped, comparison case-insensitive). `image/svg+xml` is deliberately not inline-safe and MUST be download-only; no preview, iframe, object, image, or blob URL may render SVG, HTML, or any other non-inline-safe type. A non-inline-safe type MUST offer download via `disposition=attachment` (or the existing download path) and MUST NOT show a broken preview. `text/plain` MUST render as text, never as markup; no `v-html`, `innerHTML`, or `dangerouslySetInnerHTML` may be used. A preview failure (`403`, `404`, network, unreadable body) MUST show an error, keep download available, and allow retry/close. The preview dialog MUST have an accessible name equal to the file name, focus entry and return, Escape close, no horizontal scroll at 390px, and no second `[role="dialog"]`. Object URLs MUST be revoked on close/unmount; preview MUST NOT trigger a download or an upload. Inactive evidence keeps its metadata and history but offers no content preview unless the existing download policy explicitly permits it.
- **FR-005-043**: A transaction that has never been submitted MUST NOT present a revision selector, revision tabs, a prior-revision list, or draft-stage audit events as official history. `DRAFT` is the explicit never-submitted state; the client MUST derive it from the transaction's status, not from the revision count. The surface MUST show one working-draft state without inventing a revision number, and the workspace History aggregation MUST omit that transaction's events from official history. For a submitted transaction, official history begins with the submission; legacy events whose `stage` is `DRAFT` and whose type is `REVISION_CREATED` or `TRANSACTION_CHANGED` MUST be filtered from the official view. A correction revision that has not been resubmitted MUST be labelled as the working correction, not as a prior official revision. Stored revisions and audit events MUST NOT be deleted, rewritten, renumbered, or backfilled (FR-053). The domain boundary remains **proposed** in `ADR-008` and gated as 001 `T437`; the presentation change MUST NOT claim the domain boundary is implemented while `T437` is open.
- **FR-005-044**: Loading state MUST be isolated per resource and per request. A sheet-list refetch, a sheet-detail load, a transaction-detail load, an evidence fetch, a history fetch, and a mutation MUST NOT share one boolean that can replace a loaded surface with another resource's loader. The sheet workspace MUST show its full-page “loading sheet” state only when no sheet for the current id is loaded and a detail request is in flight; a list refetch, a transaction fetch, or a mutation MUST NOT trigger it. A mutation MUST expose its busy state on the initiating control or region and MUST NOT unmount loaded data. Concurrent requests MUST be resolved by request identity/token or an equivalent mechanism so a late response from a superseded request cannot overwrite newer data or clear another request's loading state. A failed background refetch MUST keep the last loaded data and show the error. The 390px and RTL layout MUST remain stable while loading.

### Key Entities

These are **presentation and management entities**, not new persisted domain entities.

- **Locale context**: active language, resolved locale, derived direction.
- **Calendar preference**: Persian or Gregorian; display-only; persisted per device in `pettycash.calendarPreference`; no stored date value changes.
- **Sheet list session**: page, filters, scroll offset, and return marker for a detail/edit/create round trip.
- **Workspace state**: sheet ID, active tab, nested transaction view, and the invoking row used for focus return.
- **Readiness model**: per-transaction blockers derived only from server-enforced preconditions. Each blocker names the transaction and the field; receipt blockers use the server-provided `evidenceRequired` and active `evidenceCount` and are present only when `evidenceRequired` is true. There is no permanent `unknown` evidence state after `T057`.
- **Receipt staging queue**: the in-memory list of files selected before the first save. Each item has a local identity, name/size/type, and upload state (`staged`, `uploading`, `attached`, `failed`). No item has a transaction ID before creation; an upload is never attempted in that state.
- **Transaction surface state**: the transaction ID, the loaded `TransactionDetail`, the source of the capability set (`allowedActions`), the owning sheet's independently fetched state, and the loading/not-found/error state. The list summary is never a capability source.
- **Delete command intent**: the transaction ID, the single `X-PettyCash-Command-ID`, the `expectedVersion`, and the phase (`idle`, `in-flight`, `confirmed`, `failed`, `unknown`). The id is reused across retries of the same intent and is never regenerated for a retry.
- **Preview state**: the evidence ID, stored media type, inline-safe verdict, object-URL lifetime, and failure message. It never owns a second copy of the inline-safe policy; it applies the server's closed set.
- **Per-resource loading state**: the independent loading/error state for the sheet list, sheet detail, transaction detail, evidence, history, and each mutation, with a request token that makes a superseded response ignorable.
- **Development fixture set**: four debug-gated sheets of 25, 30, 35, and 40 transactions with deliberate receipt coverage (baseline 130 transactions / 66 receipts). It is verification data, not a domain entity and not production seed data; reseeding the fixture namespace restores the baseline.
- **Traceability record**: card ID, requirement IDs, canonical task IDs, current status, evidence, and gate.
